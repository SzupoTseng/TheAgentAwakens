# 第16章　机台通信：SECS/GEM 的毫秒疏洪

## 情境 11　内核机台 SECS/GEM 突发断线(T3 Timeout)的毫秒级自动闪复
**背景**：12 吋厂黄光区一台 EUV 微影机，通过 HSMS-SS over TCP/IP 与 EAP（Equipment Automation Program）长连接，承载即时的 Job 派送与 RMS 配方下载。
**问题**：凌晨 03:17，EAP 对机台发出 S2F41 远程指令后，等不到 S2F42 回复，T3 Reply Timeout（45 秒）一触即发。连接进入 NOT SELECTED 状态，机台 Control State 从 ONLINE/REMOTE 跌回 LOCAL，**整条 lot 的曝光被冻结在 plasma 尚未稳定的窗口内，每滞留一秒等于 2.3 万美元在边缘燃烧**。值班只看到 MES 一片标红，却说不清是网络、是机台堆栈、还是 EAP driver 自己卡死。
**需要的技能**：HSMS 连接状态机（CONNECTED/SELECTED/NOT-SELECTED）判读、SECS-II 报文(SxFy)解析、TCP 半开连接侦测、机台 Control State 复归流程。
**开源工具**：`secsgem`（Python SEMI 协定栈）、`Wireshark` + HSMS dissector、`tcpdump`、`Prometheus` 连接健康度埋点。
**用到的 Agent 特性**：龙虾 OpenClaw 的**本地脚本运行**监听 EAP driver 的 T3 计时器，在 Timeout 触发前 8 秒就以 `secsgem` 补发一记 Linktest.req 探活——确认是 TCP 半开而非机台真死后，**子 Agent** 立刻走 HSMS Separate→Select 重握手，重新拉起 SELECTED 状态并重送被吞掉的 S2F41；同一时间**Multi-Channel Gateway** 把「T3 将触发→已自愈，耗时 740ms」的时间轴同步推到值班 Teams 与现场 Andon 灯，附上重连前后的封包对照。
**没有 Agent 的窘境**：工程师被 call 醒、VPN 连接、开 Wireshark 抓包、肉眼比对 SELECT.req/rsp，等他判断出是半开连接时 lot 早已 scrap，MTTR 动辄 30 分钟起跳。
**效益**：T3 断线自愈 MTTR 从 30 分钟 → **740 毫秒**；单批晶圆免于报废，一次事件守住约 280 万美元。

> 💡 君之一席话
> 「Timeout 不是故障的终点，而是 Agent 介入的起跑线——人类在计时器归零时才惊醒，机器在计时器过半时就已出手。」

> 🔍 高端点评──道路在哪里
> 这个案例把龙虾从「事后告警」推向「Timeout 前的抢跑」，指向一条**预测式介入**的道路：未来 Agent 不再等故障坐实，而是在状态机的转移边缘下注。但抢跑的代价是误判——它在 740ms 内替人类重握了连接，这要求我们先划清「哪些握手动作可无人放行、哪些必须留人类最后一签」。真正的工程难题不在重连脚本，而在如何让 Agent 的自信阈值与机台的物理风险等级对齐。

## 情境 12　EAP 与机台 SECS 报文堆积(Message Queue Overflow)的智能疏洪
**背景**：一台 CVD 机台在 idle 后突然进入连续 alarm 风暴，每秒对 EAP 喷出数百笔 S5F1（Alarm Report），EAP 的收信队列开始倒灌。
**问题**：09:42，EAP 入站 queue 从常态 50 笔暴冲到 **4.7 万笔未消化**，driver 的 ack（S5F2）来不及回，机台端误判 EAP 失联，**正在进行 collection event 的另外 6 台机台 SECS 心跳一起延迟**，整个 toolgroup 面临连锁 OFFLINE。内存水位 92%，再撑 90 秒 EAP process 就会 OOM 被 kill，那意味全区 host 通信一起断。
**需要的技能**：SECS-II message queue 背压分析、Alarm 风暴源头定位、collection event 报告流量调节、EAP driver 内存水位管理。
**开源工具**：`secsgem`、`RabbitMQ`（报文缓冲中介）、`Grafana`、`htop`/`pidstat`。
**用到的 Agent 特性**：龙虾的**子 Agent** 即时对入站流做分群统计，定位出 4.7 万笔有 93% 是同一支温控 sensor 的抖动引发的重复 S5F1；**ClawHub 现成技能插件**加载「SECS Alarm 去抖」skill，对该 ALID 做秒级节流并对机台补发 S5F3（Enable/Disable Alarm Send）暂时关闭这条噪音，同时把堆积的有效报文导入 RabbitMQ 旁路慢慢消化；**Multi-Channel Gateway** 在群组贴出「queue 4.7万→已疏洪至 600，OOM 风险解除」的水位曲线。
**没有 Agent 的窘境**：人类得先 SSH 进 EAP 看 queue、再翻 alarm log 找出是哪支 sensor、手动下 S5F3——这套流程跑完，EAP 早被 OOM killer 收走，6 台机台跟着掉线。
**效益**：队列水位 4.7万 → 600 笔；EAP 免于 OOM；toolgroup 连锁断线归零，疏洪耗时 **22 秒**。

> 💡 君之一席话
> 「报文堆积从来不是水管太细，而是没人去关掉那个漏水的龙头——疏洪的智能，一半在排水，一半在找源。」

> 🔍 高端点评──道路在哪里
> 这里龙虾做的不只是「扩大缓冲」，而是**溯源节流**，这指向一条「治本式流量治理」的道路。但对机台下 S5F3 关闭某条 alarm，本质是 Agent 替工程师做了「忽略哪些告警」的决定——这是一条极危险的信任边界：被关掉的 sensor 若恰好是真实异常的前兆怎么办？落地时，Agent 必须能区分「噪音抖动」与「真实劣化的高频前兆」，这需要把机台健康模型而非单纯流量统计喂给它。

## 情境 13　SECS 队列溢出(Queue Overflow)的在线智能疏洪与动态解锁
**背景**：量产旺季，一座 EAP 同时挂 38 台机台，host 端的 SECS 发送队列采固定深度 8192 的环形缓冲。
**问题**：14:05 派工高峰，EAP 对机台群批量下 S16F11（Process Job Create），出站队列瞬间打满 8192 并开始**丢弃尾部报文**，3 台机台没收到 Job 却不报错——它们安静地停在 idle，**WIP 在 buffer 里堆成假性 fab down，产线调度系统却显示一切正常**，这种「沉默的卡死」比明着当机更致命，等到 OEE 报表掉下来已是两小时后。
**需要的技能**：环形缓冲溢出侦测、SECS 出站背压建模、Process Job 生命周期追踪、机台 idle 假死辨识。
**开源工具**：`secsgem`、`Redis`（动态溢出旁路队列）、`Prometheus`、`Locust`（压测重放）。
**用到的 Agent 特性**：龙虾**本地脚本运行**持续比对「已发 S16F11 数」与「收到 S16F12 ack 数」的差额，一旦差额随队列深度同步逼近 8192 即判定溢出在即；**子 Agent** 动态把出站深度临时扩到 12288 并将溢出报文落地到 Redis 旁路重送队列，同时对那 3 台 idle 机台逐一补发遗失的 Process Job 并验 S16F12；**Multi-Channel Gateway** 把「沉默卡死 3 台→已解锁补派」推给派工台与调度工程师。
**没有 Agent 的窘境**：没人会去看一个「显示正常」的系统，这 3 台机台会一直 idle 到产出对不上、被调度稽核才暴露，等于白白烧掉两小时产能。
**效益**：队列溢出零丢包；假死机台从「两小时后才发现」→ **即时补派**；单次救回约 5 千片 WIP 的卡关时间。

> 💡 君之一席话
> 「最可怕的不是系统当机尖叫，而是它一脸平静地告诉你『一切正常』——疏洪的第一步，是先学会怀疑那份平静。」

> 🔍 高端点评──道路在哪里
> 这个案例的价值在于发现了「沉默的丢包」，它把龙虾推向一条「对账式可观测性」的道路——不信任任何单一仪表板，而靠发送/回执的差额去逼出真相。未来这种对账能力会是无人工厂的免疫系统。工程难题在于：当 Agent 开始质疑「显示正常」的系统并自行补派 Job，它就在绕过原有的调度权威——这要求一套清晰的「补偿动作可追溯帐本」，否则两个自动化系统会在同一批 WIP 上打架。

## 情境 14　HSMS 报文快照超时(Linktest Timeout)的在线智能疏洪
**背景**：跨机房长距布线下，一台量测机(Metrology)通过 HSMS 与 EAP 连接，靠周期性 Linktest 维持心跳。
**问题**：02:50，机房间光纤链路出现微突发抖动，连续 3 个 Linktest.req 未在 T6（5 秒）内收到 rsp，HSMS 判定链路死亡并 Separate，**但机台其实活着、正在跑 CD-SEM 量测，连接一断它的量测结果报文(S6F11)全部积在机台侧发不出去**。EAP 端则开始无谓地反复重连，每次重连都重新订阅 collection event，把刚刚清掉的队列又灌回来。
**需要的技能**：HSMS T5/T6/T7/T8 计时器调校、光纤链路抖动辨识、量测结果报文补传、重连风暴抑制。
**开源工具**：`secsgem`、`mtr`/`smokeping`（链路品质）、`Wireshark`、`fluent-bit`（报文落地）。
**用到的 Agent 特性**：龙虾**子 Agent** 拉 `mtr` 即时量到是链路 jitter 而非机台死亡，于是不急着让 EAP 硬重连，而是**动态把 T6 从 5 秒临时放宽到 8 秒**度过抖动窗口，避免 Separate；**ClawHub 现成技能插件**加载「HSMS 重连退避」skill，对残余重连加上指数退避，杜绝重订阅风暴；待链路平稳，**本地脚本运行** 驱动机台补吐积压的 S6F11 量测报文并核对 data id 连号无漏；**Multi-Channel Gateway** 同步「链路抖动已平、量测报文 0 遗漏」到群组。
**没有 Agent 的窘境**：人类面对的是「机台明明在跑却连不上」的鬼打墙，多半会直接重启 EAP driver——一重启，整批量测 context 遗失，CD-SEM 数据对不回 wafer id，量测白做。
**效益**：靠动态放宽 T6 避免无谓 Separate，量测报文 0 遗漏；重连风暴消除，省下一轮全机台重订阅（约 4 分钟）。

> 💡 君之一席话
> 「心跳停了不一定是人死了，可能只是听诊器接触不良——把链路抖动误判成机台死亡，是运维最昂贵的庸医之误。」

> 🔍 高端点评──道路在哪里
> 龙虾在此最关键的一步是**动态调整协定计时器**（临时放宽 T6），这指向「自适应协定参数」的道路：未来 Agent 不只在应用层补救，更能在传输层按环境即时调参。这是巨大的能力跃升，也是巨大的信任边界——HSMS 计时器是 SEMI 标准的一部分，Agent 私自放宽会不会让某些边缘故障被掩盖？落地时必须把这类「调参」锁在可审计、可回滚、有上限的安全笼里，否则自适应会退化成自欺。

## 情境 15　EAP 与机台通信报文堆积的动态解锁(Deadlock Breaking)
**背景**：一台离子布植机(Implanter)与 EAP 之间采严格的 SECS 交握序：每一笔 S6F11 都必须等 S6F12 ack 才发下一笔（同步交握）。
**问题**：11:30，机台与 EAP 各自的 transaction id 计数器因一次重连对不齐，**机台在等 EAP 对第 N 笔的 ack，EAP 却在等机台对第 N-1 笔的回复**——典型的交握死锁。双方队列各堆了上千笔互相等待的报文，谁也不肯先走，机台 Control State 卡在 ONLINE 但完全不动作，**一炉正在布植的 wafer 拿不到下一步指令，剂量窗口正在流逝**。
**需要的技能**：SECS transaction id（system bytes）对齐、同步交握死锁辨识、单向 ack 注入解锁、布植剂量时序保护。
**开源工具**：`secsgem`、`py-spy`（卡死线程快照）、`Grafana`、`jq`（报文日志解析）。
**用到的 Agent 特性**：龙虾**子 Agent** 对两端 SECS log 做 system bytes 交叉比对，一眼认出是 transaction id 错位造成的循环等待；**本地脚本运行** 以 `secsgem` 精准补注一笔对齐用的 S6F12 给 EAP，打破循环、让较旧的那笔先结算；**ClawHub 现成技能插件** 加载「交握串行校正」skill，把后续 system bytes 重新对齐到同一基准，恢复同步流；**Multi-Channel Gateway** 把「交握死锁→已注入解锁、布植剂量窗口保住」连同死锁前后的 transaction 图谱推给设备工程师。
**没有 Agent 的窘境**：交握死锁在 log 上看起来「双方都在正常等待」，人类极难辨识，标准动作是 reset 机台通信——一 reset，布植中的那炉剂量时序断裂，整炉 scrap。
**效益**：死锁解除无需 reset；剂量窗口保住，整炉约 25 片高价 wafer 免于报废；解锁耗时 **9 秒**。

> 💡 君之一席话
> 「死锁的本质是双方都太守规矩——当两个系统都在礼让，反而没人通过路口时，需要一只手轻轻推一把那个该先走的人。」

> 🔍 高端点评──道路在哪里
> 这是全章最微妙的一手：龙虾**主动注入一笔协定报文去打破对称僵局**。它指向「协定层调停者(arbiter)」这条道路——Agent 不再只是信道，而是能介入两个系统间的握手仲裁。但这也是信任边界最薄的地方：注入错一笔 ack，可能让两端状态永久不一致。未来这种「调停权」必须创建在对交握语意的形式化理解上，且每一次注入都要能被双方系统事后对账确认——否则 Agent 解一个死锁，会种下三个更深的不一致。

## 情境 16　GEM Collection Event 报告风暴(Report Flooding)的订阅瘦身
**背景**：新导入一台薄膜机，工程师为了 debug 暂时对 EAP 打开了几乎全部 CEID（Collection Event）的 DVVAL 上报，事后忘了关。
**问题**：机台一进量产，每个 process step 触发数十个 CEID，每个 CEID 又夹带上百个 DVVAL，**S6F11 报文以每秒 1.2MB 的速率灌向 EAP**，host 端写 trace DB 的磁盘 IO 直接打满，MES 查找全线变慢，其他机台的正常上报也被拖累延迟。
**需要的技能**：GEM Report/CEID/DVVAL 订阅关系梳理、S2F33/S2F35（Define Report/Link Event Report）动态重配、trace 写入背压、必要 vs debug 事件分级。
**开源工具**：`secsgem`、`TimescaleDB`（trace 时序库）、`Grafana`、`iotop`。
**用到的 Agent 特性**：龙虾**子 Agent** 统计出 87% 的 S6F11 流量来自 12 个纯 debug 用的 CEID；**ClawHub 现成技能插件** 加载「GEM 订阅治理」skill，通过 S2F35 动态解除这 12 个 CEID 与 report 的链接、只保留量产必需的事件，**全程不重启通信**；**本地脚本运行** 把瘦身前后的订阅清单存盘备查；**Multi-Channel Gateway** 把「上报流量 1.2MB/s→180KB/s、磁盘 IO 回落」推给设备与 IT 双方群组。
**没有 Agent 的窘境**：人类得手动对照机台 EDS（Equipment Data Spec）一条条找出哪些 CEID 是 debug 残留，再小心下 S2F35——做错一条就可能把量产必需的 event 也关掉，多数人宁可忍着流量不敢动。
**效益**：上报流量降 85%，磁盘 IO 解压，MES 查找延迟恢复；订阅治理 **全程零中断**。

> 💡 君之一席话
> 「最大的流量灾难，往往源自一个忘了关掉的 debug 开关——可观测性若没有节制，本身就会变成最大的不可观测。」

> 🔍 高端点评──道路在哪里
> 龙虾在这里扮演「订阅的园丁」，动态修剪 GEM report，指向「自治理的遥测平面」这条道路。未来机台与 host 间的数据订阅量级只会更大，靠人手维护 EDS 订阅表终将崩溃。但 Agent 替你决定「哪些事件可以不上报」时，它就在定义工厂的数据边界——被修剪掉的 DVVAL 若日后追溯异常时刚好需要怎么办？这条路的工程内核，是让修剪可逆、可解释，并与下游的数据需求方做出契约式协商，而非单方静默裁剪。

## 情境 17　多机台 SECS 报文时间戳漂移(Clock Skew)的对齐校正
**背景**：FDC（Fault Detection & Classification）系统依赖各机台 S6F11 报文里的 timestamp 做跨机台关联分析。
**问题**：一次 NTP 服务器抖动后，厂内 9 台机台的本地时钟漂移了 0.3～2.1 秒不等，**它们上报的 SECS timestamp 各说各话**，FDC 把同一片 wafer 在前后站的数据对不上时序，误判出一条根本不存在的「异常温升趋势」，差点据此 hold 住一整条产线。
**需要的技能**：SECS timestamp 时序对齐、多机台 clock skew 量化、FDC 关联窗口校正、NTP 漂移补偿。
**开源工具**：`secsgem`、`chrony`（NTP 校时）、`InfluxDB`、`Pandas`（时序重对齐）。
**用到的 Agent 特性**：龙虾**子 Agent** 用一笔已知同步事件做基准，反推出 9 台机台各自的时钟偏移量；**本地脚本运行** 在 SECS 报文进 FDC 前挂一层校正中介，按各机台偏移量即时补正 timestamp，同时驱动 `chrony` 把机台重新对回权威时钟；**ClawHub 现成技能插件** 加载「时序对齐」skill 重算 FDC 关联窗口，**那条虚假的温升趋势随即消失**；**Multi-Channel Gateway** 把「时钟漂移 9 台已校正、FDC 误判已撤」推给良率与设备工程。
**没有 Agent 的窘境**：人类面对 FDC 报出的「温升趋势」第一反应是相信它，于是 hold 线、查机台、开 case——折腾半天才有人想到去比对机台时钟，这期间产线停摆的损失远超假趋势本身。
**效益**：时钟偏移即时补正，FDC 假趋势撤除，避免一次全线误 hold（约停机 40 分钟）；9 台机台校时收敛至 10ms 内。
**效益补充**：跨站数据时序重新可信，FDC 关联准确率回到基线。

> 💡 君之一席话
> 「当数据对不上时，先别急着怪机台——很多时候，是它们手表上的时间从一开始就没对齐。」

> 🔍 高端点评──道路在哪里
> 这个案例把龙虾推向「数据可信度的守门人」角色：在数据进入分析系统前先校正它的时间基准。这指向一条「前置数据治理」的道路——Agent 成为遥测流的清洗闸门。工程挑战在于，校正本身也是一种篡改：Agent 改写了机台上报的原始 timestamp，这在追溯与合规上是敏感动作。未来要走通，必须做到「原始值与校正值并存留痕」，让校正透明可审，而不是让清洗后的数据冒充原始真相。

## 情境 18　SECS-II 报文结构非法(Malformed SxFy)的在线熔断与隔离
**背景**：一台老机台固件升级后，偶发吐出 SECS-II body 结构不合 SEMI E5 规范的畸形 S6F11（list 长度字段与实际 item 数不符）。
**问题**：07:20，EAP driver 的 SECS-II parser 撞上这笔畸形报文直接抛例外，**而它对所有入站报文是单线程串行解析**——一笔畸形报文卡住整条解析链，后面排队的合法报文全部堵死，这台机台的所有上报瞬间「全黑」，连 alarm 都送不出来。
**需要的技能**：SECS-II E5 结构校验、parser 异常熔断、畸形报文隔离与旁路、机台固件兼容性判读。
**开源工具**：`secsgem`、`Hypothesis`（结构模糊测试）、`Sentry`（异常聚合）、`jq`。
**用到的 Agent 特性**：龙虾**本地脚本运行** 在 parser 前置一道轻量结构预检，第一时间拦下这笔 list 长度不符的畸形 S6F11，**熔断它而不让它进主解析链**，后面的合法报文照常流过；**子 Agent** 把畸形报文整包旁路落地、用 `Hypothesis` 反推畸形 pattern，比对出是固件某版本在特定 DVVAL 组合下的编码 bug；**ClawHub 现成技能插件** 自动生成一份含复现条件的设备异常单推给原厂；**Multi-Channel Gateway** 同步「畸形报文已隔离、主链未中断、根因疑为固件 vXX」。
**没有 Agent 的窘境**：人类看到的是「机台整个没声音」，会先当断线去查网络、查连接，绕一大圈才发现是一笔畸形报文噎死了 parser——这期间机台事实上是个黑盒，任何 alarm 都送不出来，风险敞口巨大。
**效益**：畸形报文熔断隔离，主解析链 0 中断；机台「全黑」时间从潜在数十分钟 → **0 秒**；附带交付一份可复现的固件 bug 单。
**效益补充**：parser 串行卡死的单点风险被旁路化解。

> 💡 君之一席话
> 「一笔畸形报文不该有能力噎死整条解析链——真正的健壮，不是不出错，而是让一个错误无法传染给它的邻居。」

> 🔍 高端点评──道路在哪里
> 龙虾在这里做的是「协定层的熔断与舱壁隔离」，指向一条「容错通信闸道」的道路：把每一笔报文当作不可信输入来防御。这对 SECS/GEM 这种数十年标准、机台固件良莠不齐的场域尤其关键。下一步的工程问题是规模——当 Agent 开始熔断、旁路、自动开异常单，它就成了人与原厂之间的缓冲层；如何避免它「过度宽容」地把真实的协定退化也一并熔断掉、让问题被掩盖，是这条路上必须划清的容错与纵容之间的那条线。

## 情境 19　机台 Control State 非预期跌落(Online→Local)的自动复归
**背景**：产线规定机台必须维持 GEM 的 ONLINE/REMOTE 状态才能接受 EAP 远程派工，操作员偶尔会误触机台面板把它切到 LOCAL。
**问题**：晚班 21:40，一台 PVD 机台被操作员不经意切到 ONLINE/LOCAL，**EAP 的 S2F41 远程指令全部被机台以「not in remote」拒收**，但 MES 接口上机台仍亮绿灯（连接正常）、没有任何 alarm，派工持续被静默拒绝，**WIP 在这台机台前无声堆积，直到一小时后现场人员路过才发现它一直 idle**。
**需要的技能**：GEM Control State Model 理解、S1F17/S1F15（Request ONLINE/OFFLINE）操作、远程复归与操作员权限边界、静默拒收侦测。
**开源工具**：`secsgem`、`Node-RED`（状态流可视化）、`Prometheus`、`Alertmanager`。
**用到的 Agent 特性**：龙虾**本地脚本运行** 周期轮询各机台 S1F3（Selected Equipment Status）里的 Control State，发现这台从 REMOTE 跌到 LOCAL 且已持续 3 分钟无派工；**子 Agent** 判断此刻无人在机台前做手动维修（无 maintenance lockout 标记），于是以 S1F17 请机台切回 ONLINE/REMOTE 并补发被拒的 S2F41；**Multi-Channel Gateway** 不只告知，还把「机台被切 LOCAL→已复归 REMOTE、谁在何时切的」连同面板操作时间轴推给现场班长，兼具复归与追责。
**没有 Agent 的窘境**：绿灯亮着、没有 alarm，没人会怀疑一台「看起来正常」的机台在罢工，往往要到 WIP 报表异常或交班巡检才发现，白白损失一小时产能。
**效益**：Control State 跌落从「一小时后巡检才发现」→ **3 分钟内自动复归**；附带操作追溯，杜绝重犯。

> 💡 君之一席话
> 「绿灯不等于在工作——机台最危险的状态，是它一边亮着健康的灯，一边安静地拒绝着每一个指令。」

> 🔍 高端点评──道路在哪里
> 这个案例让龙虾从「通信运维」跨入「状态治理」，它指向「机台状态的主动巡查与复归」这条道路。价值在于它替工厂盯住了「连接正常但行为失能」这层人类仪表板照不到的盲区。但替操作员把机台切回 REMOTE，是 Agent 跨越物理现场权限的一步——万一操作员是为了维修才切 LOCAL，Agent 强行复归可能带来安全风险。落地的关键，是让 Agent 能可靠读到现场的「维修意图」信号（lockout/tagout 状态），把自动复归严格限定在「无人为意图」的前提内。

## 情境 20　量产换线 SECS 配方下载失败(Recipe Download Mismatch)的自动校验回滚
**背景**：换 product 时，EAP 通过 S7F3（Process Program Send）把新 RMS 配方下载给机台，下载后须以 S7F5 取回比对确认一致。
**问题**：02:05 夜班换线，一笔 EUV 配方在 S7F3 下载过程中因封包重传，机台落地的配方比 EAP 来源**多了 14 个 byte 的尾部残留**，但机台回的 S7F4 ack code 是 0（接受）。**若就此放行，下一炉 wafer 将用一份被污染的配方曝光，整批 scrap，且因 ack 显示成功，事后极难追到是下载污染。**
**需要的技能**：S7F3/S7F4/S7F5 配方下载交握、PPID/PPBODY 内容校验（hash 比对）、配方污染回滚、换线放行 gating。
**开源工具**：`secsgem`、`xxd`/`hexdump`（字节级比对）、`git`（配方版本留痕）、`Prometheus`。
**用到的 Agent 特性**：龙虾**本地脚本运行** 在 S7F4 回 ack=0 后不轻信，立刻发 S7F5 取回机台实际落地的 PPBODY，对 EAP 来源做 SHA-256 逐比特比对，**揪出那 14 byte 的尾部残留**；**子 Agent** 判定配方被污染，自动阻挡这台机台的换线放行（gating），并重发一次干净的 S7F3、再校验至 hash 一致才解除 gating；**ClawHub 现成技能插件** 把这版配方的来源 hash 与落地 hash 一并写进 `git` 留痕；**Multi-Channel Gateway** 把「配方下载污染 14B→已重下并校验一致、换线放行」推给换线工程师与品保。
**没有 Agent 的窘境**：ack=0 代表机台「说它收好了」，人类几乎不会再去逐比特核对配方内容，于是污染配方堂而皇之上线——这类事故往往要等整批 wafer 量测异常、回头翻 log 才被发现，损失以整批计。
**效益**：配方污染在曝光前被拦下，整批 EUV wafer（约 4 百万美元）免于 scrap；换线放行从「凭 ack 盲信」→ **hash 级强校验**，全程附版本留痕。

> 💡 君之一席话
> 「机台说『我收好了』和它『真的收对了』是两回事——在百万美元的赌桌上，唯一可信的 ack，是你自己亲手比对过的那串 hash。」

> 🔍 高端点评──道路在哪里
> 这是全章的压轴，也是信任哲学的缩影：龙虾**拒绝相信协定层的 ack，坚持做端到端的内容校验**。它指向「零信任配方管理」这条道路——把每一次换线都视为一次需要密码学证明的交易。这几乎是无人工厂最不可妥协的一环，因为配方错误的代价是整批报废。未来的工程命题是：当 Agent 握有「拦下换线放行」的 gating 权，它就站在了量产节奏与品质安全的天平中央——如何让它的校验快到不拖慢换线、严到不放过一个 byte，并在误拦时能让人类以最低成本覆核放行，将决定这条零信任之路能否真正承载一座 Lights-Out Fab。
