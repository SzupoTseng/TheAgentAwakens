# 第四篇　角色②：半导体 Lights-Out Fab 的钢铁战场

# 第15章　AMHS 与天车：顶棚上的交通指挥

## 情境 1　空中塞车(OHT Traffic Jam)的智能动态分流
**背景**：12 吋厂顶棚轨道网绵延 38 公里，420 台 OHT 天车在离地 4 公尺处日夜奔驰，由 MCS(Material Control System)统一派工，串接 SECS/GEM 与 MES。
**问题**：早班 08:42，黄光区(Litho)出货尖峰叠上周期保养封路，主干道一段 60 公尺轨道塞进 27 台天车，平均移行速度从 4m/s 掉到 0.3m/s，三台 EUV 机台的进片队列见底，CIM 大屏跳出 22 个 FOUP「Delivery Late」红字——再 90 秒就会触发机台 Idle，每分钟吃掉 1.8 万美元产能。
**需要的技能**：MCS 派工算法调校、轨道拓朴图建模、即时队列分析、SECS-II 消息解析。
**开源工具**：Apache Kafka(即时事件流)、NetworkX(轨道图最短路径/中心性)、Grafana(壅塞热力图)、Prometheus。
**用到的 Agent 特性**：龙虾 OpenClaw 通过 Kafka 订阅 MCS 的 `CARRIER_LOCATION` 事件流，每 200ms 用 NetworkX 重算各路段「天车密度 × 加权延迟」中心性；当主干道密度越过阈值，子 Agent 立刻产生绕道权重表，调用本地脚本以 SECS-II `S2F49` 对 MCS 下达分流参数，把后续 31 趟搬运导向南侧备援环道。动作完成后在维运群组同步推播：「主干塞点已分流，预估 70s 后纾解，EUV-03 进片队列已回补」并附热力图快照。
**没有 Agent 的窘境**：值班工程师得先看懂三台监控、手动标出塞点、心算哪条备援道有余裕，再逐笔改派工——往往等他点完鼠标，机台早 Idle 了。
**效益**：壅塞侦测到分流生效 MTTR 从 6 分钟 → 38 秒；尖峰交期达成率 91% → 99.4%。

> 💡 君之一席话
> 「塞车从来不是因为车太多，而是因为没有人有空俯瞰全局——而龙虾永远在顶棚之上看着。」

> 🔍 高端点评──道路在哪里
> 这个案例把 Agent 从「告警工具」推向「即时控制回路的参与者」。下一步的道路，是让龙虾从「建议分流」走到「闭环派工」，但这正是信任边界的试金石：MCS 是厂级权威系统，任何写入都可能扩散成全厂效应。落地的工程难题不在算法，而在「灰度授权」——如何让 Agent 先在影子模式跑足够的决策样本、创建可审计的决策轨迹，才逐步交付写入权限。

## 情境 2　轨道异物与震动引发的晶圆滑动(Wafer Slide)阻击
**背景**：OHT 夹爪(Hoist)在 4 公尺高空升降 FOUP，轨道接缝处的微小异物或螺栓松动会放大成垂直震动，导致晶圆在卡匣槽内水平位移。
**问题**：凌晨 02:17，C 区轨道某段加速度传感器连续三趟回报 Z 轴震动 0.9G(正常 <0.35G)，且该段下游机台的 Pre-Aligner 连报两片「Wafer Slide >300μm」对位失败。若放任不管，下一批 25 片先进制程晶圆恐在搬运中位移撞伤，单批报废逼近 280 万美元。
**需要的技能**：振动频谱分析(FFT)、加速度传感器数据融合、AMHS 轨道区段封锁操作、晶圆对位数据判读。
**开源工具**：InfluxDB(时序震动数据)、SciPy(FFT 频谱)、Telegraf(传感器采集)、Node-RED(封锁流程编排)。
**用到的 Agent 特性**：龙虾持续以 SciPy 对轨道传感器做滑动窗口 FFT，侦测到该段在 28Hz 出现异常谐波尖峰、且与下游 Wafer Slide 事件时间相关系数 0.87，判定「轨道异物高度可疑」。子 Agent 立即运行本地脚本：对 MCS 下 `轨道段封锁`、把该段标为 No-Fly、改派受影响搬运绕行，并自动开出设备工单(EQP Ticket)派给夜班 PM。同步在群组通报并 @值班班长：「C 区 T-114 段 28Hz 异常谐波 + 两片 Slide，已封锁绕行，工单 #FA-7782 已派发,建议优先检查接缝螺栓。」
**没有 Agent 的窘境**：震动只是后台一条起伏曲线，没人盯;Wafer Slide 失败通常被当成偶发 Pre-Aligner 异常重试,等到连报五六片、有人觉得「不对劲」时,报废已经发生。
**效益**：滑动类批量报废年损失下降 73%；轨道异物从「事后追查」变「事前拦截」，平均提前 11 分钟。

> 💡 君之一席话
> 「机台不会说谎，但它说的是频率的语言；听得懂谐波的人，才接得住快掉下来的那片晶圆。」

> 🔍 高端点评──道路在哪里
> 这里龙虾做的是跨域关联——把「轨道震动」和「晶圆对位失败」两个本来分属不同部门的信号缝在一起。未来的道路是创建厂级的「物理事件知识图谱」，让 Agent 自动学习哪些上游物理扰动会诱发哪些下游良率事件。挑战在于因果而非相关：0.87 的相关系数能触发封锁，但要走到「自动归因」，需要可重复的对照实验设计，这在零容忍的量产在线本身就是个伦理与成本的拉锯。

## 情境 3　轨道 Wi-Fi 断线时数百台天车的智能绕路与防撞
**背景**：OHT 与 MCS 多通过轨道沿线 AP 的无线通信回报位置与接收指令，AP 群一旦失联，天车进入「最后已知指令」的盲走状态。
**问题**：19:03，B2 楼层一台内核交换器电源模块故障，连带 14 个轨道 AP 同时脱机,覆盖范围内 63 台天车瞬间失去 MCS 即时管制,还在轨道上滑行。MCS 大屏该区域变成一片「Communication Lost」灰块,任何两台天车在分叉口的相对位置都成了未知——追撞风险逼近红线。
**需要的技能**：网络拓朴与 AP 健康监测、OHT 通信协定(车载协定)理解、防撞安全距离计算、降级运转(Degraded Mode)策略。
**开源工具**：Zabbix(网络设备监控)、SNMP Exporter、Mosquitto(MQTT 备援车载通信)、Redis(天车位置缓存)。
**用到的 Agent 特性**：龙虾从 Zabbix 第一时间捕获 14 个 AP 同时 down 并关联到上游交换器,判定为「局部通信孤岛」而非单点。它不等网络修复——立即从 Redis 拉断线前最后一刻全车位置快照,子 Agent 推算各车惯性滑行落点,通过尚存活的 MQTT 备援频道对孤岛内天车广播「降速至安全速度、分叉口一律停让、维持 3 车身安全距」的保守指令,并请 MCS 冻结对该区的新派工。同步在 NOC 群组与设备群组双频道通报,@网络组去换交换器电源模块。
**没有 Agent 的窘境**：通信一断,值班只能拉紧急停止(E-Stop)把整区天车急煞——这会让 60 多台天车上的 FOUP 承受急停惯性、可能引发更多 Wafer Slide,且全区搬运中断至少半小时,连锁让十几台机台断料。
**效益**：通信孤岛事件从「全区急停半小时」变「保守降级续行 8 分钟」,零追撞、零急停 Slide;搬运中断时间下降 84%。

> 💡 君之一席话
> 「真正的自动化,不是断线时优雅地停下,而是断线时还能优雅地活着。」

> 🔍 高端点评──道路在哪里
> 失联场景揭示了一条关键道路：Agent 必须具备「脱机自治」与「降级协调」能力,而不只是云端大脑。未来厂务会走向边缘化部署——龙虾的子 Agent 下沉到楼层级边缘节点,在中央失联时就地接管。工程上的硬骨头是「脑裂(split-brain)」:当中央与边缘同时想指挥同一群天车,谁说了算?这需要明确的权限交接协定与心跳仲裁,否则自治反而制造混乱。

## 情境 4　分叉道岔(Lifter/Junction)卡死时的在线天车智能路由重组
**背景**：跨楼层搬运仰赖垂直 Lifter 与轨道分叉道岔(Junction)切换轨向,机构件是 AMHS 流量的咽喉节点。
**问题**：14:38,连接 3F 黄光与 4F 蚀刻的关键 Lifter,在门闸开合机构卡在半开位回报 `Mechanical Fault`,该垂直信道彻底断。MCS 对所有指定走此信道的 47 趟搬运仍持续派工,天车在 Lifter 入口排成长龙越积越多,跨楼层交期全面崩盘,4F 三台蚀刻机进度条开始倒数见底。
**需要的技能**：AMHS 路由表重组、多楼层搬运替代路径规划、机构故障码判读、交期影响评估。
**开源工具**：NetworkX(替代路径搜索)、Neo4j(轨道拓朴图数据库)、Celery(批量重派任务队列)、Grafana。
**用到的 Agent 特性**：龙虾收到 Lifter 的 `Mechanical Fault` SECS 告警,立刻在 Neo4j 轨道拓朴图上把该节点权重设为无限大,用 NetworkX 对 47 趟在途与待派搬运重算替代路径——其中 31 趟可改走东侧备援 Lifter,16 趟因急件改走跨楼连信道。子 Agent 通过 Celery 把重派任务批量推回 MCS,并依晶圆站点工序(Recipe Step)的等待时间敏感度排序,让最接近超时的批量优先。群组通报附上「卡死节点 / 受影响批量清单 / 新路径 ETA / 预估恢复」一览表,并 @机构 PM。
**没有 Agent 的窘境**：工程师得手翻路由表、一趟一趟判断哪些能改走哪条道、哪台 Lifter 还有余裕,改派 47 趟人工至少 40 分钟,而且漏改一趟就多一台天车卡在死路口。
**效益**：路由重组 MTTR 40 分钟 → 65 秒;Lifter 单点故障的跨楼搬运冲击面积缩小 78%。

> 💡 君之一席话
> 「一个咽喉节点卡住,考验的不是它多快被修好,而是这张网有多快学会绕过它。」

> 🔍 高端点评──道路在哪里
> 这指向「拓朴即代码(Topology-as-Code)」的道路:把整座厂的轨道网变成可被 Agent 即时查找与重写的活图谱。未来龙虾不只在故障时绕路,更能在故障前用图论预测「哪些节点是脆弱的单点(SPOF)」并建议轨道扩建。落地阻力在于图谱与物理现实的一致性——一旦 Neo4j 里的拓朴和现场改线后不同步,Agent 的「聪明绕路」就会把天车送进一条根本不存在的轨道。

## 情境 5　高空轨道微幅位移(Track Disalignment)的假性滑动拦截
**背景**：厂房结构受温度、楼层载重变化会让顶棚轨道产生毫米级缓慢位移,使天车在特定点位的对位读值漂移,被 Pre-Aligner 误判为晶圆滑动。
**问题**：连续三天,4F 西侧某固定点位的搬运,只要经过 T-208 轨道段,下游机台就零星回报 Wafer Slide,工程师反复检查晶圆、夹爪、卡匣都正常,白白拦停了 40 多片良品晶圆重对位,却找不到根因——「鬼故事」传遍整个 FA 群组。
**需要的技能**：空间定位数据分析、轨道形变趋势建模、真假滑动判别(信号特征分类)、机台对位座标系校正。
**开源工具**：pandas(点位数据聚合)、scikit-learn(滑动真假分类)、Matplotlib(漂移趋势图)、OpenTSDB。
**用到的 Agent 特性**：龙虾把近 30 天所有 Wafer Slide 事件按「轨道段 × 点位 × 时段」聚合,用 scikit-learn 训练的分类器一眼识破:T-208 段的滑动读值「方向高度一致、量值稳定、且随楼层日温曲线同步漂移」——这是轨道位移的指纹,不是真滑动(真滑动方向随机)。子 Agent 自动对该点位下达搬运座标补偿偏移量,让对位回到容差内,并把「疑似轨道结构位移」连同 30 天漂移趋势图开成厂务结构工单。群组通报:「T-208 的 Slide 是假性,根因轨道日热位移约 1.4mm,已套用座标补偿,真滑动误拦将归零,结构工单 #ME-3310 已派。」
**没有 Agent 的窘境**：人类靠经验很难分辨真假滑动,只能保守地每片都拦停重对位,既浪费产能又每天提心吊胆;根因藏在毫米级的缓慢漂移里,没有长期数据聚合几乎不可能被人眼发现。
**效益**：假性滑动误拦从每天 13 片 → 0 片;根因定位从「查三天无解」变「30 分钟锁定轨道形变」。

> 💡 君之一席话
> 「最贵的故障,是那种看起来像故障、其实不是故障的故障——它偷的不是晶圆,是工程师的判断力。」

> 🔍 高端点评──道路在哪里
> 真假滑动的分辨,本质是 Agent 在替人类「重建直觉」。这条道路通往「特征级的根因库」:龙虾累积越多被标注的真/假事件,就越能把老师傅的隐性经验转成可复用的分类模型。难点在标注成本与漂移——半导体制程一换,信号特征就变,模型会悄悄退化。未来的关键能力,是让 Agent 自己监测「我的判断还准不准」,在准确度滑落时主动请求重新标注,而非默默把良品晶圆放行。

## 情境 6　OHT 夹爪(Hoist Gripper)抓放偏移的毫米级即时校正
**背景**：天车在机台 Load Port 上方靠 Hoist 垂直升降夹取/释放 FOUP,夹爪定位若偏移 2mm 以上,轻则放料对不准触发 `Place Fail`,重则 FOUP 卡在 Load Port 边缘倾斜。
**问题**：10:55,某台天车在连续 6 次搬运中,于不同机台累计 4 次 `Place Retry`,第 5 次直接 `Place Fail` 把 FOUP 悬在 Load Port 半个身位,倾斜角触发倾倒警报——FOUP 内 25 片晶圆正悬在 4 公尺高空,随时可能连匣坠落。
**需要的技能**：Hoist 定位伺服数据分析、放料失败串行判读、单车隔离(Vehicle Quarantine)操作、夹爪偏移补偿。
**开源工具**：Telegraf(伺服数据采集)、InfluxDB、Grafana 告警、Ansible(自动化隔离剧本)。
**用到的 Agent 特性**：龙虾监测单台天车的 Place 成败串行,发现这台车的失败率在一小时内从 0.1% 飙到 6.7%、且 Hoist 定位偏移持续往同一方向累积——典型的夹爪机构渐进性偏移,不是随机。在第 5 次 Fail 触发倾倒警报的同一秒,子 Agent 用 Ansible 剧本对 MCS 下达「该车立即 Quarantine、就近开回维修侧线、禁止再接搬运」,并把该车正载运的 FOUP 标记交由人工确认。群组紧急推播 + 电话级通报班长:「天车 V-227 夹爪偏移渐进累积,已隔离回维修道,当前悬停 FOUP 请现场人工接手,建议更换夹爪校正模块。」
**没有 Agent 的窘境**：放料偶发失败常被当成正常重试,没人会盯单台车的失败趋势;等到 FOUP 真的卡住倾斜,现场人员得爬高空作业车去抢救 25 片悬空晶圆,过程一个手抖就是整匣坠毁。
**效益**：夹爪渐进故障从「卡匣倾倒才发现」提前到「失败率刚擡头就隔离」,平均提前 41 分钟;高空抢救事件年发生数归零。

> 💡 君之一席话
> 「机构件不会突然坏,它会慢慢偏;能在 0.1% 变成 6.7% 的那条斜率上拦住它,才叫预测性维护。」

> 🔍 高端点评──道路在哪里
> 这条道路是「单体健康追踪」——从监控整个车队,细化到为每一台天车创建个体健康文件。未来龙虾会给 420 台天车各自一份「履历」,夹爪寿命、定位漂移、保养记录全在里面,主动排出最佳保养时序。工程挑战在规模化的信号噪声:单台车的趋势容易被制程波动淹没,要在数百台同时跑的杂讯里稳定抓出个体斜率,需要既灵敏又不误报的阈值自适应——太钝漏抓坠匣,太敏每天误隔离拖垮产能。

## 情境 7　FOUP 滞留(Carrier Stranded)与壅塞回填的死锁解除
**背景**：当机台 Load Port 全满、Stocker(储位)也满时,天车载着 FOUP 找不到地方放,只能在轨道上「抱着货绕圈」,形成搬运死锁(Deadlock)。
**问题**：21:30,蚀刻区一台机台异常停机,它前段所有 WIP 无处可去,连锁让邻近 Stocker 在 20 分钟内塞满,11 台天车载着 FOUP 在轨道上空转绕圈、无处卸货,占住主干道又回头加剧塞车——典型「满了所以更满」的回填死锁,CIM 大屏 Stranded Carrier 计数一路冲到 11。
**需要的技能**：Stocker 储位水位管理、WIP 平衡调度、死锁侦测(资源等待环)、跨区疏散储位协调。
**开源工具**：NetworkX(等待环/死锁侦测)、Kafka、PostgreSQL(储位状态)、Grafana。
**用到的 Agent 特性**：龙虾用 NetworkX 对「天车—Stocker—Load Port」的资源等待关系建有向图,即时侦测出环状依赖=死锁。判明根因是那台停机机台造成的局部回填后,子 Agent 立刻运行两手:一是查出三个跨区较空的备援 Stocker、把 11 台空转天车的 FOUP 疏散过去解开死锁环;二是对 MES 建议暂缓该停机机台前段的投料,从源头止血。群组通报:「蚀刻 ETCH-06 停机引发回填死锁(11 Stranded),已将滞留 FOUP 疏散至 X3/X7/Y2 Stocker,并建议暂缓前段投料,死锁环已解开,主干空转天车归零。」
**没有 Agent 的窘境**：死锁是「全局现象、局部无感」,单看任一台天车都只是「在绕路」,值班很难意识到整体已锁死;等发现时十几台车已空转半小时,人工逐台找疏散储位、协调跨区授权,往往越救越乱。
**效益**：死锁侦测到解环 MTTR 35 分钟 → 90 秒;单机台停机引发的连锁空转天车数从 11 降到拦在 2 以内。

> 💡 君之一席话
> 「死锁最可怕的地方,是每一台车都觉得自己只是在等——没有人知道大家在等一个永远不会来的位子。」

> 🔍 高端点评──道路在哪里
> 死锁解除把 Agent 推向「全局资源仲裁者」的角色,这是 AMHS 自动化最深的一层。前瞻的道路是从「事后解环」走向「事前避锁」——龙虾在派工的当下就用图论预判这趟搬运会不会把系统推向死锁边缘。难点是预测与产能的取舍:过度保守的避锁会压低搬运吞吐,让厂白白损失产能。真正的工程艺术,是让 Agent 学会在「安全」与「满载」之间走钢索,而这条钢索的宽度,由厂长的风险胃纳决定。

## 情境 8　光罩(Reticle)RMHS 搬运的洁净度与时效双重拦截
**背景**：EUV 光罩价值单片逾 30 万美元,经由独立的 RMHS(Reticle MHS)在 Litho 区与 Reticle Stocker 间搬运,对洁净度(Pod 密封)与曝光时效(Reticle 出 Stocker 后须在限定时间内上机)要求极苛。
**问题**：03:50,一片 EUV 光罩的搬运因 OHT 在分叉口短暂排队,Reticle 出 Stocker 已 13 分钟仍未到曝光机台,逼近「出库后须上机」的时效红线(超时须退回重新洁净验证,延误整条 Lot);同时其搬运 Pod 的密封传感器回报一次瞬间压差跳动,疑似微泄漏。一片光罩、一条关键 Lot,双重风险叠加。
**需要的技能**：RMHS 时效链追踪、Reticle Pod 密封监测、Litho 调度耦合分析、优先权抢占式派工。
**开源工具**：Apache Kafka、InfluxDB(密封压差时序)、OR-Tools(优先权抢占调度)、Grafana。
**用到的 Agent 特性**：龙虾对每片在途 Reticle 挂一个「时效倒数计时器」,侦测到这片已逼近红线,立即用 OR-Tools 做抢占式重排——把这片光罩的搬运优先权拉到最高,让 MCS 对沿途分叉口为它清道让行,并预约曝光机 Load Port。同时它把 Pod 那次压差跳动标为「需上机后立即复检密封」。子 Agent 把这两件事打包成一条决策推给 Litho 调度系统。群组通报 @光罩工程师:「Reticle R-EUV-118 出库已 13 分,抢占派工已清道,ETA 2 分内上机可保时效;另该 Pod 有一次压差跳动,已标记上机后优先复检密封。」
**没有 Agent 的窘境**：时效计时藏在系统角落,RMHS 又是独立子系统,值班通常等到「超时退回」告警才知道,此时光罩已得退回洁净验证、整条 Lot 延误数小时;密封那一次瞬跳更是淹没在海量传感数据里无人察觉。
**效益**：Reticle 出库时效超时事件下降 88%;光罩搬运的时效+洁净双风险从「各自盲区」变「单一决策同步拦截」。

> 💡 君之一席话
> 「越贵的东西,越不能用『先到先服务』去搬它——光罩不排队,光罩有它自己的时钟。」

> 🔍 高端点评──道路在哪里
> 光罩搬运把「时效」与「洁净」两个维度绑进同一个决策,指向 Agent 的多目标即时优化道路。未来龙虾要同时权衡良率、时效、洁净、产能多个彼此冲突的目标,这已不是规则引擎能涵盖的。落地的信任边界在于可解释性:当 Agent 为了抢救一片光罩而插队、打乱了其他 Lot 的调度,工程师必须看得懂「为什么是这片优先」。没有透明的决策说明,再聪明的抢占调度也会被现场不信任而关掉。

## 情境 9　跨 Bay 搬运的尖峰负载预测与天车预部署(Pre-positioning)
**背景**：不同 Bay(制程区)间的长距搬运是 AMHS 最耗时的环节,若等到需求发生才调度空车过去,光是空车跑位就吃掉数分钟交期。
**问题**：每天 16:00 换班前后,黄光区会集中发布大批待搬 WIP,但空闲天车多半散在离黄光区最远的封装测试侧,需求一爆发,黄光区瞬间「叫不到车」,FOUP 在 Load Port 堆积、平均叫车等待从 30 秒暴增到 4 分钟,连带拖累整个下午班的搬运交期。
**需要的技能**：搬运需求时序预测、天车空闲分布分析、预部署(Pre-positioning)策略、产能尖峰建模。
**开源工具**：Prophet(时序需求预测)、pandas、scikit-learn、Grafana。
**用到的 Agent 特性**：龙虾用 Prophet 学习过去 90 天的「Bay 级搬运需求曲线」,精准预测到每日 15:50 黄光区需求即将陡升。在尖峰来临前 10 分钟,子 Agent 主动对 MCS 建议「把 N 台当下空闲、且靠近黄光区待命环道的天车预先部署过去」,让车在需求爆发时就在门口待命,而不是临时从厂尾赶来。它会避开仍有任务的车、只调真正空闲的车,把空车跑位转成「提前布局」。群组通报:「预测 15:50 黄光搬运需求 +180%,已预部署 8 台空车至黄光待命环,预估叫车等待可压回 35s 内。」
**没有 Agent 的窘境**：调度策略多半是被动反应式——需求来了才派最近的空车,可是尖峰时最近的空车早被抢光,只能从远处调,越调越慢;人类值班更不可能每天精准预判哪个 Bay、哪个时段会爆量并提前布车。
**效益**：尖峰时段叫车等待 4 分钟 → 35 秒;跨 Bay 搬运交期达成率提升至 98.6%,且不增加任何天车数量。

> 💡 君之一席话
> 「最好的调度不是反应快,而是早就把车停在了需求即将发生的地方——预测,就是把未来提前搬到现在。」

> 🔍 高端点评──道路在哪里
> 预部署让 Agent 从「灭火」转向「布局」,这是运维成熟度的分水岭。未来的道路是「预测式 AMHS」——整个搬运系统依需求预测自我调形,而非被动派工。最大的工程风险是预测误差的代价不对称:预部署猜错,白白空跑浪费能耗与轨道资源;猜对,省下整段交期。龙虾要学会量化「预测信心」并据此决定布局力度,信心高才大胆预部署,信心低则保守——把预测的不确定性诚实地写进决策,而不是假装自己永远猜得准。

## 情境 10　Lights-Out 夜班无人值守时的 AMHS 异常自主收敛
**背景**：迈向无人化智能工厂(Lights-Out Fab)的终极目标,是夜班无人值守时 AMHS 能自主处理多数异常,只在真正需要时才唤醒待命工程师。
**问题**：某周六凌晨 04:00,全厂仅一名待命工程师在宿舍,AMHS 在两小时内接连发生:一段轨道轻微壅塞、两台天车电量偏低需返充、一个 Stocker 水位逼近上限、一次 AP 短暂抖动。任一件都不致命,但若无人收敛,叠加起来就会在天亮前演变成全面塞车——而工程师正在睡觉。
**需要的技能**：异常分级与自主收敛策略、人机协作唤醒阈值设计、多异常并发协调、夜间安全降载运转。
**开源工具**：Kafka、Prometheus + Alertmanager(分级告警)、n8n(自主处置流程编排)、Grafana On-Call。
**用到的 Agent 特性**：龙虾在夜班化身「值班总指挥」:对四件异常分别自主收敛——壅塞做动态分流、低电天车调度返充、Stocker 水位高就跨区疏散、AP 抖动则保守降速观察;每件都自己处理、自己验证收敛结果,全程把处置轨迹写成可审计日志。它严守「唤醒阈值」:这四件全在可自主收敛范围,于是不打扰工程师,只在晨报摘要里留痕。直到第五件——一台天车回报夹爪倾倒风险(属不可自主处置的物理安全事件),龙虾才通过 On-Call 真的把工程师电话叫醒,并附上前四件已自主收敛的完整脉络,让人一接手就掌握全局。
**没有 Agent 的窘境**：传统夜班要嘛排人熬夜空等(多数时间无事却不能睡),要嘛靠告警轰炸——任何小异常都把工程师吵醒,半夜被叫起四五次处理琐事,真正致命的那件反而淹没在告警疲劳里被忽略。
**效益**：夜间人工介入次数从每班 11 次 → 1 次;非必要唤醒下降 91%,而真正的物理安全事件 100% 准时唤醒——这正是 Lights-Out Fab 的可运转性证明。

> 💡 君之一席话
> 「无人工厂的精髓,不是没有人,而是让人只在『非他不可』的那一刻才出现——其余的黑夜,交给龙虾守着。」

> 🔍 高端点评──道路在哪里
> 这是整章的终点,也是龙虾在 Fab 的最高形态:不是取代工程师,而是定义「什么时候该叫醒工程师」。这条道路的内核工程命题是「唤醒阈值的校准」——阈值太松,Agent 越权处理了该人类拍板的事;太紧,又回到告警疲劳。真正的信任边界在于:Agent 必须诚实地知道自己「能力与授权的边界在哪」,把不确定、不可逆、涉及物理安全的决策准确地交还给人。当龙虾学会这种「知道何时该闭嘴、何时该大喊」的分寸,Lights-Out Fab 才从口号变成可以签字负责的现实。
