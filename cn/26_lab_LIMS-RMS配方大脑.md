# 第26章　配方大脑：黄金配方的端到端守护

## 情境 11　先进制程动态配方(Recipe Check)版本不合规的秒级下线与防呆
**背景**：A10 埃米制程的原型蚀刻机台，每一炉都向 RMS 拉取「动态配方」，配方版本以 `recipe-A10-etch@v8.3.2-rc4` 的语意化标签管控，下发到机台的窗口只有 8 ms。
**问题**：凌晨 02:47，一支未通过 QA 签核的 `rc4` 候选配方被工程师误推进 production channel，机台在 6 ms 内把它加载寄存器——若这一炉跑下去，价值 320 万美元的 12 吋晶圆会在 4 秒后进腔，且整批 48 片直接报废。当班只有 1 名夜班工程师，他甚至还没打开 RMS 主控台。
**需要的技能**：语意化版本(SemVer)合规判读、配方签章验章(Cosign)、即时事件流拦截、机台 OPC-UA 指令回送。
**开源工具**：Sigstore Cosign、Open Policy Agent (OPA)、Apache Kafka、open62541 (OPC-UA SDK)。
**用到的 Agent 特性**：龙虾 OpenClaw 以**子 Agent** 常驻在 RMS 的 Kafka `recipe.dispatch` topic 上，毫秒级消费每一笔下发事件；ClawHub 加载的「SemVer Gate」技能插件比对标签是否带 `-rc`/`-beta` 预发行后缀并查 Cosign 签章链，OPA policy 一裁定「不合规」，龙虾立刻**本地脚本运行**对 open62541 送出 `HOLD` 指令冻结机台寄存器，再通过 **Multi-Channel Gateway** 同步把带机台 ID、配方 hash、拦截时间戳的告警推到夜班工程师的 Slack、机台旁的 Teams 看板与值班手机 SMS。
**没有 Agent 的窘境**：夜班工程师要先被告警吵醒，登录跳板机、开 RMS 主控台、肉眼比对版本号、再手动下 HOLD——平均 9 分钟，而晶圆 4 秒后就进腔，根本来不及，只能等报废后写事故报告。
**效益**：误推到拦截的 MTTD 从「事后才知道」变成 6 ms 侦测 + 11 ms 冻结；单次避免 320 万美元报废，防呆覆盖率从人工抽查的 ~60% 提升到 100%。

> 💡 君之一席话
> 「配方的版本号不是给人看的注解，是给机器守的法律；当下发只有 8 毫秒，唯一来得及读懂法律的，是不眨眼的那一个。」

> 🔍 高端点评──道路在哪里
> 这个案例把龙虾推向「制程指令的最后一道闸门」这条道路——它不再只是通报者，而是有权冻结机台的运行者。落地时最尖锐的工程问题是**授信边界**：谁来签发龙虾的 HOLD 权限？当 Agent 能踩煞车，它的决策延迟与误判率就直接折算成停机成本。未来的方向是把 OPA policy 与机台安全联锁(Interlock)做双签，让 Agent 的「拦」永远需要一条可审计、可回放的授权链背书。

## 情境 12　黄金配方(Golden Recipes)端到端零信任的动态销毁与重建
**背景**：A5 制程的「黄金配方」是厂里最高机密资产，明文绝不落地，只在内存中以解密态存活；台/美/欧三厂区以零信任(Zero Trust)架构共享同一份密钥封装的配方包。
**问题**：欧洲厂一台配方缓存节点的 TPM 证明(Remote Attestation)在 03:12 突然失败，意味着该节点可能被植入或被冷启动攻击。零信任原则要求：**任何信任根崩塌，黄金配方必须在毫秒内从所有挂载该节点的下游全数销毁并重建**，否则一份解密态黄金配方就暴露在不可信主机上。
**需要的技能**：远程证明(Remote Attestation)判读、信封加密与密钥轮替、分布式缓存失效广播、内存安全销毁。
**开源工具**：Keylime (TPM remote attestation)、HashiCorp Vault、Redis、age (现代加密工具)。
**用到的 Agent 特性**：龙虾的 Keylime watcher **子 Agent** 一侦测到 attestation quote 失败，立即判定信任根破裂；**本地脚本运行** 对该节点 Redis 发 `FLUSHDB` 并覆写内存页，同时调用 Vault 撤销该节点的解封密钥、轮替新密钥版本；接着它向台/美两厂的健康节点下「以新密钥重新封装并下发」的重建指令；全程通过 **Multi-Channel Gateway** 在跨国 SRE 群组同步一条带证明失败原因、销毁节点清单、重建 ETA 的事件链。
**没有 Agent 的窘境**：三地工程师要先对齐时区、在电话会议里确认谁负责销毁哪个节点、手动跑 Vault 撤销、再协调重建顺序——平均 35 分钟的人工协调窗口，等于黄金配方在不可信主机上裸奔了半小时。
**效益**：信任根崩塌到全域销毁重建的 MTTR 从 35 分钟压到 1.8 秒；黄金配方明文暴露窗口从「分钟级」降到「毫秒级」，零信任承诺首次真正做到可量测。

> 💡 君之一席话
> 「真正的机密不是藏得有多深，而是当地基一裂，它能不能比攻击者的手更快地灰飞烟灭。」

> 🔍 高端点评──道路在哪里
> 这条道路通向「自我毁灭式安全」(self-destructing security)的自动化——龙虾成为跨厂区信任状态的协调中枢。工程难点在于**规模下的协调一致性**：当三地各有上百个缓存节点，销毁与重建必须避免脑裂(split-brain)与重建风暴。下一步是让 Agent 以共识协定（如 Raft）确认「全域已销毁」再开放重建，并把每一次毁灭—重建做成可演练的混沌工程剧本，让零信任从口号变成肌肉记忆。

## 情境 13　RMS 配方漂移(Recipe Drift)的自动稽查与基线回滚
**背景**：RMS 中声明的「期望配方状态」与各机台实际运行的配方参数，本应一致；但工程师的临时微调、机台固件的隐性覆写，会让实际值悄悄偏离基线，即所谓配方漂移。
**问题**：A10 沉积机台的腔体温度补偿参数，在连续 11 天里被三名不同工程师各「临时微调」了一次，累积偏离基线 +2.3%。没人记得改过，RMS 帐面仍显示合规，但良率曲线开始以每天 0.4% 的速度阴跌——这种慢性漂移用人眼几乎不可能在事故前抓到。
**需要的技能**：声明式配置漂移侦测、时序数据统计分析、配置即代码(GitOps)基线管理、变更归因(blame)追溯。
**开源工具**：osquery、Prometheus、Argo CD (drift detection)、git。
**用到的 Agent 特性**：龙虾每 5 分钟以 osquery 快照各机台实际配方参数，**子 Agent** 与 git 中的声明式基线做 diff；一旦偏离超过 ±1% 阈值，ClawHub 的「Drift Auditor」技能插件自动关联 RMS 变更日志，**本地脚本运行** 跑 git blame 把三次微调的人、时间、原值还原成一张归因表，并计算回滚到基线的预期良率影响；经值班核可后，通过 **Multi-Channel Gateway** 把带漂移趋势图、归因表、一键回滚按钮的稽查报告推到制程群组。
**没有 Agent 的窘境**：工程师通常要等良率连跌一周、开 8 人的根因分析(RCA)会议、翻三天的操作日志，才可能拼凑出「漂移」这个结论——平均 5 个工作天，期间每天还在烧晶圆。
**效益**：配方漂移从「事故后一周才查出」变成「累积偏离达阈值即时告警」；慢性良率损失从不可见变为每 5 分钟可稽查，单一机台一季可挽回约 1.2% 良率。

> 💡 君之一席话
> 「最危险的故障从不爆炸，它只是每天偷走 0.4%，直到某天你发现帐早就对不上了。」

> 🔍 高端点评──道路在哪里
> 漂移稽查把龙虾推向「制程的真相维护者」这条道路：它让 RMS 的声明态与物理现实持续对账。落地的工程张力在于**阈值的政治学**——阈值太松漏掉慢性漂移，太紧则被工程师的合法微调淹没成告警疲劳。前瞻的解法是让 Agent 学会区分「授权变更」与「未授权漂移」，把 GitOps 的 pull request 流程嵌进机台旋钮，未来每一次旋钮转动都自带可追溯的意图，漂移将从侦测问题退化为不存在的问题。

## 情境 14　配方下发遭中间人攻击(MitM)的零容忍校验
**背景**：RMS 与机台间的配方下发走厂内工业以太网，理论上隔离，但跨厂区的分子动力学配方同步要经过一段公网 VPN 隧道，这正是中间人攻击(MitM)的高风险面。
**问题**：03:50，一份从美厂同步到台厂的 A2 制程前驱体配方，在传输中被注入篡改：某气体流量字段的 hash 与 RMS 签发端记录对不上，相差 1 个 bit。这 1 个 bit 若进机台，会让前驱体配比偏移，整炉 A2 样品作废，更糟的是它看起来「几乎正确」，足以骗过抽样检查。
**需要的技能**：传输层完整性校验、凭证钉选(Certificate Pinning)、端到端签章验证、异常封包取证。
**开源工具**：Sigstore Cosign、OpenSSL、Suricata (IDS)、Zeek。
**用到的 Agent 特性**：龙虾的网络 **子 Agent** 旁路挂在 VPN 隧道出口，Suricata/Zeek 一触发配方流量的完整性告警，它立即用 Cosign 对下发包做端到端验章，发现实际 hash 与签发端的签章 payload 差 1 bit；**本地脚本运行** 阻断该下发 session、保留原始封包做取证、向 RMS 索取干净副本重发，并比对凭证指纹确认是否凭证被替换；同时 **Multi-Channel Gateway** 把带 diff 比特位置、来源 IP、凭证链的安全告警同步到资安(SOC)与制程群组。
**没有 Agent 的窘境**：MitM 注入的单比特篡改几乎不可能靠人工抽查发现；通常要等整炉 A2 样品的电镜分析出现异常、回溯三天才怀疑到传输环节——而那时攻击者早已收手，取证证据也已轮转刷新。
**效益**：篡改侦测从「事后电镜才发现」变成下发当下毫秒级验章拦截；单比特完整性破坏的拦截率达 100%，并首次留下可呈堂的封包取证链。
> 💡 君之一席话
> 「在埃米尺度，一个比特的谎言就足以毁掉一整炉真理；零容忍不是洁癖，是物理的底线。」

> 🔍 高端点评──道路在哪里
> 此案让龙虾走向「制程数据的端到端公证人」这条道路——它在每一段传输的缝隙处验章。真正的工程挑战是**验章的延迟预算**：跨国同步本就吃紧，逐包验章不能成为新瓶颈。未来方向是把验章下沉到硬件(如智能网卡 SmartNIC)，让 Agent 从「逐包检查」升级为「策略编排与异常裁决」，把毫秒级的密码学苦工交给硅，把判断与通报留给智能。

## 情境 15　配方缓存遭污染的硬核内存粉碎(RAM Zeroing)
**背景**：机台旁的边缘节点把热配方解密后缓存在 RAM 中以求微秒级访问；这份解密态缓存是攻击面最敏感的一块——任何污染或残留都是灾难。
**问题**：04:20，边缘节点的内存完整性监测侦测到配方缓存区出现非预期写入：一段 256 byte 的配方参数被外部行程改写，疑似恶意污染或内存越界踩踏。若机台下一个微秒从这块被污染的缓存读参数，A5 制程会以错误配比运行；更隐蔽的是，旧配方残留在已释放但未清零的内存页里，可被 cold boot 攻击捞出。
**需要的技能**：内存完整性监测、安全内存清零(secure zeroing / explicit_bzero)、行程沙箱与权限收敛、运行时自我保护(RASP)。
**开源工具**：eBPF / bpftrace、libsodium (`sodium_memzero`)、Falco、AppArmor。
**用到的 Agent 特性**：龙虾以 eBPF/Falco 挂勾监看配方缓存区的内存写入，**子 Agent** 一捕捉到未授权行程的写入即判定污染；**本地脚本运行** 立刻冻结机台读取、用 libsodium 的安全清零把整块缓存与已释放页面粉碎(RAM zeroing)、撤销肇事行程的能力(capabilities)、再从可信源重新解密回填干净缓存；全程以 **Multi-Channel Gateway** 同步污染地址、肇事 PID、清零范围到资安与运维群组，并附上一份「本节点本轮已无解密态残留」的证明。
**没有 Agent 的窘境**：内存污染与残留靠人工几乎无法即时发现，通常是机台跑出异常配比、做完事故鉴识才回溯到缓存；而那时污染与残留早已被覆写或泄漏，清零时机完全错过。
**效益**：缓存污染从「事后鉴识才知」变成微秒级侦测 + 毫秒级粉碎回填；解密态配方在内存中的非预期残留窗口从不可控降到接近零，cold boot 捞取面被实质清空。

> 💡 君之一席话
> 「机密的生与死都在那几微秒的内存里——你不主动把它烧干净，攻击者就会替你把它读出来。」

> 🔍 高端点评──道路在哪里
> 内存粉碎把龙虾带向「运行时的免疫系统」这条道路：它不防外墙，而守最内层的细胞质。工程上的硬骨头是**清零与可用性的拉锯**——每一次粉碎都打断微秒级的热路径，过度敏感会让机台抖动。下一步是让 Agent 结合机密运算(Confidential Computing / SEV-SNP、TDX)的硬件飞地，把解密态配方从一开始就关进加密内存，让「污染侦测—粉碎」从常态运维退化为飞地被攻破时才启动的最后手段，把免疫反应的代价降到只在真正生病时才付。

## 情境 16　配方依赖图(Recipe DAG)循环引用导致下发死锁的自动拆环
**背景**：A2 复合制程的配方不是单一文件，而是上百个子配方(sub-recipe)组成的有向图(DAG)，下发时依拓扑序逐层展开；任何一条循环引用都会让展开器卡死。
**问题**：05:05，一名工程师把 `pre-clean` 子配方改成引用 `post-bake`，而 `post-bake` 早已引用 `pre-clean`，凭空造出一条循环。RMS 的配方展开器在拓扑排序时陷入无限等待，下发队列在 40 秒内堆积 217 笔待发任务，整条 A2 线的机台全部空转等配方——每分钟空转成本约 1.1 万美元。
**需要的技能**：有向图循环侦测、拓扑排序与依赖解析、配方建构系统理解、最小修复集(minimal fix set)推导。
**开源工具**：NetworkX、Graphviz、Dagger (CI/CD DAG engine)、jq。
**用到的 Agent 特性**：龙虾的 **子 Agent** 监看下发队列深度，一侦测到队列暴涨且展开器无进展，ClawHub 的「DAG Doctor」技能插件把配方依赖导入 NetworkX 跑强连通分量分析，**本地脚本运行** 精准定位 `pre-clean → post-bake → pre-clean` 这条环、用 Graphviz 画出环路图、并推导出「还原最近一次 pre-clean 变更」这个最小拆环修复集；经核可后回滚并重启展开器，最后以 **Multi-Channel Gateway** 把环路图、肇事 commit、217 笔积压的清空进度同步到制程群组。
**没有 Agent 的窘境**：工程师面对卡死的展开器只看到「队列堆积」这个表象，要手动 dump 上百个子配方、肉眼追引用链找环——在百节点 DAG 里靠人脑找环平均要 50 分钟，期间整线持续空转烧钱。
**效益**：死锁侦测到拆环的 MTTR 从 50 分钟降到 38 秒；A2 线空转时间从近一小时压到分钟级，单次事件省下逾 50 万美元空转损失。

> 💡 君之一席话
> 「配方的复杂不在于它有多少行，而在于它指向谁——一个指错方向的引用，就能让整座工厂原地打转。」

> 🔍 高端点评──道路在哪里
> 拆环案让龙虾走上「配方拓扑的维护工程师」这条道路：它把抽象的图论病理变成可操作的运维动作。落地的关键是**自动修复的胆量边界**——拆环有时不只一种解，回滚哪一条变更涉及制程语意，Agent 不能盲拆。前瞻方向是在配方提交时就做 DAG 环检的 pre-commit 守门，把死锁消灭在进入队列之前，让 Agent 的角色从「事后拆环的急诊医师」前移为「设计期的依赖顾问」，这才是规模化下唯一可持续的路。

## 情境 17　跨国 HPC 配方同步分裂脑(Split-Brain)的权威仲裁
**背景**：分子动力学仿真的最佳配方，由台/美/欧三地 HPC 集群协同演算后写回同一份 RMS 主配方；正常时三地以最终一致性同步，但网络分区会制造分裂脑。
**问题**：05:40，跨大西洋骨干链路抖动 90 秒，欧厂与台/美短暂失联。失联期间欧厂 HPC 基于本地仿真把主配方 `md-A2-precursor` 升到 `v12`，台/美则升到另一个内容不同的 `v12`——同一版本号、两份矛盾内容。链路恢复后，三地同步引擎面对两个 `v12` 直接卡住，没有任何一方敢宣称自己权威，配方写回全线冻结。
**需要的技能**：分布式一致性与 CRDT 冲突解析、矢量时钟(vector clock)因果排序、权威源仲裁策略、仿真结果可信度评分。
**开源工具**：etcd (Raft)、Automerge (CRDT)、Apache ZooKeeper、NTP/chrony。
**用到的 Agent 特性**：龙虾的仲裁 **子 Agent** 侦测到同版本号双内容冲突，调出两份 `v12` 的矢量时钟与仿真可信度评分(收敛残差、样本数)，**本地脚本运行** 依预定义仲裁策略（谁的仿真残差更低 + 因果更晚者胜）裁出权威版本、把落败版本自动重编号为 `v12.1-divergent` 留存稽核，再以 etcd Raft 广播权威结果解除冻结；**Multi-Channel Gateway** 同步把分裂原因、两版差异、仲裁依据与被降级版本去向，推送到三地 HPC 群组，时区无感。
**没有 Agent 的窘境**：三地工程师得跨时区开紧急会议，各自坚持自家 HPC 算得对，靠人工比对仿真参数与时间戳争论谁权威——平均 40 分钟的扯皮，期间主配方完全冻结，下游仿真调度全部卡住。
**效益**：分裂脑仲裁的 MTTR 从 40 分钟的跨国会议降到 12 秒的自动裁决；配方权威源的判定从「靠嗓门」变成「靠残差与因果」，跨国同步可用性从分区即瘫痪提升到秒级自愈。

> 💡 君之一席话
> 「当两个地方同时宣称自己是真理，沉默的仲裁者不问谁的声音大，只问谁的证据更晚、误差更小。」

> 🔍 高端点评──道路在哪里
> 仲裁案把龙虾推向「跨国数据一致性的中立法官」这条道路：它在 CAP 的裂缝里替人类做了最难的取舍。最深的工程问题是**仲裁策略的可解释与可问责**——当 Agent 裁定欧厂的 v12 落败，落败方必须能看懂并挑战这个判决。未来方向是把仲裁规则做成版本化、可审计、可投票修订的「配方宪法」，让 Agent 执法而非立法；同时引入因果一致性的保存底座(如 CRDT 原生 RMS)，从根上减少分裂脑的发生面，把仲裁从常态降为例外。

## 情境 18　配方参数越界引爆制程窗口(Process Window)的物理防呆
**背景**：每个配方参数都有一个由物理与良率界定的「制程窗口」(process window)，超出窗口即便密码学上完全合规，物理上也会炸炉；RMS 校验版本与签章，却不懂物理。
**问题**：06:15，一份签章完全合法、版本完全正确的 A10 退火配方，因为单位换算笔误，把腔体升温速率写成 850 °C/s，而该机台的安全制程窗口上限是 120 °C/s。这份配方通过了所有资安关卡，却会在加载后 3 秒内让石英腔热冲击碎裂，损失机台与整炉晶圆逾 700 万美元。
**需要的技能**：制程物理约束建模、单位量纲(dimensional analysis)校验、配方语意校验(非仅语法)、安全联锁(Safety Interlock)集成。
**开源工具**：Open Policy Agent (OPA / Rego)、Pint (量纲计算)、JSON Schema、CASL (能力授权)。
**用到的 Agent 特性**：龙虾在下发前置一道「物理校验」**子 Agent**，ClawHub 的「Process Window Guard」技能插件加载每台机台的物理窗口边界与量纲规则，**本地脚本运行** 用 Pint 做量纲与单位一致性核算、用 OPA Rego 把 850 °C/s 比对窗口上限 120 °C/s，当场判定越界并拒发、触发机台安全联锁；随后 **Multi-Channel Gateway** 把越界参数、窗口边界、推测的单位笔误根因，连同「合规但物理危险」的标签推到制程与安全群组。
**没有 Agent 的窘境**：因为配方密码学上完全合法，所有资安关卡都会放行；唯一防线是工程师的肉眼复核，但凌晨疲劳下一个多打的 0、一次单位混淆，就足以让 850 直接送进机台——这正是无数真实炸炉事故的剧本。
**效益**：物理越界拦截率从「靠人眼运气」变成 100% 量纲化校验；单次避免逾 700 万美元的机台与晶圆损失，并把「合规 ≠ 安全」这道盲区补上一层物理防呆。

> 💡 君之一席话
> 「最危险的配方往往是那份每一项签章都合法的——它骗过了所有懂密码的关卡，只差一个懂物理的守门人。」

> 🔍 高端点评──道路在哪里
> 此案把龙虾带向「资安与物理的接缝处」这条最稀缺的道路：它让 Agent 同时理解签章链与升温速率。工程上的深水区是**物理模型的维护成本**——每台机台、每代制程的窗口都在变，这份知识若过时，防呆会反成误杀。前瞻方向是把制程窗口从人工维护的规则库，演进为由机台传感数据与良率回馈持续校准的活模型，让 Agent 的物理直觉随制程一起进化；这也预示了 LIMS/RMS 配方大脑的终极形态——一个既懂数字信任、又懂物理极限的双语守护者。

## 情境 19　黄金配方知情权最小化的即时遮罩(Recipe Redaction)
**背景**：黄金配方里只有约 12% 的「关键参数」属最高机密，其余是通用框架；但传统做法是整份配方一起授权，导致外包工程师、稽核员、跨厂支持都能看到全文，知情权严重外溢。
**问题**：06:50，一名外部稽核员依法定流程调阅 A5 黄金配方做合规查核，他只需要看到版本、签章、变更纪录这些元数据，却被系统授予了完整明文访问——12% 的内核配比就这样摊在一个非内核人员眼前 40 分钟，构成一次实质的机密外溢，且事后无人察觉。
**需要的技能**：属性基访问控制(ABAC)、字段级数据遮罩(field-level redaction)、最小知情权(need-to-know)策略、访问行为审计。
**开源工具**：Open Policy Agent (OPA)、HashiCorp Vault (Transform / data masking)、OpenFGA (细粒度授权)、Apache Ranger。
**用到的 Agent 特性**：龙虾在配方访问闸道挂一个 ABAC **子 Agent**，每一次调阅请求都带上请求者角色、目的、厂区属性；ClawHub 的「Recipe Redactor」技能插件依 OPA 策略判定该角色「需知」哪些字段，**本地脚本运行** 用 Vault Transform 对 12% 内核参数做即时遮罩、只回传元数据视图，并把这次调阅（谁、看了什么视图、遮罩了哪些字段）写入不可篡改审计链；**Multi-Channel Gateway** 在侦测到「请求权限 > 实际需知」时，同步把降权事件通报数据治理群组。
**没有 Agent 的窘境**：传统做法只有「全给」或「全不给」两档；给了，内核配比就外溢；不给，稽核又做不下去。要做字段级遮罩得人工拷贝一份删节版配方给稽核员，既慢又容易删错，且每次调阅都要人手操作，无法规模化。
**效益**：机密知情面从「整份明文」收敛到「仅需知字段」，内核参数的非必要曝光次数下降逾 85%；每次调阅皆自动遮罩 + 留审计，知情权最小化从政策口号变成缺省行为。

> 💡 君之一席话
> 「保护机密最优雅的方式，不是筑更高的墙，而是让每个人都只看见他真正需要看见的那一块。」

> 🔍 高端点评──道路在哪里
> 遮罩案让龙虾走向「知情权的即时裁剪者」这条道路：它把粗暴的全有全无，磨成贴合每个人需求的精准视图。工程难点在于**策略的爆炸性组合**——角色 × 目的 × 厂区 × 字段的授权矩阵会随组织膨胀到难以维护。前瞻的解法是让 Agent 从静态策略走向意图推断：根据请求者当下的任务上下文动态决定遮罩粒度，并用可解释的理由回应「为什么这栏被遮」。当 Agent 能为每一次访问即时编织恰好够用的视图，最小知情权才真正从合规负担变成无感的缺省。

## 情境 20　配方供应链出处(Recipe Provenance)断链的可信溯源重建
**背景**：一份黄金配方的可信，创建在它完整的出处链(provenance)上：哪次仿真产出、谁签核、经哪些变更、由哪个流水线打包——这条链一旦断裂，配方即便能跑，也不该被信任。
**问题**：07:30，A2 量产前的最终放行检查发现，待用配方 `md-A2-final@v9` 的出处链在第 7 跳断裂：签核它的中间流水线记录因一次保存迁移遗失，无法证明 v9 是从哪份仿真、经谁签核而来。依零信任放行规则，一份无法溯源的配方等同来路不明，必须挡下——但量产调度在 90 分钟后启动，挡下就是整批延误。
**需要的技能**：软件供应链出处(SLSA / in-toto)、构建来源证明(build provenance)、签章链重建、跨系统证据关联。
**开源工具**：in-toto、SLSA framework、Sigstore Rekor (透明日志)、Grafana Tempo (分布式追踪)。
**用到的 Agent 特性**：龙虾的溯源 **子 Agent** 在放行检查时验证出处链完整性，侦测到第 7 跳断裂后，ClawHub 的「Provenance Mender」技能插件**本地脚本运行** 去 Rekor 透明日志、HPC 调度器与 git 三处交叉捞取残存证据，把遗失的中间流水线记录从旁证重建并重新做 in-toto 证明、补回断链；若旁证不足以重建，则明确标记「不可信、禁止放行」而非勉强放行；最后以 **Multi-Channel Gateway** 把断链位置、重建证据链、放行/拦截裁决同步到制程与品保群组。
**没有 Agent 的窘境**：工程师面对断掉的出处链，要手动去四五个系统翻日志凑证据，平均 1 小时还未必拼得回来；赶量产的压力下，人常会选择「看起来没问题就放行」——这正是供应链攻击最爱钻的人性缝隙。
**效益**：出处断链的处置从「1 小时人工拼凑 + 赌一把放行」变成 90 秒自动重建或明确拦截；放行决策首次有了可审计的证据链背书，供应链「来路不明即不放行」从原则落地为自动执法。

> 💡 君之一席话
> 「一份跑得动的配方，和一份值得信任的配方，差的就是那条能一路问到源头的出处链——断在哪里，信任就到哪里为止。」

> 🔍 高端点评──道路在哪里
> 溯源案把龙虾推向「配方供应链的可信史官」这条道路：它让每一份放行的配方都带着可一路回溯到仿真源头的家谱。最关键的工程边界是**重建与伪造的天然张力**——当 Agent 能从旁证「补回」断链，这份能力本身就可能被滥用来伪造出处。前瞻方向是让出处证明从一开始就写进不可篡改的透明日志(append-only)，使溯源无需事后重建；而 Agent 的角色则升级为连续验证者，在配方生命周期的每一跳即时盖章。当出处不再可能断裂，配方大脑才真正完成它的闭环：从物理仿真到机台运行，每一比特都有来历、每一次信任都有出处。
