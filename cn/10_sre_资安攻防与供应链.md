# 第10章　资安攻防：把反应时间压到秒级

## 情境 51　勒索软件大量文件加密行为的黄金阻断（Ransomware Golden-Cut）
**背景**：一间跨境电商的内部文件服务器集群，NFS 挂载着 47 TB 的订单与设计资产，平日尖峰约 3,000 IOPS。
**问题**：凌晨 02:14，某台被钓鱼信攻陷的研发机开始横向加密，`.locked` 扩展名以每秒 800 个文件的速度蔓延，磁盘写入暴冲到平日的 19 倍。值班工程师若按 SOP 开会、拉群、确认、再运行隔离，平均要 22 分钟——足够吃掉 100 万个文件。
**需要的技能**：文件系统 inotify 事件流分析、熵值（entropy）异常侦测、网段微隔离、不可变快照（immutable snapshot）回复。
**开源工具**：Wazuh（FIM 文件完整性监控）、Velociraptor（端点猎捕）、osquery、ZFS snapshot。
**用到的 Agent 特性**：龙虾 OpenClaw 通过 ClawHub 挂载的 `fim-entropy-watch` 技能，订阅 Wazuh 的 inotify 事件流；当它侦测到「同一 PID 在 5 秒内对 200+ 文件运行 rename + 高熵覆写」这个勒索软件签名，子 Agent 立刻在本地运行 `iptables` 把该机 IP 从 NFS 网段剔除，并对 ZFS 触发唯读冻结。Multi-Channel Gateway 同步把「已阻断、已隔离 1 台、影响 3,200 文件、快照 02:00 可回复」这张卡片推到 Slack、PagerDuty 与企业微信。
**没有 Agent 的窘境**：人类得先被告警吵醒、登录跳板机、肉眼比对哪台在狂写、再手动下隔离指令——每一步都是分钟级，而勒索软件是毫秒级。
**效益**：受害文件从预估 100 万+ 压到 3,200 个，阻断时间 22 分钟 → 4.1 秒，数据回复点精确到加密前 14 分钟。

> 💡 君之一席话
> 「勒索软件不跟你谈判反应时间，它只跟你的磁盘带宽谈判。你能省下的每一秒，都是别人赎回不了的文件。」

> 🔍 高端点评──道路在哪里
> 这个案例把龙虾推向「行为签名即策略」的自治防御道路：未来的 Agent 不再等规则库更新，而是把「异常行为模式」本身当成可运行的隔离条件。落地时最尖锐的工程问题是误杀——一次合法的大批量转档可能长得跟勒索很像。真正的成熟度不在于敢不敢砍，而在于砍之前能否用快照把「可逆性」当作安全网，让自动化在可回滚的前提下大胆行动。

## 情境 52　史诗级开源漏洞（类 Log4Shell）的全库动态清查（Fleet-wide CVE Sweep）
**背景**：一个由 1,400 个微服务组成的平台，跨 6 个 Kubernetes 集群、19,000 个容器映像，技术栈横跨 Java、Go、Node。
**问题**：周五晚上 21:30，一个 CVSS 10.0 的 RCE 漏洞（藏在某个被间接依赖 7 层深的串行化函数库）被公开 PoC。安全长要的答案只有一句：「我们到底有几个服务中招？」——而没有人能在当晚回答。
**需要的技能**：SBOM（软件物料清单）的「采集时刻」治理、传递依赖的版本约束求解、可达性分析(reachability)、容器映像层扫描、跨集群批量查找。
**开源工具**：Syft（SBOM）、Grype/OSV-Scanner（漏洞比对）、Trivy、`osv-scanner --call-analysis`(Go 可达性)、CodeQL/反向调用图、runtime eBPF profiler。
**用到的 Agent 特性**：龙虾接到 CVE 编号后，子 Agent 的工作分三层，每一层都正面回应一个「想当然」的坑：
> **(1) SBOM 采集时刻问题**——出事才现跑 Syft 扫 19,000 个映像，扫到的是「映像当下文件系统」的快照，但很多服务的依赖是 runtime 才下载/注入(动态 plugin、`pip install` at start、JNDI 远程加载)，build-time SBOM 抓不到。所以龙虾**不靠临时扫描**，而是查 CI 阶段每次 build 就自动生成、签章(in-toto/cosign attestation)并入库的**持续增量 SBOM**——出事那一刻是「静态查表」而非「动态狂扫」，且每笔 SBOM 带 build 时间戳，能标出「此清单已 23 天未更新、可信度低」。对没有持续 SBOM 的旧服务才退回临时 Syft 扫描，并明确标注「快照可能漏 runtime 依赖」。
> **(2) 传递依赖的版本约束求解**——「受影响版本区间 ∈ [2.0, 2.14.1)」这种比对，在第七层间接依赖上不是字符串比大小：Maven 的 nearest-wins、npm 的 hoisting/多版本并存、Go 的 MVS，会让「lockfile 写了 2.17 但实际解析出 2.8」。子 Agent 直接读**已解析的 lockfile / 映像内实际 jar 的指纹(sha)**，而非声明的版本范围，避开 SAT 级约束求解的不确定性——以「实际落地的 artifact」为准。
> **(3) 可达性分析——有漏洞 ≠ 可利用**：137 个「依赖树中含漏洞库」的服务里，真正危险的是「代码确实会走到那条触发 API」的子集。子 Agent 对其中关键服务跑 `osv-scanner --call-analysis`/静态反向调用图，判断有没有任何路径能调用到 sink 函数；对动态语言或反射场景，再挂 eBPF/runtime profiler 观察该符号是否真被加载调用。最终把「中招」拆成三级：**确认可达(call-graph 命中)/加载但未证实可达/仅存在于依赖树**。
>
> ClawHub 的 `cve-fanout` 技能把结果聚合成热力图：「确认可达」红色 31 个(优先且立即)、「不确定」橙色 106 个(WAF 兜底+排查)、「仅存在」黄色 275 个(调度升级即可)。Multi-Channel Gateway 把分级清单连同「建议升级版本」「临时 WAF/出站封锁规则」推给各 owner，并 @ 值班——让有限的周五夜人力先扑那 31 个。
**没有 Agent 的窘境**：传统做法发全公司信「请各组自查」等三天，回复率 60%、其中 30% 答错；就算有扫描工具，也只会吐出「137 个服务依赖树含此库」这种**不可达性过滤的长清单**，把 31 个真危险的淹没在 137 个里，周五夜的人力平均分散到全部、反而救不了最该救的。
**效益**：「我们有几个中招」从三天问卷地狱 → 8 分钟的**分级**精确清单(可达 31 / 不确定 106 / 仅存在 275)，覆盖率 60% → 100%；人力先扑真正可利用的 31 个，而非无差别 137 个，并附可一键套用的缓解规则。

> 💡 君之一席话
> 「漏洞公告出来那一刻，比的不是谁先看到新闻，而是谁先分得清『依赖树里有它』和『代码真会用到它』——前者让你恐慌，后者才让你会被打穿。」

> 🔍 高端点评──道路在哪里
> 这指向龙虾成为「常驻 SBOM 哨兵」的道路——SBOM 不该是出事才现生成的应急报告，而是 CI 每次 build 就持续沉淀、签章入库的资产。但要诚实承认两处灰色地带：其一，**build-time SBOM 永远抓不全 runtime 才出现的依赖**(远程类加载、容器内动态安装)，静态查表必须配上 runtime 物料清单(eBPF 观测实际加载的 .so/.jar)才完整，否则你查的是「应该有什么」而非「正在跑什么」。其二，**可达性分析给的是几率而非真理**——静态 call-graph 过不了反射/动态派发/串行化触发这种「数据即代码」的场景(Log4Shell 正是这类)，所以「不可达」永远不能当「安全」的同义词，只能用来**排优先序**而非排除清查。工程上最危险的，仍是一张过期或被伪造的 SBOM：它比没有清单更糟，因为它给了你一个有时间戳、有签章、看起来很可信的虚假安全感。

## 情境 53　Git 仓库敏感凭证外泄的秒级黄金救援（Secret Leak Golden-Rescue）
**背景**：一个有 600 名工程师的单体大仓（monorepo），每天约 1,200 次 push。
**问题**：14:07，一名实习生把整份 `.env` 连同 AWS Access Key、数据库主密码、Stripe 私钥一起 commit 并 push 到了公开镜像分支。这把钥匙的有效暴露时间，理论上从 push 成功那一刻就开始计费——撞库机器人扫 GitHub 公开仓的平均命中时间是 51 秒。
**需要的技能**：Git pre-receive / push event 拦截、正则与熵值双重凭证辨识、云端 IAM 密钥即时撤销、历史改写（history rewrite）。
**开源工具**：Gitleaks、TruffleHog、git-filter-repo、AWS CLI（IAM 撤销）。
**用到的 Agent 特性**：龙虾挂在 Git 服务器的 webhook 上，每次 push 由子 Agent 跑 Gitleaks + TruffleHog 双引擎扫描。命中 AWS Key 的瞬间，本地脚本直接调用云端 API `aws iam update-access-key --status Inactive` 把密钥停用、轮换，并对 Stripe key 触发 revoke。同时 Multi-Channel Gateway 私讯那位实习生、副本给他的 mentor 与安全组，附上「已撤销 3 把、已对该 commit 打开 filter-repo 清史任务」的状态卡。
**没有 Agent 的窘境**：人类流程是「有人刚好看到 → 截屏丢群 → 问是不是真的 → 找谁有 IAM 权限 → 登 console 撤销」，整条链走完 15 分钟，撞库机器人早已用这把钥匙开了挖矿机。
**效益**：密钥活命窗口 15 分钟 → 6 秒，撤销在撞库平均命中时间（51 秒）之前完成，云帐单损失归零。

> 💡 君之一席话
> 「凭证一旦离开私有边界，它就不再是『你的』秘密了——你唯一能控制的，是它从『有效』变成『废铁』的那几秒。」

> 🔍 高端点评──道路在哪里
> 这个场景把龙虾推向「撤销优先于清理」的反应哲学：泄漏发生后，改 Git 历史是慢动作，让密钥失效才是真急救。未来的道路是 Agent 直接持有受控的、最小权限的撤销令牌，形成「泄漏即作废」的闭环。但这也划出一条锋利的信任边界——一个能自动停用生产密钥的 Agent，本身就是最高价值的攻击目标。它的撤销权必须被审计、被限速、被多方背书，否则救火的水管会变成纵火的油管。

## 情境 54　红蓝对抗未知后门的自动捕获与沙盒隔离（Red-Team Backdoor Hunt）
**背景**：年度红蓝对抗演练，蓝队守着一个有 4,000 台主机的生产环境，红队植入了一个未知签名的内存常驻后门。
**问题**：红队的 C2（命令控制）信标每 300 秒以 DNS 隧道外连一次，流量混在 9 万 QPS 的正常 DNS 里，传统 IDS 规则完全静默。蓝队三天没抓到任何东西，士气低落。
**需要的技能**：DNS 隧道行为基线分析、进程内存取证、YARA 规则动态生成、沙盒爆破（detonation）。
**开源工具**：Velociraptor、YARA、Suricata、Cuckoo Sandbox（CAPE）。
**用到的 Agent 特性**：龙虾的子 Agent 对 DNS 流量做周期性建模，揪出「固定 300 秒间隔、子域名高熵、TXT 纪录异常长」的信标节律。锁定可疑进程后，本地脚本用 Velociraptor 抓取内存段，丢进 CAPE 沙盒爆破，自动萃取出 C2 域名并由 ClawHub 的 `yara-forge` 技能反向生成 YARA 规则，回灌全网扫描。Multi-Channel Gateway 把「已捕获 1 个未知后门、已生成签名、全网命中另外 2 台」推给蓝队指挥频道。
**没有 Agent 的窘境**：蓝队老手得靠肉眼在 PCAP 里捞那根 300 秒一次的针，捞到了还要手写 YARA、手动分发——往往演练结束都没捞出来，只能在覆盘会上听红队得意洋洋公布答案。
**效益**：未知后门发现时间 3 天未果 → 27 分钟捕获并生成可复用签名，且自动牵连出 2 台同源失陷主机。

> 💡 君之一席话
> 「后门最致命的不是它做了什么，而是它的『规律』——再隐蔽的潜伏者，也逃不过它必须定时回家报到的宿命。」

> 🔍 高端点评──道路在哪里
> 这条路通往「Agent 即猎手」：从等签名匹配，进化到主动对行为节律建模、自动取证、自动生成新签名的闭环。最迷人的是它让防御方第一次拥有了「现学现卖」的能力——抓到一个就立刻认得它全部的同类。但沙盒爆破带来真实的工程张力：自动把可疑样本丢去引爆，本身就是一种受控的危险动作，沙盒逃逸一旦发生，猎手的工具反而成了入侵的跳板。

## 情境 55　NPM/Pip 依赖包供应链投毒（Typosquatting）的即时防御
**背景**：一条每天触发 2,300 次的 CI/CD 流水线，前端用 npm、数据团队用 pip，依赖安装全自动。
**问题**：03:41，一个攻击者注册了 `reqeusts`（少一个 t）的恶意包，并在 `postinstall` 脚本里偷扫环境变量外传。一名工程师手滑打错，CI 自动 `pip install` 后，建置容器里的所有 secret 都在被外泄的边缘。
**需要的技能**：套件名称编辑距离（Levenshtein）比对、安装期脚本行为分析、包元数据信誉评分、CI 出站流量管控。
**开源工具**：Socket.dev（开源规则）、OSV-Scanner、Falco（容器运行期侦测）、pip-audit。
**用到的 Agent 特性**：龙虾在 CI 的依赖解析阶段插入子 Agent，对每个新包做三件事：算它与热门包的编辑距离、查它的发布时间与下载量信誉、静态扫 `postinstall` / `setup.py` 是否有网络外连或读环境变量的可疑行为。`reqeusts` 同时命中「与 requests 距离为 1」「发布仅 6 小时」「postinstall 含 curl 外连」三项，子 Agent 立刻中断该次 build、隔离容器，并由 Falco 确认没有实际外传发生。Multi-Channel Gateway 把「拦截 typosquatting 投毒、疑似拼错、正确包名为 requests」推给该工程师与平台组。
**没有 Agent 的窘境**：这类投毒在传统流水线里完全静默通过，往往要等几周后安全厂商发报告、或 secret 已经被滥用，才回头发现「那天 CI 装了个假包」。
**效益**：供应链投毒从「事后数周才发现」 → 「安装期 11 秒拦截」，secret 外泄量归零，且自动提示正确包名避免下次再错。

> 💡 君之一席话
> 「供应链攻击不攻你的城墙，它假扮成你每天都要迎进门的快递——你信任的自动化，正是它最爱的入口。」

> 🔍 高端点评──道路在哪里
> 这把龙虾推向「依赖安装即安检」的道路：每一个 `install` 都该经过一道信誉与行为的闸门，而非无条件信任 registry。未来的工程命题是把这道闸门做成「缺省零信任、按信誉放行」的策略引擎。难点在规模与摩擦的平衡——闸门太严会卡死开发者的日常，太松又形同虚设。真正的道路是让 Agent 维护一份组织自己的「可信依赖白名单」，把安全的判断从每次临时扫描，前移成持续累积的信任资产。

## 情境 56　mTLS 凭证链大规模过期的雪崩前夜抢救（Cert Expiry Avalanche）
**背景**：服务网格（service mesh）里 800 个服务以 mTLS 双向认证互连，凭证由内部 CA 签发、自动轮换。
**问题**：自动轮换的 cron 因一次静默的 RBAC 变更失效了 11 天，没人发现。直到监控显示有 230 张叶凭证将在未来 6 小时内集中过期——一旦过期，服务间握手全失败，整个网格会在凌晨同时雪崩。
**需要的技能**：X.509 凭证链解析、到期时间批量盘点、ACME / CA 签发自动化、变更影响范围评估。
**开源工具**：cert-manager、step-ca（smallstep）、OpenSSL、Prometheus blackbox exporter。
**用到的 Agent 特性**：龙虾的常驻子 Agent 每小时用 blackbox exporter 拉全网 TLS 端点的 `notAfter`，创建到期分布直方图。当它侦测到「未来 6 小时到期数量异常聚集（230 张）」且轮换 cron 已 11 天无成功记录，立刻定位到根因是 cert-manager 的 ServiceAccount 失去签发权限。本地脚本修复 RBAC 后触发批量重签，并按依赖顺序滚动下发，避免同时重启造成抖动。Multi-Channel Gateway 把「侦测到凭证雪崩、根因=RBAC、已重签 230 张、预计 12 分钟完成」推给 SRE 值班。
**没有 Agent 的窘境**：这种「自动化坏了却没人知道」的灰色失效最致命——所有人都以为轮换在跑，直到凌晨三点被全网握手失败的告警海啸淹没，然后在睡眼惺忪中手动签 230 张凭证。
**效益**：从「6 小时后全网雪崩」 → 提前 6 小时侦测并 12 分钟自愈，避免一次预估 4 小时的全网握手中断。

> 💡 君之一席话
> 「最危险的不是没有自动化，而是坏掉的自动化还在假装一切正常——沉默的成功，和沉默的失败，长得一模一样。」

> 🔍 高端点评──道路在哪里
> 这个案例直指 SRE 的灰色地带：自动化任务本身需要被监控其「是否还在成功」，而不只是监控业务指针。龙虾的道路是成为「自动化的监工」——监控那些沉默运行的 cron、轮换、备份是否真的在生效。落地的工程哲学是：任何宣称自治的系统，都必须对外暴露一个可被第三方验证的「心跳与成功率」，否则自治就只是无人值守的定时炸弹。

## 情境 57　恶意内鬼数据外渗的行为基线异常拦截（Insider Exfiltration Tripwire）
**背景**：一间金融科技公司的数据仓库，内核客户 PII 表约 9,000 万列，平日由 40 名分析师通过受控查找接口访问。
**问题**：一名即将离职的工程师，利用合法权限在周日深夜运行 `SELECT *` 全表扫描，并分 17 次将结果压缩加密后外传到个人云端。每一笔操作单看都「合规」，DLP 规则完全没触发。
**需要的技能**：用户行为基线建模（UEBA）、查找量级异常侦测、出站流量指纹分析、最小权限即时收敛。
**开源工具**：Wazuh、osquery、Suricata、OpenUBA（行为分析）。
**用到的 Agent 特性**：龙虾为每位分析师创建查找与外传的行为基线。当这名工程师在「非工作时段 + 查找量是其 90 天均值的 340 倍 + 出站到非企业云」三维同时偏离，子 Agent 判定为高可信外渗，本地脚本即时撤销其数据库 session 与出站权限，并对流量打快照存证。Multi-Channel Gateway 把「疑似内部数据外渗、已冻结帐号、已留证」静默推给安全组与法务（刻意不通知当事人，避免毁证）。
**没有 Agent 的窘境**：合法权限 + 合规操作的内鬼是 DLP 的盲区，传统做法往往是离职几个月后客户数据在暗网出现，才回头调日志——那时数据早已卖完。
**效益**：内部外渗从「事后数月才察觉」 → 「17 笔中第 2 笔即拦截」，外泄列数从 9,000 万压到 约 530 万，并完整保全链式证据。

> 💡 君之一席话
> 「最难防的攻击者，是那个有钥匙、知道规则、还清楚你监控盲点的自己人——对付他，靠的不是权限墙，而是行为的指纹。」

> 🔍 高端点评──道路在哪里
> 这条路通往「身分即边界」的零信任纵深：当权限合法时，唯一能说话的就是行为的统计偏离。龙虾的未来角色是持续学习每个身分的「正常形状」，让异常自己浮出水面。但这划出极敏感的信任边界——对人做行为画像，游走在安全与隐私、监控与信任之间。真正的工程难题不在算法，而在治理：谁有权看这些基线、误判一个忠诚员工的代价、以及如何让「静默存证」不沦为「静默监视」。

## 情境 58　容器逃逸与 K8s 提权的运行期即时封堵（Container Escape Runtime Block）
**背景**：一个多租户 Kubernetes 平台，跑着 30 个外部客户的工作负载，共用底层节点。
**问题**：某租户的容器利用一个 runc 漏洞尝试逃逸到宿主机，并读取 `/var/run/secrets` 想偷 ServiceAccount token 提权到整个集群。从逃逸成功到拿到 cluster-admin，攻击链只需要约 90 秒。
**需要的技能**：syscall 级行为侦测（eBPF）、容器逃逸特征辨识、Pod 即时驱逐与节点隔离、RBAC 爆炸半径评估。
**开源工具**：Falco、Tetragon（eBPF）、Tracee、Kyverno。
**用到的 Agent 特性**：龙虾订阅 Falco/Tetragon 的 eBPF 事件流，当侦测到容器内出现「挂载宿主 namespace + 访问 `/var/run/secrets` + 异常 `setns` 调用」这组逃逸指纹，子 Agent 在数百毫秒内由本地脚本 `kubectl drain` 隔离该节点、删除恶意 Pod、轮换被触碰的 ServiceAccount token，并用 Kyverno 即时下发禁止该租户再调度到共用节点的策略。Multi-Channel Gateway 把「侦测容器逃逸、已隔离节点 node-17、已轮换 token、爆炸半径=0」推给平台安全频道。
**没有 Agent 的窘境**：容器逃逸是秒级攻击链，人类从收到告警到搞懂「哪个 Pod、哪个节点、要不要 drain」就要十几分钟——而那 90 秒早已决定了攻击者是否拿到了整个集群的钥匙。
**效益**：提权阻断时间 十余分钟 → 约 600 毫秒，攻击在拿到 cluster-admin 前被掐断，爆炸半径从「整个集群」收敛到「单一 Pod」。

> 💡 君之一席话
> 「在共用内核的世界里，租户之间只隔着一层 namespace 的薄纸——容器逃逸比的不是谁更强，而是谁能在那 90 秒里先动手。」

> 🔍 高端点评──道路在哪里
> 这指向 eBPF 驱动的「运行期即时防御」道路：安全防线从镜像扫描的「事前」，下沉到 syscall 的「事中」。龙虾的未来是站在内核事件流上做毫秒级裁决的反射神经。工程上的硬约束是延迟与稳定性——在 syscall 热路径上做判断，误杀一个合法操作就可能让整个节点抖动。自治封堵的成熟标志，是它能精准地只切断那一个 Pod，而不波及无辜的邻居。

## 情境 59　DDoS 与凭证填充混合攻击的流量画像分流（L7 DDoS & Credential Stuffing）
**背景**：一个电商登录闸道，平日尖峰 12,000 RPS，背后是有限的后端认证资源池。
**问题**：大促首日 20:00，攻击者用 4 万个代理 IP 发动凭证填充（credential stuffing），伪装成正常登录请求灌入 18 万 RPS，后端认证服务 CPU 飙到 98%，真实用户被挤到登不进来，订单转换率瞬间腰斩。
**需要的技能**：L7 流量行为画像、IP 信誉与设备指纹聚类、自适应限速与挑战（challenge）下发、后端资源保护。
**开源工具**：Crowdsec、ModSecurity（WAF）、Fail2ban、HAProxy（动态 ACL）。
**用到的 Agent 特性**：龙虾的子 Agent 对登录流量做即时聚类，识别出「同一 UA 指纹 + 失败率 99% + 来自云端 IP 段」的填充集群，与真实用户区分开。本地脚本动态把这些指纹写入 HAProxy ACL 限速、对可疑请求下发 JS 挑战，并把确认恶意的 IP 段批量推给 Crowdsec 社群黑名单。它刻意对真实用户「只挑战、不封锁」，保护转换率。Multi-Channel Gateway 把「侦测凭证填充、已分流 17.2 万恶意 RPS、真实用户通过率回升至 96%」推给营运与安全。
**没有 Agent 的窘境**：人类在大促夜手动调 WAF 规则，往往一刀切把限速设太狠，结果恶意流量是挡住了，真实用户也被一起挡在门外——救了系统，杀了营收。
**效益**：后端认证 CPU 98% → 41%，真实用户登录成功率从 约 40% 回升至 96%，且未误伤正常下单流量。

> 💡 君之一席话
> 「挡下 DDoS 不难，难的是在风暴里认得出哪些是来捣乱的、哪些是来付钱的——防御的最高境界，是让坏人寸步难行的同时，好人毫无察觉。」

> 🔍 高端点评──道路在哪里
> 这条路通往「流量画像即防御」：从基于阈值的粗暴限速，走向基于行为与指纹的精准分流。龙虾的价值不在于挡得多狠，而在于分得多准——把恶意与善意在同一条洪流里剥离开。未来的工程命题是这套画像必须即时自适应，因为攻击者也在进化指纹。最微妙的信任边界在于「挑战」的尺度：每多一道验证码，就多流失一批真实用户，自动化必须学会在安全与体验之间做即时的经济学权衡。

## 情境 60　CI/CD 建置管线投毒与签章供应链完整性防护（Build Pipeline Poisoning & SLSA）
**背景**：一条为 200 个服务产出生产映像的中央建置平台，每天输出 1,800 个签章映像，下游集群只信任有签名的产物。
**问题**：攻击者攻陷了一个有写权限的 CI 共用 runner，悄悄修改建置脚本，在 `docker build` 阶段注入一个挖矿二进位，再用平台的合法签章密钥签名——产出的映像「血统纯正、签名有效」，却夹带后门。传统信任链在这里完全失守。
**需要的技能**：建置来源证明（provenance）验证、可重现建置（reproducible build）比对、签章密钥使用稽核、SLSA 等级评估。
**开源工具**：Sigstore / cosign、in-toto、Tekton Chains、SLSA verifier。
**用到的 Agent 特性**：龙虾的子 Agent 对每个产出映像做两道交叉验证：用 in-toto 比对「建置步骤的 provenance 是否与声明的 Dockerfile 一致」，并对关键映像做可重现建置——在一个干净的隔离环境里重跑建置，比对产物哈希。当被投毒的映像出现「哈希不一致 + provenance 多出一个未声明的下载步骤」，子 Agent 立刻撤回该映像的部署、冻结那把疑似被滥用的签章密钥，并回溯标记同一 runner 当天签出的全部产物。Multi-Channel Gateway 把「侦测建置投毒、provenance 不符、已撤回 1 映像、已隔离 runner、待复核 43 个同源产物」推给平台与安全。
**没有 Agent 的窘境**：一旦攻击者拿到了合法签章能力，「有效签名」这道防线就形同虚设——人类只会看到一个签名正常的映像安心部署，直到挖矿拖垮集群或后门被利用，才知道信任链早在 runner 那一层就断了。
**效益**：建置投毒从「签名有效即被信任、部署到生产才暴露」 → 「产出阶段 provenance 比对即拦截」，受污染映像部署数从 43 → 0，并精准框出失陷 runner 的影响范围。

> 💡 君之一席话
> 「签章只能证明『东西是我签的』，不能证明『我签的是对的东西』——当攻击者潜入产线本身，唯一的真理是把建置重跑一遍，看哈希对不对得上。」

> 🔍 高端点评──道路在哪里
> 这把龙虾推向供应链安全的终局命题：信任不能只创建在「签名有效」上，而要创建在「来源可验证、过程可重现」上（即 SLSA 的高端要求）。未来的道路是 Agent 成为产线的「血统公证人」，对每一个产物追问它的完整族谱。落地最硬的工程约束是可重现建置本身——让建置在不同时间、不同机器上产出比特级一致的结果，需要根除一切非确定性，这是整个产业都还在攀登的高山。而它的回报是：一旦达成，供应链攻击将无所遁形于哈希的对照之下。
