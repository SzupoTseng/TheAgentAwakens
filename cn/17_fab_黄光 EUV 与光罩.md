# 第17章　黄光与光罩：曝光前的最后防线

## 情境 21　光罩寿命到顶：Shot Count 超限的在线拦截与遣返
**背景**：黄光区一台 NXE:3600 EUV 扫描机 24 小时连接曝光，每片光罩(Reticle)都有原厂核定的最大曝光次数(Shot Count Limit)，超限后膜面热应力累积、CD 均匀度(CDU)开始漂移。
**问题**：凌晨 02:47，一片承载 7nm 逻辑关键层的光罩在 MES 显示累计 Shot Count 已达 198,400，距离原厂上限 200,000 仅剩 1,600 shots——但下一个批量的 Lot Size 是 2,100 片，一旦调度派工，最后 500 片将在「寿命已过期」状态下曝光，整批 25 片晶圆、每片 EUV 层成本逾 4 万美元，报废风险直逼 100 万美元。传统 SPC 报表要到早班 08:00 才会被人看到。
**需要的技能**：SECS/GEM 机台事件解析、MES Shot Count 累积查找、Reticle 生命周期管理、派工拦截(Hold)策略。
**开源工具**：`secs4python`(SECS/HSMS 通信)、`Apache Kafka`(机台事件串流)、`PostgreSQL`(光罩台帐)、`Grafana`(寿命可视化)。
**用到的 Agent 特性**：龙虾 OpenClaw 通过 `secs4python` 子 Agent 持续订阅扫描机的 `ProcessProgram Selected` 与 `Wafer Start` 事件，每收到一片就把 Shot Count 累加写进 PostgreSQL；本地脚本在派工前做「预测式余量检查」——把 `(上限 - 现值)` 与 `即将派入的 Lot Size` 相减，算出会在第几片越线。02:47 它发现缺口，立刻向 MES 发 Equipment Hold，把光罩锁在当前批量结束点，并在运维群组 @ 黄光值班与光罩工程，附上一张 Grafana 余量曲线：「本罩 1,600 shots 后到顶，建议拆批 1,600/500，后段改派备援罩 RET-7L-02。」
**没有 Agent 的窘境**：值班只能靠早班翻 SPC 报表才发现，那时超限的 500 片晶圆早已曝完，整批进入 Scrap 判定，还要开 8D 报告追责。
**效益**：寿命越线从「事后 6 小时才发现报废」→「派工前 0 秒拦截」，单次避免约 100 万美元 Scrap，光罩台帐准确率 100%。

> 💡 君之一席话
> 「设备不会在它死的那一刻通知你；它在你还能补救的那一刻沉默——Agent 的价值，就是把那段沉默翻译成一句警告。」

> 🔍 高端点评──道路在哪里
> 这个案例把 Agent 从「监控」推向「预测式派工守门」。往前一步，龙虾该做的不只是拦，而是直接向 APS 调度引擎提出「拆批+换罩」的可运行建议。落地的信任边界在于：谁有权让 Agent 真的动 Hold？在零容忍的 Fab，自动 Hold 一旦误判也会造成停线，因此规模化时必须创建「分级权限」——低风险自动运行、高风险人工覆核，这条人机协作的界线将是无人工厂最关键的工程命题。

## 情境 22　光罩表面微尘突发：Particle 侦测的天车紧急遣返与封锁
**背景**：EUV 光罩无保护薄膜(Pellicle)运作时对微尘(Particle)极度敏感，一颗 30nm 的落尘就能在整片晶圆上印出重复缺陷。光罩在传输前会经过 Reticle Inspection(如 KLA 机台)做表面扫描。
**问题**：检测机回报某片光罩膜面添加一颗 42nm Particle，落在 Active 区域边缘。但此时这片光罩已被 AMHS 天车(OHT)派车、正沿轨道前往曝光机，距离到站只剩 90 秒。一旦上机曝光，后续所有用此罩的批量全数带缺陷，按当日调度估计波及 14 个 Lot、350 片晶圆。
**需要的技能**：Reticle Inspection 结果解析、AMHS/OHT 派车状态查找、即时搬运中止(Abort Transfer)、缺陷座标比对。
**开源工具**：`secs4python`(GEM 事件)、`MQTT/Eclipse Mosquitto`(搬运状态总线)、`OpenCV`(缺陷座标叠图)、`Redis`(在途搬运缓存)。
**用到的 Agent 特性**：龙虾的子 Agent 同时挂在 Inspection 机台事件流与 AMHS 派车总在线。收到 Particle 告警的瞬间，本地脚本用 OpenCV 把缺陷座标叠到光罩 Active 区做命中判定，确认「踩线」后立刻对 AMHS 发 Transfer Abort，把天车就地改道到缓存站(Stocker)，同时在 MES 把该光罩标记 Quarantine。整个动作在 11 秒内完成，并在群组贴出缺陷叠图与一句「RET 已遣返封锁，建议转 Reticle Cleaning，曝光机改派 RET-备 03」。
**没有 Agent 的窘境**：检测结果与搬运系统是两套不互通的画面，人要先在 A 系统看到告警、再切到 B 系统找车、再打电话请 AMHS 工程手动 Abort——90 秒根本来不及，光罩通常已经上机。
**效益**：污染光罩拦截时间从「平均 4 分钟(已上机)」→「11 秒(在途遣返)」，单次避免 350 片连锁缺陷，年化挽回损失逾 800 万美元。

> 💡 君之一席话
> 「最贵的缺陷不是被看见的那一颗尘，而是它被印了三百五十次才被看见。」

> 🔍 高端点评──道路在哪里
> 此案例的关键突破是「跨系统事件的因果缝合」——Inspection 与 AMHS 本是孤岛，Agent 成了它们之间那条缺失的反射弧。未来的道路是把这种「感知到致动」的闭环标准化成 ClawHub 上的可复用技能包。但规模化挑战随之而来：当数百台天车、数十台检测机同时上线，Agent 的 Abort 指令会不会彼此冲突、造成轨道死锁？这要求龙虾从「单点反应」进化到「全局调度感知」，否则救一台会塞死整条线。

## 情境 23　EUV 光源掉电：Source Drop 突发的晶圆紧急暂存保护
**背景**：EUV 光源(LPP, 雷射激发锡电浆)是全厂最娇贵的子系统，光源功率(Source Power)一旦骤降(Source Drop)，正在曝光的晶圆会曝光不足、且机台需要长时间重新点火校准。
**问题**：14:22，扫描机回报 Source Power 从 250W 在 0.8 秒内崩到 60W，触发 Light Source Alarm。此刻机台内有 1 片晶圆正曝到第 9 层的一半，Load Port 上还有 2 个 FOUP 等待进站。若不处置，半曝晶圆会卡在腔体内氧化、暂存晶圆因机台进入长校准(预估 40 分钟)而暴露在队列瓶颈,后段 6 台机台将连锁断流(Fab Down 风险)。
**需要的技能**：EUV 光源告警解析、晶圆在腔状态判读、FOUP 紧急改派、瓶颈队列重排。
**开源工具**：`secs4python`(光源告警)、`Apache Kafka`(告警广播)、`Node-RED`(应急流程编排)、`Prometheus`(光源功率时序)。
**用到的 Agent 特性**：龙虾在收到 Light Source Alarm 的同一秒，由 Node-RED 子流程触发三件事并行：① 命令机台对半曝晶圆运行安全 Unload 到内部缓存、防止氧化；② 对 Load Port 上 2 个待入 FOUP 发改派指令，AMHS 转送邻近同型机台;③ 把该机标记 Down 并从 APS 瓶颈图中移除。同时龙虾把 Prometheus 上那条「0.8 秒崩跌」的功率曲线截给设备工程，附判断:「疑似 Droplet Generator 异常，非全厂停电，建议先查锡滴供应。」
**没有 Agent 的窘境**：光源掉电瞬间，工程师还在判断「是不是全厂跳电」，半曝晶圆在腔内氧化、暂存 FOUP 干等，等人手动改派时后段已经断流，一次小掉电演变成半条线停摆。
**效益**：应急响应从「人工判断+改派约 15 分钟」→「并行自动处置 6 秒」，半曝晶圆抢救成功率从 0 提到 90%，避免连锁 Fab Down。

> 💡 君之一席话
> 「光源熄灭只是一瞬，真正烧钱的是人类在黑暗里犹豫的那十五分钟。」

> 🔍 高端点评──道路在哪里
> 这是 Agent 从「告警转达」跃升为「应急编排者(Orchestrator)」的范例——它不只喊救命，还同时下三道并行指令。未来道路指向「Fab 级的自动应急预案库」：每一种告警对应一套经验证的处置剧本，由龙虾秒级运行。工程难点在于剧本的「副作用协调」：改派 FOUP 可能让邻机重载、Unload 动作可能与正在进行的 PM 冲突。无人工厂真正的门槛，不是写出单一剧本，而是让上百套剧本在同时触发时不互相踩踏。

## 情境 24　光罩盒湿度微超标：SMIF Pod 内置传感的天车拦截
**背景**：EUV 光罩存放于密封传输盒(EUV Pod / SMIF Pod)，盒内须维持极低湿度以防膜面吸附水气与雾化(Haze)。先进 Pod 内置环境传感，数据通过 RFID/载具系统上报。
**问题**：一个 Pod 在从 Stocker 出库、由天车送往曝光机的途中，内置湿度传感回报相对湿度从基准 0.5% 缓升到 4.2%——仍在表面看似「绿灯」的告警阈值下限，但已超过 EUV 制程的 Haze 风险红线(2%)。MES 的粗阈值不会拦它,而这片罩接下来要连续曝 8 个 Lot。若雾化在膜面生成，CD 漂移会让 200 片晶圆良率全线下滑。
**需要的技能**：载具环境数据解析、自订制程阈值规则、AMHS 在途拦截、Reticle 环境履历追溯。
**开源工具**：`MQTT/Mosquitto`(Pod 传感上报)、`InfluxDB`(环境时序)、`Grafana`(湿度趋势)、`secs4python`(AMHS 指令)。
**用到的 Agent 特性**：龙虾的子 Agent 订阅 Pod 的环境 MQTT 主题，本地脚本套用「比 MES 更严格的制程级阈值」(2% 而非 5%)。当湿度爬过 2% 且趋势仍在上升，它判定「将触 Haze 风险」，对 AMHS 发在途拦截、把 Pod 转去干燥 Purge 站做 N2 吹驱，并在群组贴 InfluxDB 趋势图：「Pod 湿度 0.5%→4.2% 持续上升，已转 Purge，预计 12 分钟回干，曝光调度顺延或改备罩。」
**没有 Agent 的窘境**：湿度还没到 MES 红灯，没人会看；等到雾化在晶圆上印出来、良率掉了才回头查光罩,环境数据早已滚掉,根本对不上是哪一段路湿了。
**效益**：把拦截阈值从「MES 粗阈值 5%」收紧到「制程级 2%」，提前 12 分钟介入，单罩避免 200 片 Haze 良率损失，并创建 Pod 全程湿度履历。

> 💡 君之一席话
> 「绿灯不代表安全，只代表没有人替你把标准调到够严。」

> 🔍 高端点评──道路在哪里
> 这个案例揭示了一条被忽视的道路：Agent 可以承载「比 MES 更精细的制程知识」，成为设备粗阈值之上的一层智能滤网。往前看，这些制程级规则会逐渐沉淀为 ClawHub 上由制程工程师维护的「知识插件」。但信任边界很现实——当 Agent 用比官方系统更严的标准挡料，IT 与制程的权责如何划分?规模化时，这套「影子阈值」必须有版本控管与审计轨迹，否则就成了无人管辖的灰色规则。

## 情境 25　光罩条码碳化：Barcode 读取失败的大迷航自愈
**背景**：每片光罩以条码(Barcode/2D Matrix)做身份识别，AMHS 与机台在每个交接点扫码确认载具身份。EUV 高能曝光环境长期下会让条码标签表面碳化、对比度下降。
**问题**：03:15，一片高频使用的光罩在曝光机 Load Port 交接时扫码失败(No Read)，AMHS 因为「不知道车上是谁」而拒收，光罩被退回轨道、进入「身份不明」状态，俗称光罩大迷航(Reticle Lost)。它在系统里变成幽灵载具，既不能上机也回不了 Stocker，依赖它的 3 个批量全部卡死，每分钟瓶颈损失逾 2 万美元。
**需要的技能**：条码读取事件解析、载具身份比对与重绑、AMHS 载具状态修复、影像增强识别。
**开源工具**：`ZXing/zbar`(条码解码)、`OpenCV`(影像对比度增强)、`secs4python`(AMHS 载具重绑)、`SQLite`(交接点履历)。
**用到的 Agent 特性**：龙虾侦测到 No Read 事件后，子 Agent 立刻调出该交接点的摄影影像，本地脚本用 OpenCV 做对比度拉伸+去碳化滤波，再交给 ZXing 重新解码；同时用「最后已知位置+调度关联」做交叉验证(这条轨道上、这个时段、该去这台机的，只可能是 RET-7L-09)。双重确认身份后，它对 AMHS 发载具重绑(Re-associate)指令，把幽灵载具救回正常状态，并在群组通报:「RET-7L-09 条码碳化致 No Read，已影像重识+身份重绑，建议调度更换标签。」
**没有 Agent 的窘境**：光罩一迷航就得叫 AMHS 工程半夜进无尘室，人工到轨道上肉眼确认载具、再手动在系统里重绑,流程动辄 30 分钟以上，期间整条黄光支线卡死。
**效益**：光罩迷航自愈，MTTR 从 30 分钟 → 50 秒，避免半夜人工进无尘室，并自动产生标签更换工单做根因预防。
> 💡 君之一席话
> 「机器迷路时不会喊救命，它只是安静地停在那里，等一个认得它的人——而现在那个人是 Agent。」

> 🔍 高端点评──道路在哪里
> 条码自愈展示了 Agent 的「多模态交叉验证」——影像、调度、轨道位置三路证据彼此印证，把不确定性压到可自动运行的门槛下。未来道路是让这种「身份恢复」成为 AMHS 的标准自愈能力。但这里藏着无人工厂最敏感的信任边界:让 Agent 自动「重绑载具身份」，等于授权它修改物理世界的真值来源。一旦推论错误、把 A 罩当 B 罩绑回去，后果是灾难性的。规模化的前提，是为每一次自动重绑创建可回溯、可推翻的证据链与信心分数门槛。

## 情境 26　Pellicle 薄膜破损：EUV 光罩护膜穿孔的曝光前急停
**背景**：EUV 光罩的护膜(Pellicle)是悬在膜面上方的超薄碳纳米管薄膜，用来挡落尘。它本身极脆，任何微穿孔(Pinhole)都会让尘粒直接落到 Active 区。光罩上机前会过 Pellicle Inspection。
**问题**：检测回报某片光罩的 Pellicle 在边缘出现一个约 5μm 的穿孔(Pinhole)，且穿孔位置正对着一个 Stage 气流涡流区——这意味着尘粒被「吸」进去的几率极高。但这片罩已排定 4 分钟后上机,连续曝 11 个 Lot。一旦带孔曝光，落尘缺陷会周期性印满每片晶圆。
**需要的技能**：Pellicle Inspection 结果解析、气流风险区判读、曝光调度急停(Hold)、光罩送返清洗派工。
**开源工具**：`secs4python`(检测事件)、`OpenCV`(穿孔定位)、`Node-RED`(急停流程)、`PostgreSQL`(Pellicle 履历)。
**用到的 Agent 特性**：龙虾的子 Agent 接到 Pellicle Inspection 的 Pinhole 告警，本地脚本把穿孔座标与机台 Stage 的气流风险区图层叠图，判定「落在高风险涡流区」后，直接对曝光调度发 Hold、阻止上机，并开立 Pellicle 更换工单把光罩导向 Re-pellicle 站。群组通报附叠图:「RET Pellicle 边缘 5μm 穿孔，落在 Stage 涡流区，已急停上机，建议重贴护膜，11 个 Lot 改备罩接力。」
**没有 Agent 的窘境**：穿孔小到报表上只是一行数字，没人会把它跟「气流风险区」联想在一起；等晶圆上出现周期性落尘缺陷、回头查才发现是 4 小时前那个 Pinhole，11 个 Lot 已全数曝完。
**效益**：把「孤立的检测数字」升级为「带物理脉络的风险判断」，提前 4 分钟急停，单次避免 11 Lot 连锁落尘，护膜履历可追溯。

> 💡 君之一席话
> 「一个五微米的洞本身无害，害的是没有人把它和那股看不见的气流连起来想。」

> 🔍 高端点评──道路在哪里
> 此案例的高端点，是 Agent 把「检测数据」与「机台物理模型(气流场)」做了融合判断——这已超越规则告警，逼近工程直觉的数字化。未来道路是把更多机台物理模型(热场、气流、振动)喂给 Agent，让它做「情境化风险推理」。落地的工程难题是模型的维护成本与可信度:物理模型一旦过时或失准，Agent 的「聪明判断」反而会制造误停。无人工厂的成熟标志，是创建模型与现场数据的持续校准闭环，而非一次性灌入。

## 情境 27　双罩 CDU 漂移：同层多光罩 CD 均匀度交叉比对的早期拦截
**背景**：高良率关键层常配置多片同设计光罩轮替使用以分摊 Shot Count。各罩之间的曝光特性须一致,否则同一层用不同罩会造成晶圆间 CD 均匀度(CDU)分裂,SPC 上呈现双峰分布。
**问题**：早班量测站(CD-SEM)数据显示某关键层的 CDU 出现双峰:用 RET-A 的晶圆中位 18.2nm、用 RET-B 的中位 19.6nm，差 1.4nm，已逼近制程窗(±1.5nm)边缘。传统 SPC 对「全体」做管制不会报警，因为合在一起的平均值还在中心，但分罩看就是两个族群在拉扯，再漂一点就会有半数批量超规。
**需要的技能**：CD-SEM 量测数据分群、按光罩维度的 SPC 拆解、制程窗风险预测、光罩特性校正建议。
**开源工具**：`pandas`(数据分群)、`scikit-learn`(双峰/聚类侦测)、`Grafana`(分罩 SPC)、`PostgreSQL`(量测仓)。
**用到的 Agent 特性**：龙虾定时拉 CD-SEM 量测仓，本地脚本用 pandas 把数据按「使用的光罩 ID」重新分群,再用 scikit-learn 侦测到显著双峰。它计算出 RET-B 偏高 1.4nm、外推 3 个批量后 RET-B 将触顶，于是在 SPC 失控前主动通报制程:「本层 CDU 隐性双峰,RET-A/RET-B 差 1.4nm,建议将 RET-B 送 Reticle Qualify 重校或暂停轮替。」并附 Grafana 分罩趋势图。
**没有 Agent 的窘境**：合并看的 SPC 一片祥和，没人想到要「按光罩拆开看」；等真的有批量超规、品保拦料、回头做相关性分析才挖出是某片罩偏移,中间几百片晶圆已带风险流到下站。
**效益**：把隐藏在合并 SPC 下的「分罩双峰」提前暴露，在失控前 3 个批量介入，避免半数批量 CD 超规,并精准锁定问题光罩。

> 💡 君之一席话
> 「平均数是最温柔的谎言——它把两群正在分裂的数据，安慰成一个看似健康的中心。」

> 🔍 高端点评──道路在哪里
> 这个案例代表 Agent 从「事件反应」走向「数据洞察」——它不等告警，而是主动换维度看问题，挖出统计学上被平均值掩盖的真相。未来道路是让龙虾成为一个「永不疲倦的数据侦探」,持续对全厂数据做多维拆解与异常聚类。工程挑战在于「洞察的讯噪比」:换维度看一定会发现大量统计巧合，如何让 Agent 只在真正有制程意义时才开口，而非用一堆 p 值轰炸工程师?这需要把领域知识编码进判断,是数据驱动 Agent 规模化的内核门槛。

## 情境 28　EUV Stage 温漂：曝光台热稳定异常的套刻(Overlay)风险预警
**背景**：EUV 曝光的套刻(Overlay)精度对温度极敏感，曝光台(Wafer Stage)的环境温度须恒定在毫度级。扫描机持续上报 Stage 温度与套刻量测回授。
**问题**：机台 Stage 温度在两小时内出现 0.012°C 的缓慢单向漂移——数值微小到没触发任何机台告警，但 Overlay 量测上已能看到 X 方向系统性偏移 0.6nm 并持续扩大。当前制程 Overlay 规格 3.0nm，看似还很安全，但这是「会自己长大」的漂移，照趋势 5 小时后将吃掉一半预算,且期间曝的所有晶圆都带累积偏移。
**需要的技能**：Stage 温度时序分析、Overlay 趋势回归、漂移外推预测、设备 PM 触发建议。
**开源工具**：`InfluxDB`(温度/套刻时序)、`Prometheus`(趋势告警)、`statsmodels`(线性外推)、`Grafana`(双轴关联图)。
**用到的 Agent 特性**：龙虾的子 Agent 把 Stage 温度与 Overlay 偏移两条时序拉进 InfluxDB，本地脚本用 statsmodels 对近两小时做线性回归，发现两者高度相关且皆单向扩大。它外推出「5 小时后 Overlay 触 1.5nm」，于是在还没有任何告警时就主动预警设备:「Stage 温漂 0.012°C 与 Overlay X 偏移 0.6nm 强相关且持续扩大,建议调度内安插温控校验,勿等告警。」并把双轴关联图贴进群组。
**没有 Agent 的窘境**：0.012°C 在任何仪表板上都像杂讯，没人会盯;等 Overlay 真的逼近规格、套刻不良率上升才查，发现是温控组件慢性老化,期间几小时的晶圆全带系统性偏移。
**效益**：把「亚告警级」的慢漂移在失控前 5 小时抓出，避免数百片套刻偏移晶圆，并把被动 PM 变成预测性维护(PdM)。

> 💡 君之一席话
> 「最危险的故障不是爆炸，而是温柔地、每小时长大一点点,直到你来不及。」

> 🔍 高端点评──道路在哪里
> 这是 Agent 迈向「预测性维护(PdM)」的典型样本——它关注的不是当下值，而是趋势的「导数」。未来道路是让龙虾对全厂关键参数普遍创建漂移外推模型,在告警阈值之前数小时就介入。规模化的工程张力在于「狼来了」风险:外推预测本质带不确定性，太早喊会被当杂讯忽略，太晚喊又失去意义。如何校准预测的提前量与信心,并让 Agent 学会「在对的时间、对的对象、用对的证据」开口,将决定 PdM 是真资产还是告警疲劳的新来源。

## 情境 29　光罩出库冲突：Reticle 双重派工(Double Booking)的并发拦截
**背景**：高产出黄光区多台 EUV 机共用一个光罩库(Reticle Stocker)，热门关键层的光罩数量有限。调度系统在高负载下偶尔会把同一片光罩在重叠时间派给两台机台。
**问题**：09:33，调度在 4 秒内对 RET-7L-01 连发两笔出库请求:一笔要送往 EUV-03 曝 Lot-A，另一笔要送往 EUV-07 曝 Lot-B,时间窗重叠。物理上一片光罩不可能同时在两台机,结果必然是其中一台等不到罩、机台闲置断流,而调度系统因为两笔都「已派工」而毫无察觉,典型的并发双重派工(Double Booking)。
**需要的技能**：出库请求并发监测、载具独占性校验、派工冲突仲裁、机台闲置风险评估。
**开源工具**：`Redis`(分布式锁/在途登记)、`Apache Kafka`(出库事件流)、`secs4python`(派工指令)、`PostgreSQL`(光罩占用台帐)。
**用到的 Agent 特性**：龙虾的子 Agent 监看光罩出库事件流,本地脚本对每片罩维护一把 Redis 分布式锁(代表「物理独占」)。当 RET-7L-01 的第二笔请求进来、发现锁已被第一笔持有,它立即判定 Double Booking,拦下冲突的第二笔派工,并用「机台优先序+Lot 急迫度」做仲裁:Lot-A 已在 Load Port 等候、Lot-B 还在排队,于是放行 EUV-03、把 EUV-07 改派轮替罩 RET-7L-05。群组通报:「侦测 RET-7L-01 双重派工,已仲裁:EUV-03 优先,EUV-07 改 RET-7L-05,避免机台闲置。」
**没有 Agent 的窘境**：两笔派工都显示绿灯,没人知道撞车;直到 EUV-07 干等光罩、机台闲置告警响起,工程师才一头雾水地查「罩到哪去了」,发现被另一台抢走,手动协调又是十几分钟断流。
**效益**：并发双重派工从「事后机台闲置才发现」→「请求进来即时仲裁」,把潜在 15 分钟机台断流压到 0,并补上调度系统缺失的「物理独占性」防线。

> 💡 君之一席话
> 「软件可以同时答应两个人,但物理世界只有一片光罩——Agent 的职责,就是替调度系统还清它开不出的支票。」

> 🔍 高端点评──道路在哪里
> 这个案例把 Agent 定位成「物理世界的并发守门员」——它用分布式锁为现实中的独占资源加上调度系统缺失的一致性保证。未来道路是让龙虾承担更广的「资源仲裁者」角色:光罩、量测机、特殊治具,凡是稀缺且独占的物理资源都该有它守着。工程上的深水区是仲裁公平性与全局最优的拉扯——每次「就近放行」的局部决策,累积起来可能让某些 Lot 长期被插队饿死。规模化的无人工厂需要 Agent 从「冲突拦截」升级到「全局公平调度」,这已触及分布式系统最硬的一致性与调度理论。

## 情境 30　光罩误装关键层：Wrong Reticle 上机前的设计层号交叉验证
**背景**：一个产品有数十个曝光层,每层对应特定光罩。MES 在派工时下发「该上哪片罩」的指令,理论上不会错,但在换产品、急插单、人工干预出库等情境下,曾发生把 A 层的罩装去曝 B 层的致命错误(Wrong Reticle)。
**问题**：16:08,一笔急插单在人工出库后,系统指令要把 RET-M2(Metal-2 层)的光罩装上 EUV-05,但这台机当前批量的 Recipe 对应的是 Via-1 层。层号对不上——这是会让整批晶圆图案完全错置、100% 报废的致命误装。MES 的派工指令本身「格式合法」,不会自己报错,而曝光只要一启动就无法挽回,25 片晶圆、超过 100 万美元当场蒸发。
**需要的技能**：Recipe 层号解析、光罩设计层比对、上机前致命错误拦截(Interlock)、人工出库稽核。
**开源工具**：`secs4python`(Recipe/Reticle 事件)、`PostgreSQL`(光罩-设计层对照表)、`Node-RED`(上机前 Interlock)、`Grafana`(误装稽核看板)。
**用到的 Agent 特性**：龙虾在光罩上机(Reticle Load)的最后一刻插入一道软件 Interlock:子 Agent 从机台事件取出「即将装载的光罩 ID」与「当前批量 Recipe 的设计层号」,本地脚本拿去查 PostgreSQL 的光罩-设计层对照表做交叉验证。发现 RET-M2(Metal-2)≠ Recipe 要求的 Via-1,立即对机台发 Inhibit、阻止 Reticle Load,并红字通报:「⚠ Wrong Reticle 拦截:EUV-05 欲装 RET-M2(Metal-2),但 Recipe 为 Via-1,层号不符,已 Inhibit 上机,请黄光复核出库单。」这道防线在曝光启动前 0 秒筑起。
**没有 Agent 的窘境**：人工出库一旦拿错罩、MES 指令又合法,没有任何系统会喊停;曝光按下去、整批图案错置,等下站量测发现「这层怎么是别层的图」才惊觉,25 片晶圆已是废品,还要追为什么会误装。
**效益**：在不可逆的曝光前筑起最后一道层号 Interlock,把致命 Wrong Reticle 拦截率提到 100%,单次避免逾 100 万美元整批报废,并留下完整误装稽核轨迹。

> 💡 君之一席话
> 「在黄光区,最后按下去的那一键没有 Ctrl+Z;Agent 存在的全部意义,就是在那一键之前多问一句『你确定这是对的层吗?』」

> 🔍 高端点评──道路在哪里
> 这是全章的压轴,也是 Agent 价值的纯粹形态:在不可逆操作前,做一次人类会跳过的交叉验证。未来道路是把这种「上机前 Interlock」标准化为所有致命操作的通用前置守卫,由 ClawHub 沉淀成可复用的「最后防线」技能。但这里是信任边界的极点——当 Agent 有权 Inhibit 生产,它的误判成本(无谓停线)与漏判成本(整批报废)必须被审慎权衡。无人化智能工厂的终局,不是让 Agent 取代人按下那一键,而是让它成为那个永远清醒、永不疲倦、永远在问「你确定吗」的最后一道理性。
