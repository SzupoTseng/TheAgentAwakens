# 第7章　ストレージとデータベース：一貫性とパンクの戦い

## シナリオ21　マスター・スレーブ複製遅延(Replication Lag)における読み書き分離の緊急流量制限
**背景**：ECサイトのマスターDB(Primary)が書き込みを引き受け、5台のリードレプリカ(Read Replica)がクエリを分散処理する。独身の日セール前週、負荷試験の流量が流れ込んできている。
**問題**：深夜02:14、あるセール企画がバッチ書き込みを引き起こし、マスターDBのWAL生成速度が180 MB/sまで急騰、レプリカの `pg_stat_replication` の `replay_lag` が200msから **47秒** まで跳ね上がった。ユーザーが注文後に注文照会で「該当する注文なし」となるクレームが毎分300件殺到し、さらに悲惨なことに——重複注文した者まで現れた。一貫性の綻びが、金銭の綻びへと変わりつつある。
**必要なスキル**：複製トポロジーの健全性判読、読み書き分離のルーティング戦略、流量整形(Traffic Shaping)、業務分級ダウングレード。
**オープンソースツール**：PostgreSQL、Patroni、ProxySQL/PgBouncer、Prometheus + `postgres_exporter`。
**活用されるエージェントの特性**：ロブスター🦞 OpenClaw は Prometheus アラートにより起動され、まず ClawHub 上の `replica-lag-triage` スキルプラグインを実行、5台のレプリカの `replay_lag` とマスターDBの `pg_current_wal_lsn` の差分を突き合わせ、「書き込みストームによる全域的 lag」であって単一レプリカの故障ではないと判定する。ローカルでスクリプトを実行し、ProxySQL のルーティング規則を動的に調整——「注文照会」のような強一貫性が求められる読みリクエストを**一時的にマスターDBへ向け直し**、弱一貫性の読み(商品閲覧)はレプリカのまま維持、さらにバッチ書き込みには token-bucket で80 MB/sへの流量制限をかける。Multi-Channel Gateway は「読み流量のマスターDB回帰 + 書き込み制限を起動済み」という判断を Slack 戦況室と当番の PagerDuty に同期し、lag 曲線のスクリーンショットを添付する。
**エージェントがない場合の苦境**：当番のSREが叩き起こされ、まず8分かけて踏み台サーバーにログインし、いったいどのレプリカが壊れたのか、それとも全滅なのかを確認、それから手動で ProxySQL の規則を変更する——手が滑って注文読みまでレプリカに振り分けてしまい、火に油を注ぎ、クレームはさらに倍増する。
**効果**：一貫性の綻びの収束時間 MTTR が **22分 → 50秒**；重複注文事故が1,200件から18件へ圧縮。

> 💡 珠玉のひとこと
> 「複製遅延は決してデータベースの病ではない。あなたが『読んだものこそ真実だ』と装ったその瞬間に蒔かれた因なのだ。」

> 🔍 上級者の講評──道はどこにあるか
> この事例はロブスターを「一貫性レベルの動的ルーター」という道へ押し出す——未来のエージェントは単に規則を変えるのではなく、各SQLの業務的意味に応じて、それがどれだけの staleness を許容できるかを自動判定するようになる。実装上の難点は信頼境界にある：読み流量をマスターDBへ回帰させるのは諸刃の剣であり、エージェントは「マスターDBに書き込みの余力がどれだけ残っているか」を理解せねばならない。さもなくば一貫性を救った代わりに書き込みパスを潰してしまう。次のステップはエージェントに「業務一貫性 SLA マップ」を持たせることだが、このマップの維持権限こそ、人とエージェントが最も長く綱引きをする領域となるだろう。

## シナリオ22　PostgreSQLデッドロック(Deadlock)の根本原因追跡とロック解除
**背景**：決済の照合突合サービス。2つのworkerがそれぞれトランザクション内で `accounts` と `ledger` を更新するが、ロック取得順序が一致していない。
**問題**：14:03に照合バッチが起動すると、`pg_stat_activity` に大量の `wait_event_type = Lock` が現れ、アクティブ接続が40から**プール上限の200**まで積み上がり、新規リクエストはすべて `too many connections`。ログには `deadlock detected` が7秒ごとに流れ、PostgreSQLは一方を犠牲にして自動ロールバックするものの、2つのworkerはドアを互いに譲り合う2人のように、無限にリトライしては衝突し合い、スループットはゼロに落ちた。
**必要なスキル**：ロック待ちグラフ(Lock Wait Graph)分析、トランザクションのロック取得順序監査、接続プール統治、`pg_blocking_pids` 判読。
**オープンソースツール**：PostgreSQL、`pg_locks`/`pg_stat_activity`、pgBadger、pganalyze collector(オープンソース版)。
**活用されるエージェントの特性**：ロブスターは `deadlock detected` のログパターンから起動され、ClawHub の `deadlock-grapher` スキルを呼び出し、`pg_blocking_pids()` を照会してロック待ちの環を再構築、2つのSQLのロック取得順序が逆という根本原因を特定する。それは**むやみに kill せず**、まずサブエージェントで2つのworkerの呼び出しスタックを引き出し、どちら側のトランザクションが短くロールバックの代償が小さいかを確認してから、そのPIDに `pg_terminate_backend` を実行してデッドロックを打破し、さらに接続プールの `statement_timeout` を一時的に5sまで絞って止血する。Multi-Channel Gateway は「ロック待ちの環の Mermaid 図 + 犯人の2つのSQL」をエンジニアリングのグループに貼り付け、該当する code owner を@する。
**エージェントがない場合の苦境**：DBAが手動で3層の `pg_locks` JOIN クエリを走らせ、十六進数のPIDの間を目で行き来して照合し、10分かかってようやく環がどこにあるかを理解する。その間に接続プールはとっくにあふれ、照合サービス全体が503となっている。
**効果**：デッドロック根本原因の特定 **15分 → 40秒**；接続プール枯渇によるサービス不可用の窓口が11分から35秒へ短縮。

> 💡 珠玉のひとこと
> 「デッドロックは運が悪いのではない。2つのコードが『先にどちらをロックするか』で各々言い張った結果だ——データベースはただ、お前たちの傲慢に裁定を下しただけだ。」

> 🔍 上級者の講評──道はどこにあるか
> 真の価値はロック解除にあるのではなく、エージェントが「ロック取得順序が逆」というこの根本原因を逆方向にCIへ送り返せる点にある——これは「運用事故を自動的に静的検査ルールへ変換する」道を指し示している。難点はこうだ：backend を殺すのは副作用を伴う破壊的動作であり、エージェントは自分が選んだのが「ロールバックの代償が最小」の側だと証明せねばならない。さもなくば斬り捨てたのは実行中の重要な照合かもしれない。スケール化した後、誰がエージェントの `terminate` 権限を承認するのか、どの粒度まで授けるのかは、どの会社も改めて一度交渉せねばならないレッドラインとなる。

## シナリオ23　Ceph/MinIOオブジェクトストレージ容量の突発的ゼロ化に対する即時封鎖
**背景**：自前構築の MinIO クラスタがログとメディアのアップロードを引き受け、バックエンドは4ノード × 12台 HDD の Erasure Set。
**問題**：21:40、監視がクラスタの利用可能容量が25分で18 TBから**まっすぐゼロへ**落ちたと表示する。元凶はあるサービスの debug スイッチが誤ってオンにされ、完全な request body をオブジェクトとして狂ったように書き込んだこと。QPSは高くないが1件あたり40 MBである。MinIOは `XMinioStorageFull` を返し始め、同クラスタの正常なアップロードまで道連れに引きずり倒した。さらに危険なのは——ディスクが満杯になるとメタデータの更新まで失敗し、クラスタは読み取り専用、さらには破損のリスクに直面する。
**必要なスキル**：オブジェクトストレージ容量の水位判読、Bucketのトラフィック帰属分析、クォータ(Quota)の即時下発、ライフサイクル(Lifecycle)戦略。
**オープンソースツール**：MinIO、`mc` admin CLI、Prometheus(`minio_bucket_usage` metrics)、Grafana。
**活用されるエージェントの特性**：ロブスターは水位が92%を突破した時点で起動し(ゼロ化を待たない)、ClawHub の `object-store-hog-finder` スキルを実行、`mc admin` と bucket metrics を用いて40秒以内に暴走書き込みの bucket と発信元IPへ帰属分析する。それは**即座に封鎖する**：当該 bucket に一時クォータを下発し、bucket policy で犯人の service account の `PutObject` を遮断、同時に7日間の lifecycle 規則を取り付けて debug オブジェクトを掃除する。ローカルスクリプトはついでに top-10 の急増プレフィックス(prefix)をダンプ出力する。Multi-Channel Gateway は「bucket X を封鎖済み、発信元 svc-Y、回収容量見積もり9 TB」を on-call と当該サービス owner の Teams チャンネルに同期する。
**エージェントがない場合の苦境**：SREは「ディスク満杯」アラートを受け、まずログの容量爆発ではないかと疑い、bucketごとに `mc du` を走らせて調査する(毎回数分)。犯人を見つけた頃にはクラスタはすでに満杯、メタデータ書き込みが失敗し、緊急の容量拡張と fsck を余儀なくされ、数時間の停止となる。
**効果**：アラートから犯人封鎖まで **30分 → 45秒**；クラスタ満杯後の読み取り専用ダウングレードを回避し、約6時間の潜在的停止を取り戻した。

> 💡 珠玉のひとこと
> 「ストレージ容量は『使い切られる』のではない。誰も見ていない debug スイッチによって、お前が眠っている間に1バイトずつ盗まれていくのだ。」

> 🔍 上級者の講評──道はどこにあるか
> この道は「容量の能動免疫システム」へ通じる——エージェントが100%ではなく92%で手を打つのは、本質的に運用を『消火』から『予防接種』へ変えることだ。エンジニアリング上の真の難題は帰属分析の速度と精度にある：PB級のオブジェクトストレージでリアルタイムに top prefix を算出するのは安くない。エージェントには臨時の全スキャンではなく、常駐の増分統計が必要だ。そして service account を封鎖するというこの動作は、ある業務ラインを直接供給停止にする。エージェントは「暴走した debug」と「正当なピーク」を区別せねばならず、この判断問題を一度でも誤れば、信頼は使い果たされる。

## シナリオ24　大陸をまたぐデータベース複製リンク断絶におけるグローバルな読み書き転移
**背景**：金融グレードのサービスが3拠点展開(東京 Primary、フランクフルト Sync Standby、バージニア Async Replica)を採用し、大陸をまたぐ専用線で複製する。
**問題**：03:27、東京↔フランクフルト間の海底ケーブル区間が揺らぎ、同期複製(synchronous_commit)が standby の確認を待ちきれず**書き込み全体がフリーズ**——東京マスターDBの commit がすべて `SyncRep wait` で hang し、欧州ユーザーの取引タイムアウト率は60%まで急上昇した。これは最も凶悪な種類だ：マスターDBが落ちたのではなく、それが「健全に、永遠に返ってこないACKを待ってフリーズしている」のだ。
**必要なスキル**：同期/非同期複製の意味論、Quorum commit の調整、リージョンをまたぐフェイルオーバー(Failover)の意思決定、スプリットブレイン(Split-brain)防護。
**オープンソースツール**：PostgreSQL、Patroni + etcd、HAProxy、Prometheus blackbox_exporter。
**活用されるエージェントの特性**：ロブスターは `SyncRep wait` の継続時間 + リージョン間 RTT 探測によって同時に起動され、ClawHub の `geo-failover-advisor` スキルを実行、まず blackbox プローブで「リンク断絶」であって「standby プロセスの死」ではないことを確認し、誤判定を避ける。それは段階的な動作を下す：第一歩で `synchronous_standby_names` を強同期から `ANY 1 (frankfurt, virginia)` へダウングレードし、**commit をまだ通じているバージニアへ向けて quorum を取得させ**、ただちに書き込みの hang を解除する；同時に Patroni に対し、リンクの揺らぎ期間中にフェイルオーバーを誤発動しないよう通知する(スプリットブレイン防止)。サブエージェントは並行して海底ケーブルの復旧を監視し、RTT が安定し次第、自動的に強同期へ昇格させる。Multi-Channel Gateway は「同期戦略を quorum へダウングレード済み、RPO リスク窓口 X 秒」を全世界の SRE on-call へブロードキャストする。
**エージェントがない場合の苦境**：当番のエンジニアは「マスターDBは落ちていないのに書き込めない」という奇怪な現象を前に、第一反応でフェイルオーバーをしようとし、危うくスプリットブレインを発動させてデータ分岐を引き起こしかける；「切るべきかどうか」を整理するだけで20分の電話会議を開いた。
**効果**：書き込み hang の解除 **MTTR 25分 → 60秒**；一度の大陸をまたぐスプリットブレイン(潜在的なデータ分岐と数時間の照合)を回避。

> 💡 珠玉のひとこと
> 「最も恐ろしい故障は、マスターDBが死ぬことではない。それが生きていて、健全で、それでいて永遠に来ない返信を待っていることだ——これこそが分散システムのグレーゾーンなのだ。」

> 🔍 上級者の講評──道はどこにあるか
> この事例はエージェントの最も敏感な能力境界を指し示す：**一貫性とRPOのトレードオフを自動調整すること**。同期戦略をダウングレードするということは「数秒のデータ損失リスクを引き受けて可用性と交換する意志がある」ということで、これは従来、人間だけが署名できる決定だった。それをエージェントに委ねるには、明確で監査可能な「業務が一貫性を可用性とどこまで交換する意志があるか」という契約が必要だ。そしてスプリットブレイン防止というこの一件は我々に告げる：リージョンをまたぐ災害において、エージェントの最大の価値は、時に『人間をむやみに切らせないよう諫めること』である——自制こそ、次世代の運用エージェントが最も訓練しにくい美徳となるだろう。

## シナリオ25　Longhorn/Rook-Cephのスタックボリューム(Stuck Volume)の無痛解除
**背景**：Kubernetes クラスタが Longhorn で PV を提供し、ステートフルサービス(StatefulSet)のデータベース Pod が RWO ボリュームをマウントする。
**問題**：ノードが予期せずハードリブートした後、Pod が新ノードへドリフトしたものの `ContainerCreating` でスタックし、イベントには `Multi-Attach error: Volume is already exclusively attached to one node` が流れ続ける。旧ノードの `VolumeAttachment` オブジェクトが、kubelet が優雅にアンマウントできなかったために**孤児**となり、PV はもはや存在しない旧ノードにがっちり縛り付けられている。データベースのマスター Pod はすでに **14分** ダウンし、マスター・スレーブ切り替えもボリュームのスタックで完了できず、サービスは完全に倒れた。
**必要なスキル**：CSI Attach/Detach ライフサイクル、Longhorn ボリュームのステートマシン、K8s finalizer の掃除、StatefulSet 復旧のオーケストレーション。
**オープンソースツール**：Longhorn、Kubernetes、`kubectl`、Longhorn Manager API。
**活用されるエージェントの特性**：ロブスターは Pod の `ContainerCreating` が90秒を超過 + `Multi-Attach` イベントを検知した時点で起動し、ClawHub の `stuck-volume-rescue` スキルを実行する。それは**まず安全前提を検証する**：Longhorn API を通じて旧ノードが確かにすでに NotReady であり、当該ボリュームに実際の書き込みマウントがないこと(二重書き込みによるデータ破壊を回避)を確認してから、掃除を実行する——孤児 `VolumeAttachment` を削除し、スタックした finalizer を除去、Longhorn の detach を発動してボリュームを新ノードの attach へ解放する。ローカルスクリプトは続けてデータベース Pod が `Running` でかつ readiness プローブを通過したことを確認する。Multi-Channel Gateway は全過程で「孤児 VA を掃除済み、ボリュームを再マウント済み、DB ヘルスチェック通過」を SRE グループへ送り、イベントのタイムラインを添付する。
**エージェントがない場合の苦境**：エンジニアは `Multi-Attach error` に怯える——この語自体が「下手に弄ると二重書き込みでデータが吹き飛ぶ」という警告を帯びているため、手を出す勇気が出ず、まず Longhorn のドキュメントをめくり、それから会議を開いて旧ノードが本当に死に切ったかを確認、30分が過ぎても Pod はまだ倒れている。
**効果**：スタックボリュームの解除 **MTTR 35分 → 70秒**；ステートフルデータベースの復旧時間が40分超から2分以内へ圧縮。
> 💡 珠玉のひとこと
> 「`Multi-Attach error` の恐ろしさはエラー自体ではない。『旧ノードはいったい死に切ったのか』が確信できないことだ——そしてこれを確認すること、それこそエージェントがお前に代わって担うべき仕事なのだ。」

> 🔍 上級者の講評──道はどこにあるか
> この道は「ステートフルワークロードの自己治癒」へ通じる、K8s 運用における最後の、そして最も硬い骨だ。難点はすべてあの一句「まず安全前提を検証する」にある：孤児 VolumeAttachment の掃除は、前提判断さえ誤れば二重書き込みでデータを破壊する高危険動作であり、エージェントの価値は『掃除する勇気』ではなく、『掃除できると確認しきるまでの勇気』にある。スケール化した後、エージェントには CSI ベンダー(Longhorn/Rook/EBS)をまたぐ統一されたボリューム状態の抽象が必要となる。さもなくばストレージバックエンドを替えるたびに、この自己治癒ロジックを一から書き直さねばならない——標準化こそ、この道の最大の障害となるだろう。

## シナリオ26　MySQL大テーブルへのオンライン索引追加がマスターDBをテーブルロックさせる事態のローリング回避
**背景**：コア取引DBの8億行の大テーブル `orders` について、PMが緊急で照会用索引の上線を要求した。
**問題**：あるエンジニアが手早さを求め、マスターDBで直接 `ALTER TABLE ... ADD INDEX` を走らせた。MySQL 8.0 は Online DDL を謳うものの、このテーブルの DDL は metadata lock の昇格を引き起こし、以降 `orders` へのすべての読み書きが**ことごとくキュー待ち**となった。`SHOW PROCESSLIST` の `Waiting for table metadata lock` が3,000件まで積み上がり、マスターDBの QPS は5万から800へ半減、注文ページがぐるぐる回り始めた。
**必要なスキル**：Online DDL の仕組みと制約、Metadata Lock チェーン分析、gh-ost の cut-over 原子性と失敗モード、binlog replay/DML buffer 監視、変更ウィンドウのスケジューリング。
**オープンソースツール**：MySQL、gh-ost、pt-online-schema-change(Percona Toolkit)、Orchestrator。
**活用されるエージェントの特性**：ロブスターは `Waiting for table metadata lock` のカウント急増 + 1本の長寿命 DDL 接続が MDL を保持しているのを検知し、ClawHub の `ddl-guardian` スキルを実行する。それは**真っ先に止血する**：そのネイティブ ALTER 接続を kill して MDL 雪崩を解除する；続いて gh-ost に切り替えて再オーケストレーションする——シャドウテーブル + binlog 再生でロックなしに履歴データを流し込み、その間 row-copy と binlog apply の2本の流れを並走させる。だがロブスターは gh-ost を「`--max-load` を1つ設定すれば枕を高くして眠れる」ブラックボックスとは扱わず、3つの現実的なリスクに正面から対処する：
> **(1) cut-over のその瞬間はやはりロックする**——gh-ost の cut-over は `LOCK TABLES` + 原子的 RENAME でシャドウテーブルを切り替えるが、この一瞬は元テーブルに対し**排他的 MDL であり、典型的には数十から数百ミリ秒**(テーブルが熱いほど in-flight query の排出を待つ時間が長くなる)。そこでロブスターは `--cut-over-lock-timeout-seconds=3` を設定する：ロックを取れなければ**自動的に今回の切り替えを諦め、元テーブルは無傷、後で再試行する**のであって、オンラインリクエストを詰まらせるまで強引に待ち続けたりはしない。
> **(2) `--max-load` で運に賭けず、時機を選んで切り替える**——`--max-load Threads_running=50` のこの50は魔法の数字ではなく、当該DBの履歴で「`Threads_running` がこの値を超えると明らかな競合(contention)が出現する」p95 から逆算した閾値であり、しかもそれは**row-copy のスロットリングだけ**を制御し、cut-over のロック待ちには関与しない。そこでロブスターは `--postpone-cut-over-flag-file` を取り付ける：row-copy が完走しても**自動では切らず**、cut-over を flag file の背後に留め、自身がマスターDBの負荷曲線を読み続け、本物の谷間(`Threads_running` の低下、長トランザクションなし、binlog に突発なし)を待ってから flag を削除して切り替えを発動する——**時機を選んで切り替える方が、`--max-load` でランダムな瞬間に賭けるよりはるかに安全だ**。理想を言えば、変更全体を直接オフピークウィンドウに回して走らせ、そもそもピークで賭けないことだ。
> **(3) replay/DML buffer を監視してライブロックを防ぐ**——履歴データを流し込む間、オンライン DML は絶え間なく新しい binlog を生成して apply を要する；もしこの時、業務 DML が急増して apply 速度が生成速度に追いつかなければ、gh-ost の再生待ち buffer は膨張し続け、永遠に cut-over の条件に収束せず、**ライブロック**を形成する。ロブスターは gh-ost の `Lag`(シャドウテーブルの遅延秒数)と binlog apply の滞留を見張り、遅延が拡大し続ければ**自ら row-copy 速度をさらに下げて**帯域を replay へ譲るか、あるいは直接一時停止して DML の洪水ピークが過ぎるのを待つ。
>
> Multi-Channel Gateway は「ネイティブ DDL を中止済み、gh-ost のバックグラウンド実行に切り替え、cut-over に3sタイムアウト+手動/谷間での時機選択切り替えを設定、replay 遅延を監視中、オフピーク完了見込み」を通報し、あの手早いエンジニアを@して事後の指導を行う。
**エージェントがない場合の苦境**：DBAはマスターDBの雪崩を見ても、あの DDL を軽率に kill する勇気が出ず(中途半端なものが残るのを恐れて)、5分ためらううちに取引で数十万を損失する；gh-ost に切り替えたとしても、新人はよく「`--max-load` を設定すれば万全」と思い込み、結果 cut-over がピークにぶつかって大量の in-flight query にスタックされたり、DML 急増で replay が永遠に追いつかずに一晩中ライブロックしたりする。
**効果**：MDL 雪崩の止血 **18分 → 35秒**；8億行の索引が cut-over の数百ミリ秒という制御可能なロックの代償で、オフピークに時機を選んで完了し、replay はオーバーフローせず、ライブロックもせず、マスターDBの QPS はもはや影響を受けない。

> 💡 珠玉のひとこと
> 「『Online DDL』という言葉の最大の罠は、それがすべてのテーブル、すべての時刻に対して online だと思い込ませることだ——そして gh-ost ですら真の『ゼロロック』ではない。それは避けられないあのロックを、お前が時機を選べ、諦められ、再試行できる数百ミリ秒へ圧縮しただけなのだ。健全性はロックを撲滅することにあるのではなく、ロックをお前が選んだ瞬間に発生させることにある。」

> 🔍 上級者の講評──道はどこにあるか
> この事例はロブスターを「変更ゲートキーパー(Change Gatekeeper)」の役割へ押し出す——理想の終局は、危険なネイティブの大テーブル DDL がマスターDBに入る前に阻止され、自動的に gh-ost フローへ書き換えられることだ。だが正直に向き合わねばならない：cut-over のあの MDL ロックは**消去できず、時機を選べるだけ**であり、「最低の谷間はどこか、選んだ途端に一波の流量が来ないか」は本質的に未来の数百ミリ秒に対する賭けである——`--postpone-cut-over-flag-file` はこの賭けを人/エージェントの時機選択へ返すもので、`--max-load` でランダムな瞬間に賭けるよりは良いが、それでもゼロリスクではない。さらに深いグレーゾーンは replay ライブロックだ：業務 DML が apply 能力を持続的に上回るとき、gh-ost は**永遠に完走できない**かもしれない。このとき唯一誠実な答えは「もっと減速する」ではなく、「このテーブルはこの時間帯にはオンライン変更に適さない、オフピークのメンテナンスウィンドウを組んでくれ」と認めることだ——賭けの卓を片付ける方が、賭けの腕を磨くより安全である。エージェントがスキーマ変更を確実に引き受けられるようになれば、DBAの役割は実行者から戦略の審査者へ昇格する；そしてマスターDB接続を kill するこの種の権限をエージェントに委ねるには、依然として明確に書かれた授権境界が必要だ。

## シナリオ27　Redisキャッシュ雪崩(Cache Avalanche)がマスターDBを撃ち抜く多段サーキットブレーカー
**背景**：高トラフィックのコンテンツサイト。Redis クラスタがホットデータのキャッシュを担い、TTLは一律1時間に設定、背後は単一の MySQL マスターDB。
**問題**：18:00ちょうど、同時に書き込まれた一群のキャッシュ key が**同一秒に一斉に期限切れ**となり、瞬間的に数十万のリクエストがすべて MySQL へ突き抜けた。マスターDBの接続数は1秒以内に200から上限の2,000へ突進、`Threads_running` は400まで急騰、CPU 100%となり、キャッシュ撃ち抜きがキャッシュ雪崩へ発展した——MySQLが接続拒否を始め、まだ期限切れになっていないキャッシュの埋め戻しまで道連れにスタックさせ、サイト全体が死のスパイラルに入った。
**必要なスキル**：キャッシュ失効モード(雪崩/撃ち抜き/貫通)の識別、ホット key の探測、相互排他リビルド(mutex rebuild)、バックエンド過負荷保護。
**オープンソースツール**：Redis、`redis-cli --hotkeys`、Sentinel、Sentinel/Resilience4j 風サーキットブレーカー(ここでは envoy で流量制限)。
**活用されるエージェントの特性**：ロブスターは「MySQL接続数の急増 + Redis miss rate の急騰」という二重信号で起動され、ClawHub の `cache-avalanche-breaker` スキルを実行、これが「集団 TTL 同時失効」型の雪崩だと即座に判定する。それはコンビネーションを繰り出す：接続層(Envoy)で DB へ突き抜けるリクエストに**キュー待ち流量制限を起動**し、各ホット key につき1つのリクエストだけをリビルドへ通し(分散相互排他ロック)、残りは短時間 stale キャッシュを返す；ローカルスクリプトは埋め戻す key にバッチで**ランダムなジッターTTL**(3600±300s)を注入し、次回また同期して期限切れになるのを防ぐ。サブエージェントはマスターDBの `Threads_running` が低下した後、段階的に流量制限を緩める。Multi-Channel Gateway は「DB に相互排他リビルドの流量制限を起動済み、TTL にジッターを追加済み」を当番グループへ同期する。
**エージェントがない場合の苦境**：SREは MySQL 接続のあふれを見てまず接続プールを拡張しに行き、結果としてより多くのリクエストを呼び込んでマスターDBを完全に圧死させる；20分ほど回り道してようやく根本原因が Redis のちょうどの時刻における集団期限切れにあると気づく。
**効果**：雪崩からサーキットブレーカー止血まで **MTTR 20分 → 40秒**；マスターDBの過負荷窓口が12分から30秒へ短縮、さらに根本から「ちょうどの時刻の集団期限切れ」の再発を解消した。

> 💡 珠玉のひとこと
> 「キャッシュの善意はマスターDBの弾除けになることにある。だがすべてのキャッシュが同一秒に一緒に倒れる約束をしたとき、それらはマスターDBを押し潰す同一の軍隊と化す。」

> 🔍 上級者の講評──道はどこにあるか
> この道は「層をまたぐ(キャッシュ↔データベース)協調的過負荷保護」を指し示す——Redis だけ、あるいは MySQL だけを見ても救えない。エージェントの独自の価値は、両層の信号を同時に握って統合的な意思決定を下すことにある。エンジニアリング上の硬い骨は「stale を出すか、リクエストを遮るか」の取捨であり、それは業務のデータ鮮度に対する許容度と強く結びついている。エージェントには per-endpoint の「許容できる staleness」リストが必要だ。さらに先を見据えれば、キャッシュ TTL に自動でジッターを注入するこの種の「根治動作」が一度エージェントによって常態的に実行されれば、運用は『雪崩の消火』から『雪崩を物理的に発生不可能にする』へ進化する——これこそ自動化の終点である。

## シナリオ28　誤削除データのポイントインタイムリカバリ(PITR)とbinlogの精密再生
**背景**：運営バックオフィスのあるスクリプトが WHERE 条件を書き間違え、本番DBで `UPDATE users SET status=0` の**限定条件を漏らし**、全テーブル200万ユーザーがワンクリックで権限停止された。
**問題**：09:12に事故発生、カスタマーサポートの電話が3分以内に鳴り止まなくなり、200万ユーザー全員がログインできなくなった。前夜のフルバックアップから直接復元すれば午前中まるまる一回分の実際の業務書き込みを失うことになり、その代償は受け入れがたい；「この一回の誤操作だけをロールバックし、残りすべての正常な取引を保持する」外科手術的な復旧を実現せねばならない。
**必要なスキル**：ポイントインタイムリカバリ(PITR)の原理、binlog イベントの解析と逆生成、シャドウDBによる検証、データ損失最小化の復旧。
**オープンソースツール**：MySQL、Percona XtraBackup、my2sql/binlog2sql、mydumper。
**活用されるエージェントの特性**：ロブスターは「単一SQLの影響行数 = 全テーブル」という異常監査ルールで起動され、ClawHub の `pitr-surgeon` スキルを実行する。それはまずあの災害SQLの binlog 中の正確な GTID とタイムスタンプ(09:12:07)を特定し、binlog2sql で**ロールバックSQLを逆生成**(`status=0` をトランザクション前の元の値へ復元)、そして隔離されたシャドウDBでまず再生して行数とサンプリング照合に誤りがないことを検証してから、マスターDBで補償を実行する。全過程で**9:12以降の他の正常な書き込みには一切触れない**。ローカルスクリプトは「誤操作の影響リスト + ロールバック diff」の完全な一式を生成する。Multi-Channel Gateway は「誤削除 GTID を特定済み、シャドウDB検証通過、ロールバック実行の人手による最終承認待ち」を DBA 責任者へ送り、**人間の最終確認権を保持する**。
**エージェントがない場合の苦境**：DBAは「フルバックアップで半日分のデータを失う」と「手書きのロールバックSQLでまた間違えるのが怖い」の間で苦悶し、手動で binlog をめくってあのSQLの位置を探すだけで40分を費やし、その間200万ユーザーは扉の外に締め出され続けた。
**効果**：誤削除の特定から実行可能なロールバックまで **40分超 → 90秒**；データ損失は「半日の業務」から「ゼロ」へ低下、復旧精度は単一トランザクション級に達した。

> 💡 珠玉のひとこと
> 「WHERE を書き漏らした1本の UPDATE が、0.3秒で200万人の朝を壊せる——データベースはお前が手を滑らせたかどうかなど決して問わない。それはただ忠実に、お前の傲慢を実行するだけだ。」

> 🔍 上級者の講評──道はどこにあるか
> この事例の最も核心的な設計は「エージェントがロールバックを準備し、人間が確認ボタンを押す」——それは明確な信頼境界を引いた：**生成と検証は自動化できるが、破滅級の補償の実行には人間の署名が必須**。この道は「可逆運用」の理想を指し示す：あらゆる書き込み操作に、いつでも実行可能な逆向きの補償を付帯させること。エンジニアリング上の難点は binlog 逆生成の完全性(トリガー、カスケード、JSON フィールドはいずれも落とし穴)、そしてシャドウDB検証が事故の窓口内に完了できるほど速いことにある。この能力一式が成熟すれば、DBAが誤削除に直面したときの心構えは『災難』から『取り消し(Undo)』へ変わる——そしてこれこそ、エージェントが人間の運用に与える最大の贈り物である：不可逆を、再び可逆へ変えること。

## シナリオ29　分散取引台帳のデータ不整合に対する突合と結果整合性の修復
**背景**：マイクロサービスアーキテクチャの下、注文サービスと在庫サービスがそれぞれ自前のDBを持ち、ローカルメッセージテーブル + MQ で結果整合性を取り、理論上「注文成立は必ず在庫を引く」。
**問題**：ある時の MQ broker のローリング再起動中、一部の「在庫を引く」メッセージが配送に成功しないまま、ローカルメッセージテーブルの補償タスクも bug でリトライされず、**2,317件の「注文は成立したが在庫は引かれていない」グレーデータ**が発生した。帳簿上の在庫が実際より多く、売り越しリスクが蓄積しつつあり、しかもこの種の不整合は**エラーも出さず、アラートも出さない**。それはただ2つのDBの間に静かに横たわり、いつかの日に売り越し事故として爆発するのを待っている——これこそ分散システムの最も陰険なグレー失敗である。
**必要なスキル**：結果整合性の突合(Reconciliation)、冪等補償の設計、サービスをまたぐデータ diff、グレー失敗の探測。
**オープンソースツール**：PostgreSQL/MySQL、Debezium(CDC)、Apache Kafka、自前構築の突合 job。
**活用されるエージェントの特性**：ロブスターは ClawHub の `eventual-consistency-auditor` スキルを実行し、定時に CDC ストリームで両DBの「注文—在庫」イベントを双方向 diff し、合わない2,317件のレコードを能動的に拾い出す(爆発を待つのではなく)。それは各件について**冪等補償**を行う：注文が確かに有効であることを照合した後、冪等キー付きの在庫引きを改めて一度発動し、重複引きを避ける。diff 中の「注文側は無効だが在庫はすでに引かれている」逆向きの不整合については、返戻補正伝票を生成する。サブエージェントは自動判定できない難案件(注文ステータス自体が矛盾しているなど)を個別に分類保管する。Multi-Channel Gateway は「突合で2,317件の不整合を発見、自動修復2,290件、27件は人手要」を日報にまとめて財務と業務 owner へ送る。
**エージェントがない場合の苦境**：そもそも不整合があると誰も知らない——ある売れ筋商品が売り越しとなり、ユーザーが代金を払ったのに発送できず、ようやく3週間前のあの MQ 再起動を掘り起こし、人手でSQLを書いて突合し、まる2日かけて拾い出すまでは。
**効果**：グレー不整合が「事後3週間でようやく爆発」から「T+1で能動的に発見」へ；自動修復率98.8%、売り越し事故ゼロ；人手突合が2日 → バックグラウンドで無感運行へ。

> 💡 珠玉のひとこと
> 「分散システムで最も危険なデータは、誤ったデータではない。エラーも出さず、アラートも出さず、2つのDBの間に静かに横たわって爆発を待つ、あの『合わないもの』だ。」

> 🔍 上級者の講評──道はどこにあるか
> これは本章で最も「グレー失敗(Grey Failure)」の哲学を体現する事例だ——故障はクラッシュではなく、2つのDBが各々正常なのに、合わせると嘘をつく。ここでのロブスターの役割は『消防士』から徹底的に『常駐監査員』へ転じる。これはエージェントの最も価値ある未来形態を指し示す：**能動巡検であって受動アラートではない**。エンジニアリング上の真の難題は冪等補償の正しさにある——補償自体が冪等でなければ、エージェントは修復者から増幅器へと変わってしまう。スケール化した後、突合ルールの維持(何をもって『整合』とするか)は、業務とエージェントの間で持続的に交渉される生きた契約となる。そしてエージェントに『返戻補正伝票』のような金銭に関わる補償を自動実行する権限を与えることは、信頼境界が最も遠くまで押し広げられ、最も監査の痕跡を残すべき一歩となる。

## シナリオ30　時系列データベース(TSDB)カーディナリティ爆発(Cardinality Explosion)のラベル統治
**背景**：可観測性プラットフォームが Prometheus/VictoriaMetrics で全社のメトリクスを保存しているが、あるチームが新サービスを上線した際に `user_id`、`request_id` を label にした。
**問題**：02:50、監視自身を監視するアラートが鳴る：VictoriaMetrics の active time series が30分で800万から **1.2億** へ暴騰、メモリ OOM の連鎖再起動が起き、クエリ遅延が200msから30秒へ急騰、アラートシステム全体——本来最後に倒れるべきこのシステム——が自ら盲目になった。根本原因は高カーディナリティ label により一意な `request_id` ごとに独立した時系列が1本生成され、カーディナリティが組み合わせ爆発を起こしたことだ。
**必要なスキル**：時系列データモデルとカーディナリティの原理、高カーディナリティ label の帰属分析、メトリクスの relabel/drop 統治、TSDB 容量保護。
**オープンソースツール**：VictoriaMetrics/Prometheus、`vmui`/TSDB status API、Grafana、vmagent relabel。
**活用されるエージェントの特性**：ロブスターは「active series 増加速度の異常 + TSDB メモリ水位」で起動され、ClawHub の `cardinality-buster` スキルを実行、TSDB status API の top cardinality レポートを照会し、40秒以内に犯人 metric の `request_id` label へ帰属分析する。それは**即座に止血する**：vmagent/Prometheus の relabel_config に動的に `labeldrop`/`drop` 規則を1本下発し、当該高カーディナリティ label の取り込みを遮断、カーディナリティの増加を止めてメモリを安定回復させる；すでに書き込まれた爆発した系列には加速失効を取り付ける。ローカルスクリプトは「Top 10 高カーディナリティ metric/label」リストを生成する。Multi-Channel Gateway は「犯人 label を drop 済み、active series が1.2億で増加停止、X時間で低下見込み」をプラットフォームグループへ送り、`request_id` を label にしたあのチームを@してメトリクス設計規範のリンクを添付する。
**エージェントがない場合の苦境**：監視プラットフォーム自身が OOM し、SREは Grafana すら開けず、いったいどのメトリクスがカーディナリティ爆発を起こしたのか調べられず、盲目的にメモリを拡張して対症療法するしかない；手動で犯人 label を特定した頃にはすでに1時間以上が過ぎ、その間、全社のアラートが「失明」していた。
**効果**：カーディナリティ爆発の帰属分析と止血 **MTTR 60分超 → 50秒**；監視システム自身の崩壊による全社「アラート失明」の窓口を回避。

> 💡 珠玉のひとこと
> 「監視システム自身が1つの `request_id` ラベルで膨れ上がって倒れたとき、お前はようやく悟る：見張る者もまた見張られる必要があると——そして最初に統治されるべき高カーディナリティは、往々にしてエンジニアの何気ない一筆なのだ。」

> 🔍 上級者の講評──道はどこにあるか
> この事例の妙味は、被害者がまさに監視それ自体である点にある——それは「誰が監視者を監視するのか」というメタ問題に我々を直面させ、エージェントはちょうどこの盲点に立って手を打てる。この道は「可観測性の自己統治」を指し示す：エージェントは消火するだけでなく、高カーディナリティ label の設計アンチパターンを開発フローへ逆向きに押し返す(commit 前に阻止する)。エンジニアリングの難題は `drop` label が破壊的な決定である点にある——それはある次元の可観測性を永久に失わせるため、エージェントは「暴走した request_id」と「業務が真に必要とする高カーディナリティ次元」を見分けねばならない。スケール化した後、メトリクスの『カーディナリティ予算』はコスト予算のように配分と責任追及を要するようになり、そしてエージェントは、アラート伝票を発行しながら、黙ってお前のために予算を守る、そういう存在となるだろう。
