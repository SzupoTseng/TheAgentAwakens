# 第8章　可観測性：目に砂を入れたまま戦うな

## シナリオ31　Prometheus メトリクスのカーディナリティ爆発(High Cardinality)に対する動的プルーニング
**背景**：1,800 のマイクロサービスにまたがる Prometheus フェデレーションクラスタ。毎秒およそ 2,400 万の active series を取り込んでおり、TSDB はメモリの限界ぎりぎりで持ちこたえている。
**問題**：あるチームが metric label に `user_id` と `request_uuid` を詰め込んだ結果、三時間で active series が 2,400 万から 1.9 億へと急騰し、Prometheus の head block は 220GB の RAM を食い尽くした。OOMKilled 後の再起動には WAL の再生に 17 分を要する——この 17 分間、組織全体のアラートルールはすべて視力を失い、どのダッシュボードも点灯しない。
**必要なスキル**：PromQL によるカーディナリティ分析、TSDB 内部構造の理解、relabel_config の設計、キャパシティプランニング。
**オープンソースツール**：Prometheus、`promtool`、Grafana Mimir、cardinality-exporter。
**活用するエージェントの特性**：ロブスター(🦞) OpenClaw は `prometheus_tsdb_head_series` の二階微分を購読し、傾きに異常が出ると自動で `promtool tsdb analyze` と TSDB の `/api/v1/status/tsdb` を実行する。サブエージェントは 30 秒以内に爆発の発生源を `payment-gw` の `request_uuid` label に特定し、ローカルで `metric_relabel_configs` の drop ルールを生成する PR を作成、さらに Multi-Channel Gateway を通じて「まもなく回路が焼き切れる label のトップ3」をヒートマップ付きで Slack とオンコールグループへ同期投稿する。
**エージェントがいない場合の苦境**：人間はまず RAM が膨らんでいることに気づき、手動で `/api/v1/status/tsdb` を辿って top-10 series をめくり、肉眼で label を突き合わせ、relabel rule を書き、config reload を待つ——たいていは調査を始める前に爆発はとっくに OOM を引き起こしている。
**効果**：カーディナリティ暴走の検知からプルーニング PR までが平均 25 分から 40 秒へ短縮。TSDB の OOM 事故は四半期あたり 4 件から 0 件へ。

> 💡 珠玉のひとこと
> 「カーディナリティ爆発はディスクの問題ではなく、『誰かが無限の次元を無料だと思い込んでいる』という認知の問題だ。メトリクスの価値はそれが集約できる点にある。集約できない次元とは、請求書を観測のふりをさせているだけだ。」

> 🔍 上級講評──道はどこにあるか
> この事例はロブスターを「メトリクス・ガバナンスの門番」という道へと押し出す。爆発後にプルーニングするだけでなく、CI 段階で高カーディナリティ label のコミットを差し止めるのだ。実装上の難題は信頼境界にある——label を自動で drop することは、他チームに代わって「この次元は観測する価値がない」と決めることに等しく、重要な次元を誤って drop すれば、かえって新たな盲点を生む。今後ロブスターに必要なのは「可逆で、交渉を伴うプルーニング」だ。まずダウンサンプリングし、次にマークを付け、owner に確認の猶予を与える——いきなり切り捨てるのではなく。

## シナリオ32　APM 性能退化(Performance Regression)に対するマイクロサービス・ブラインドテストの根本原因追跡
**背景**：14 ホップにわたる発注クリティカルパス。6 チーム・3 種類の言語をまたぎ、APM は OpenTelemetry + Tempo を用いる。
**問題**：リリース後、P99 レイテンシが 180ms から 540ms へ漂流した。だが各チームが自分のサービスのダッシュボードを見るとどれも「緑」だ——退化が各ホップに均等にならされ、どの単一サービスも自分の SLO の閾値を超えていないからだ。これは典型的なグレー障害で、合計は爆発しているのに、犯人は誰もいない。
**必要なスキル**：分散トレーシング分析、統計的差分比較(diff profiling)、サービス横断のベースライン構築、Apdex の読解。
**オープンソースツール**：OpenTelemetry、Grafana Tempo、Jaeger、Pyroscope。
**活用するエージェントの特性**：ロブスターは「リリース前後それぞれ 10,000 本の trace」に対して span レベルの分位点 diff を行う。サブエージェントは、退化が単一の span にあるのではなく、各ホップに新たに追加された `auth-sidecar` のインターセプタにあることを突き止める——mTLS 証明書の検証がキャッシュから同期 RPC へ変わり、各ホップで +25ms になっていた。ロブスターはローカルで Pyroscope のフレームグラフ diff を回して裏付けを取り、CPU は増えておらず wait time が増えていることを示し、その sidecar を変更したプラットフォームチームをグループ内で @ し、「14 ホップ × 25ms」の累積証拠を添える。
**エージェントがいない場合の苦境**：6 チームが事故ブリッジ上で三時間にわたり責任のなすり合いをし、誰もが「自分のサービスは退化していない」と証明できてしまい、全サービスを横断するあの sidecar を見に行く者は誰もいない。
**効果**：チーム横断の押し付け合いの時間が平均 3 時間から 8 分へ収束。退化の特定精度は単一のコミットまで。

> 💡 珠玉のひとこと
> 「全員のダッシュボードが緑なのにシステムは遅くなっている——そのとき問題は必ず『誰も所有していない層』に潜んでいる。横断的関心事とは、組織の盲点が物理的に現像されたものだ。」

> 🔍 上級講評──道はどこにあるか
> これはロブスターを「全リンク統計家」という道へと指し示す。根本原因分析を「閾値超過のサービスを探す」から「閾値超過の分布を探す」へと格上げするのだ。先を見据えた工学的課題は相関ではなく因果である——span diff はどこが遅くなったかを教えてくれるが、それが原因だと証明はできない。次の一歩としてロブスターは変更イベントストリーム(deploy/flag/config)を取り込み、レイテンシ分布の変曲点をタイムライン上の変更に揃える必要がある。そうしてはじめて「相関による告発」から「信頼に足る因果帰属」へと進める。

## シナリオ33　ログレベル(Log Level)暴走に対する動的なオンライン降格
**背景**：本番クラスタは 600 個の Pod。標準的な logback/zap を用い、ログは Fluent Bit 経由で Loki へ送られる。
**問題**：あるトラブルシュート時、誰かがホットパス上のサービスの log level を INFO から一時的に DEBUG へ変え、戻し忘れた。QPS のピーク時、そのサービスは毎秒 90 万行のログを吐き出し、Loki ingester は 429 を叩き出し、全社のログクエリがタイムアウトし始めた——さらに悪いことに、本当に有用な ERROR が DEBUG の海に呑み込まれ、まったく検索できなくなった。
**必要なスキル**：ログフレームワークの動的設定(actuator/logging endpoint)、Loki の rate limit チューニング、ログ量の帰属分析、ホットパスの識別。
**オープンソースツール**：Loki、Fluent Bit、Spring Boot Actuator、Vector。
**活用するエージェントの特性**：ロブスターは Loki の `distributor_bytes_received_total` に階段状の跳躍が現れるのを監視する。サブエージェントは LogQL を使い 90 秒以内に大量送出を単一サービスの単一 logger に帰属させ、そのサービスの actuator `/loggers` endpoint を呼び出して当該 logger をオンラインで INFO へ戻し(再起動なし)、Multi-Channel Gateway を通じて「誰のレベルを、なぜ、いつ自動で復旧するか」を通知し、14:02 に DEBUG へ変更したのは誰かという監査記録を添える。
**エージェントがいない場合の苦境**：オンコール担当は慌てふためいてどのサービスが噴出しているのかを探し、見つけてからも owner と調整して設定を戻し、リリースフローを通さねばならない——その間にログシステムはとうに爆発しており、「誰が level を変えたのか」というログ自体すら引けない。
**効果**：ログストームの止血が平均 22 分から 90 秒へ。ERROR の検索可能率がストーム中の 12% から 99% へ回復。

> 💡 珠玉のひとこと
> 「DEBUG はトラブルシュートのサーチライトだ。だがサーチライトを消し忘れれば、照らし出すのは自分が墜落する滑走路だ——可観測性の対極はログがないことではなく、ログが多すぎてシグナルが消えることだ。」

> 🔍 上級講評──道はどこにあるか
> これはロブスターを「一時変更の番人」という道へ導く。デバッグ目的のオンライン変更はすべて TTL を持つべきで、ロブスターがするのは人間の物忘れを下支えすることだ。実装上の信頼境界は微妙である——ロブスターがトラブルシュートの最中に誰かの DEBUG を戻すと、まさにその人が見ていた手がかりを断ち切ってしまうかもしれない。今後の解は直接降格ではなく「交渉式 TTL」だ。危険な level 変更を検知したらまずマークしてカウントダウンし、元の操作者に維持や延長の選択肢を残す。越権の止血はシステムが回路遮断に迫ったときだけ発動する。

## シナリオ34　コンテナログ暴噴によるホストマシンのディスク崩壊に対するリアルタイム清掃
**背景**：ベアメタルの Kubernetes ノード。コンテナログはホストの `/var/lib/docker/containers` に書き込まれ、log rotation の上限が設定されていない。
**問題**：クラッシュループ(CrashLoopBackOff)に陥った Pod が毎秒 stderr へスタックトレースを噴き出し、単一コンテナが 8 時間で 480GB を書き尽くし、ホストの root パーティションが 100% に達した——kubelet は書き込み能力を失い、ノードは NotReady となり、その上の 30 個の無実の Pod が連座して退去させられ、雪崩が隣接ノードへ広がり始めた。
**必要なスキル**：Linux ファイルシステムと inode の診断、kubelet/containerd の動作機構、ディスク圧迫による退去ポリシー、安全なログ切り詰め。
**オープンソースツール**：containerd、`logrotate`、node-problem-detector、ncdu。
**活用するエージェントの特性**：ロブスターの node-exporter 番兵は `node_filesystem_avail_bytes` が 5% を割り込むと発火する。サブエージェントはノードにログインして `du`/`ncdu` を回し、20 秒以内に元凶コンテナの log ファイルをロックオンし、ローカルスクリプトで `truncate -s 0` を使って安全に空にする(`rm` ではなく——fd リークによって領域が解放されない事態を避けるため)。同時にその Pod に cordon を打ってノードを乗り換えてさらに暴れるのを防ぎ、グループに「どのファイルを清掃し、どれだけ解放し、なぜ truncate を選んだか」を通報する。
**エージェントがいない場合の苦境**：オンコール担当は真夜中に PagerDuty に叩き起こされ、SSH で入って `df -h` で 100% を目にし、慌てて書き込み中のログファイルを `rm` してしまい、領域はまったく解放されず(fd がまだ握っている)、ノードは死に続け、雪崩は三ノードへ拡大する。
**効果**：ディスク満杯事故の止血が平均 18 分(人間が正しい止血手法を見つける時間を含む)から 35 秒へ。連座退去させられた Pod 数が平均 30+ から 0 へ。

> 💡 珠玉のひとこと
> 「夜中の三時にログを消すとき、`rm` と `truncate` の違いは『ノードの蘇生』と『ノードの仮死』の違いだ——SRE の筋肉記憶は、雪崩を一度また一度と経験して買い取ったものだ。」

> 🔍 上級講評──道はどこにあるか
> この道は「資源の崖の手前の反射弧」だ。ロブスターがするのは、睡眠不足の人間が最も間違えやすい類の操作である。先を見据えたリスクは自動止血の「巻き添え被害」にある——truncate したログこそが、事後 RCA の唯一の証拠だったかもしれない。今後ロブスターがすべきは単なる空にすることではなく「まずサンプリングしてアーカイブしてから切り詰める」ことだ。空にする前に末尾の数万行をオブジェクトストレージへ退避させ、止血と証拠保全を二者択一にしない。これこそが、人間が root 権限をエージェントに委ねる勇気を持つための前提だ。

## シナリオ35　分散トレーシングのフレームグラフ(Flame Graph)によるチーム横断の押し付け合いの終結
**背景**：22 ホップの検索リクエストチェーン。フレームグラフは 7 チームにまたがり、大事故のたびに「戦況ブリッジ」を開いて大勢を呼び集めねばならない。
**問題**：検索の P99 が散発的に 3 秒へ跳ね上がる。事故ブリッジ上の 18 人が各自勝手なことを言い、フレームグラフは幅広く深すぎて全貌を読める者は誰もおらず、「自分じゃない」という反響が会議室で 90 分こだまし続け、実際に 2.4 秒を占めていたその span は、名前が `internal_call_42` であるがゆえに全員に無視された。
**必要なスキル**：フレームグラフのクリティカルパス(critical path)読解、span の帰属識別、テールレイテンシのサンプリング分析、チーム横断の責任マップ維持。
**オープンソースツール**：Jaeger、Grafana Tempo、Parca、speedscope。
**活用するエージェントの特性**：ロブスターは遅い trace に対して自動でクリティカルパスを算出する(最も幅広い span ではなく、本当に総所要時間を詰まらせているチェーン)。サブエージェントは `internal_call_42` を service ownership map を通じて「インデックスチームのキャッシュウォームアップロック」へと解決し、それが 2.4s / 3.0s = 80% の責任比率を占めると計算し、そのままグループでそのチームの owner を @ し、無関係な span をすべて除いてクリティカルパスだけを残した簡潔なフレームグラフを添える。事故ブリッジに人が揃いきる前に、犯人はすでに名指しされている。
**エージェントがいない場合の苦境**：18 人がブリッジ上で順番に潔白を証明し合い、フレームグラフは共有画面で右往左往して誰も読み取れず、MTTR の半分が「誰が責任者か」を探すこと自体に食い尽くされる。
**効果**：チーム横断の帰属が平均 90 分から 5 分へ。事故ブリッジの平均参加人数が 18 から 4 へ(本当に関係する人だけを呼ぶ)。

> 💡 珠玉のひとこと
> 「フレームグラフで最も危険な span は、往々にして最も退屈な名前のものだ——`internal_call_42` と呼ばれるものは、誰もそれに名を付けたがらなかったからこそ、誰もそれに責任を負いたがらないのだ。」

> 🔍 上級講評──道はどこにあるか
> これはロブスターの最も政治的破壊力を持つ道、「自動帰属者」を指し示す。押し付け合いを終わらせる技術の核心は、フレームグラフを「視覚」から「クリティカルパス上の責任ベクトル」へと変えることだ。だがここでの信頼境界は極めて敏感である——エージェントがグループ内である チームを犯人と名指しするとき、それは反論される代償を引き受けねばならない。今後この道を通すには、ロブスターの帰属に「再生可能な証拠パッケージ」(trace id + span + ownership の出所)を添え、自らの帰属に信頼区間を示さねばならない。名指しは権力であり、監査可能な名指しこそが制度である。

## シナリオ36　アラートストーム(Alert Storm)の重複排除と根本原因の畳み込み
**背景**：4,000 本のアラートルールを持つ監視体系。Alertmanager は PagerDuty と複数のオンコールグループに接続している。
**問題**：コアデータベースのプライマリノードが故障し、連鎖的に 312 本のアラートが 90 秒以内にオンコールグループへ流れ込んだ——コネクションプール満杯、上流タイムアウト、リトライストーム、キャッシュ貫通、ディスク IO 急騰……オンコール担当のスマホは振動で熱くなり、本当の根本原因「DB プライマリノードがダウンした」という一本は、187 番目の通知に埋もれて誰の目にも入らない。これはアラートシステム自身が作り出したグレー障害だ。
**必要なスキル**：アラートトポロジのモデリング、因果の畳み込み(causal correlation)、抑制ルール(inhibition)の設計、オンコールの認知負荷管理。
**オープンソースツール**：Alertmanager、Karma、Keep、Grafana OnCall。
**活用するエージェントの特性**：ロブスターは 90 秒のウィンドウ内で 312 本のアラートをサービス依存グラフに基づいて因果畳み込みする。サブエージェントは 311 本がすべて「DB プライマリノード故障」の下流症状だと判定し、1 本の根本原因アラートだけを P1 へ格上げしてプッシュし、残り 311 本は展開可能な付録へ畳み込む。Multi-Channel Gateway は「根本原因 + 影響を受ける下流リスト + 推奨フェイルオーバー指令」を一度に貼り出し、その 311 本のノイズを自動で ack する。
**エージェントがいない場合の苦境**：オンコール担当は 312 本の通知の中を狂ったようにスクロールして手がかりを探し、手動 ack で親指がつるまで操作し、ようやく「DB がダウンした」と組み立て終えたときには、落ち着いてフェイルオーバーする黄金のウィンドウはとっくに閉じている。
**効果**：アラートノイズの圧縮比 312:1。ストーム開始から根本原因の特定までが平均 14 分から 50 秒へ。

> 💡 珠玉のひとこと
> 「312 本のアラートは 312 個の問題ではなく、1 個の問題の 312 通りの泣き声だ——オンコールの苦痛はそもそもアラートがないことではなく、アラートシステムが『一度の心の破れ』を三百回語ることだ。」

> 🔍 上級講評──道はどこにあるか
> この道はロブスターを「アラートの運搬人」ではなく「アラートの編集者」へと押し出す。畳み込みの本質はオンコールの認知を肩代わりして降ろすことであり、その前提は依存トポロジが十分に正確であることだ——トポロジが古くなれば、ロブスターは本当に独立した一本のアラートを誤って他人の物語に畳み込んで沈黙させてしまうかもしれない。今後の工学的要点は「トポロジの自己学習」だ。過去のアラート共起からサービス依存を逆算し、畳み込み判断には「誤畳み込みリスクスコア」を残し、高リスク時には畳み込みを減らしてでも誤殺は避ける。可観測性自動化のレッドラインは、永遠に「うるさくても見逃すな」である。

## シナリオ37　クロックスキュー(Clock Skew)によるトレース時刻の錯乱——「どの時計を信じるか」の権威的仲裁
**背景**：1,400 個のサービスが三つの AZ にまたがり、約 6,000 ノード。分散トレーシングは各ノードのローカルクロックに依存して span にタイムスタンプを打つ。NTP はそもそも**確率的同期**である：正常時でもノード間の残差には 1〜20ms のジッタがあり、これはベースラインのノイズであって故障ではない。
**問題**：ある AZ の上流 stratum-2 時刻源が静かに失われ、chrony は holdover に入りローカル水晶発振器で自走を始めた。クロックはおよそ 35 ppm でゆっくり漂流し、八時間で累積 −400ms に達した。フレームグラフには「子 span が親 span より先に終了する」という負のレイテンシが現れ始める。難しいのは：(1) 漂流は**連続的かつ単調**で、きれいな階段状の跳躍ではないため「ジャンプ検知」では捕まえられない；(2) 三つの AZ がそれぞれに漂流し、方向も幅も異なり、グローバルな真実が存在しない；(3) `node_timex_offset_seconds` 自体が node_exporter によって 15s 間隔で採取され、さらに remote_write を経て格納されるため、**採取経路自体にも秒単位の遅延とタイムスタンプがある**——信頼できない時計を使って別の信頼できない時計を測るのは、循環論法だ。
**必要なスキル**：NTP/chrony の holdover 機構、`node_timex` 各フィールドの意味、複数時刻源のフォールトトレラント仲裁(Marzullo/Chrony の falseticker 除去)、AZ 横断の相対オフセット計測、PTP との対照。
**オープンソースツール**：chrony(`chronyc tracking` / `sources -v` / `sourcestats`)、Prometheus node-exporter(`node_timex_offset_seconds` / `node_timex_maxerror_seconds` / `node_ntp_root_dispersion`)、Jaeger、OpenTelemetry、(対照基準として)PTP の `phc2sys`。
**活用するエージェントの特性**：ロブスターはまず非物理的な特徴を捉える——一群の trace に負の duration と因果逆転が現れる。サブエージェントは**いかなる単一ノードの offset の数値も直接は信じず**、時刻源の仲裁を行う：(1) 各 AZ から一組のノードを取り、chrony のヘルスシグナルを読む——`Leap status` が `Not synchronized` に変わったか、stratum が 2 から 16 へ跳ねたか、`Root dispersion` が <5ms から >200ms へ急騰したか、`sourcestats` の skew(ppm)推定誤差が 10 ppm を超えたか——これらは holdover の動かぬ証拠であり、raw offset より信頼できる；(2) 三つの AZ を二つずつ**相対オフセット計測**する(同時に到着した同一バッチの span の server/client タイムスタンプ差を使い、絶対時計ではなく)。すると AZ-B が他の二区に対して一貫して −400ms ずれており、しかも単調に拡大し続け、一方 AZ-A/C は互いに一致していることが分かる——「多数の一致」によって AZ-B を falseticker と判定する；(3) AZ-B 全体の chrony `root dispersion` が同期して急騰し、上流源の reach が 0 に落ちていることを交差確認し、個別ノードの問題ではなく時刻源の失効だと確定する。60 秒以内の結論：「ネットワークジッタではなく、AZ-B の時計が holdover で漂流しており、しかもそれは少数派だ。他の二区を信じよ」。これにオフセットしたノードリストと相対オフセット曲線を添え、**まず AZ-B の trace を分析側で offset 補償する**ことを勧める(乱暴に chrony を再起動して強制的に階段状に直すのではなく——それでは実行中の span のタイムスタンプがもう一度引き裂かれる)。
**エージェントがいない場合の苦境**：チームは連続的な漂流をネットワークジッタやプログラムの bug と誤認し、誤った方向へ丸一日 debug する；たとえ時計を見ようと思いついても、「結局どの AZ の offset を信じればいいのか」で行き詰まる——グローバルな真実がなく、三つとも動いているため、肉眼ではどれが falseticker か仲裁のしようがないからだ。
**効果**：「丸一日追った偽のジッタ」を 1 分での真因特定へ収束させ、しかも与えるのは「どの AZ が、どれだけ漂流し、なぜ信頼できないか」という仲裁可能な結論であって、単点の数値ではない；誤った前提に基づく緊急リリースを一度回避する。

> 💡 珠玉のひとこと
> 「フレームグラフが『結果が原因より前に起きた』と告げたら、因果律を疑う前に、まず時計を疑え——だがより難しいのは時計が狂っていると気づくことではなく、三つとも密かに漂流している時計の中で『どれを信じるか』に答えることだ。分散システムに神の視点の真の時刻はない。できるのは、多数派に少数派を投票で追い出させることだけだ。」

> 🔍 上級講評──道はどこにあるか
> 正直に言おう：ここには校正に使える「絶対に正しい時刻」など存在せず、あるのは**相対的一貫性**と**多数決によるフォールトトレランス**だけだ。ロブスターがしているのは Marzullo/Chrony の falseticker のような仲裁の工学化である——その本質は「同時に壊れるのは過半数を超えない」という賭けであり、この仮定は上流が同じ stratum-1 を共有していたり、region 全体の GPS 測時が妨害されたりすれば直ちに崩壊する(三つの AZ が一緒に漂流すれば多数決は失効する)。本当の次の一歩は時刻そのものに信頼を格付けすることだ：レイテンシに敏感なクリティカルパス上では PTP(ハードウェアタイムスタンプ、誤差をサブマイクロ秒まで下げる)を**独立した第二の時刻源**とし、NTP と PTP を互いの falseticker 検知に使う；同時に「時計の信頼度」を一等遥測(テレメトリ)に仕立て——root dispersion が急騰したら、下流の trace 分析は自動で「この区の時間軸は低信頼」とマークすべきで、鵜呑みにしてはならない。最終命題はこうだ：エージェントが遥測に基づいて自動的に意思決定し始めるとき、遥測の時間次元の信頼度評価は、あれば嬉しいものから、迂回不可能な安全の前提へと変わる。

## シナリオ38　サンプリング率(Sampling)の盲点下での散発的エラー狩り
**背景**：コスト管理のため、トレーシングシステムはヘッドベースサンプリング(head-based sampling)1% を採用し、毎秒百万リクエストを捌く。
**問題**：0.03% の確率で起きる散発的な 5xx が顧客からの苦情を絶やさないが、1% サンプリングではこれらの失敗リクエストはほぼ決して採取されない——SRE は失敗した一本の完全な trace を見たいのに、どうやっても掬い上げられない。可観測性はここに「構造的盲点」を抱えている：稀で重要なエラーほど、サンプリングで捨てられやすい。
**必要なスキル**：ヘッド vs テールサンプリングのトレードオフ、サンプリングバイアスの定量化、動的サンプリング戦略の設計、稀少イベントの捕捉。
**オープンソースツール**：OpenTelemetry Collector(tail sampling processor)、Grafana Tempo、Jaeger、Prometheus exemplars。
**活用するエージェントの特性**：ロブスターはメトリクス層から、5xx の比率は低いものの持続しており、対応する trace のサンプリング命中率がほぼ 0 であること(典型的な盲点の特徴)を発見する。サブエージェントは OTel Collector に一時的なテールサンプリング戦略を動的に配布する：「status≥500 もしくは latency>1s の trace はすべて 100% 保持」。30 秒後に最初の完全な失敗 trace が手に入り、ロブスターはそれを根本原因 span とともにグループに貼り、問題解決後はコスト管理のため一時戦略を自動で撤回する。
**エージェントがいない場合の苦境**：SRE は一方で全体のサンプリング率を一時的に 100% へ引き上げ(コストとストレージが瞬時に爆発)、一方で失敗 trace を掬えることを祈り、掬えた後は戻し忘れ、月末の請求が三倍になる。
**効果**：稀少エラーの完全な trace 捕捉が「ほぼ不可能」から 30 秒以内へ；しかも戦略を自動撤回できるため、ストレージコストの追加増加はゼロ。

> 💡 珠玉のひとこと
> 「1% サンプリングの残酷さは、あなたが最も見たい 0.03% を正確に捨てることだ——稀少な災厄であればあるほど、『平均』に優しく隠されてしまう。」

> 🔍 上級講評──道はどこにあるか
> この道は「オンデマンドで焦点を合わせる可観測性」だ。可観測性は均等に網を撒くべきではなく、免疫系のように、平時は低消費で、敵に遭えば集結すべきだ。ロブスターはここで「観測解像度を動的に調整する」役を演じる。実装上の工学的緊張は制御ループの安定性にある——もしロブスターが一度のジッタでサンプリングを満杯にし、それがさらなるジッタを引き起こせば、観測の自己発振が形成されてしまう。今後この道に必要なのは、ダンピングとコスト予算を備えた閉ループだ：「はっきり見たい」と「こんなに高いものは見ていられない」を同じ目的関数の中に入れて解くのだ。

## シナリオ39　SLO バーンレート(Burn Rate)の複数ウィンドウによる早期予兆
**背景**：コア API の月次エラーバジェット(error budget)を SLO で管理しており、従来は静的閾値アラート。
**問題**：あるカナリアリリースが緩やかなメモリリークを持ち込んだ。エラー率はいかなる瞬時閾値も突破せず(毎分わずか 0.4% の 5xx 増)、アラートは全行程沈黙したままだった——だがこの速度は 6 時間後に月のエラーバジェットを丸ごと燃やし尽くす。これは最も陰険なグレー障害だ：いかなる単点異常もないのに、システムは一定速度で SLO 違反へと向かっている。
**必要なスキル**：複数ウィンドウ複数バーンレートアラート(multi-window multi-burn-rate)の設計、エラーバジェットのモデリング、燃焼速度の外挿、カナリアロールバックの意思決定。
**オープンソースツール**：Prometheus、Sloth、Pyrra、Grafana。
**活用するエージェントの特性**：ロブスターは 1h/6h の速いウィンドウと 3d の遅いウィンドウのバーンレートを同時に計算する。サブエージェントは 6h ウィンドウのバーンレートが 4× で安定していることを発見し、「バジェットは 5h48m 後にゼロになる」と外挿する。いかなる瞬時アラートも発火していないにもかかわらず、それでも能動的に予兆へ格上げし、燃焼曲線の外挿図、疑わしいカナリアバッチ、そしてワンクリックのロールバック指令をまとめてグループにプッシュし、人間がバジェットを燃やし尽くす 5 時間前にロールバックを決断できるようにする。
**エージェントがいない場合の苦境**：すべての瞬時アラートが静かで、オンコール担当はまったく警戒せず、ある日の真夜中に SLO ダッシュボードが突然赤くなり、月次バジェットが一夜で燃え尽き、顧客が大規模にタイムアウトし始めて、ようやく六時間前のあのカナリアが地雷を埋めていたことに気づく。
**効果**：「バジェット燃え尽き後の受け身の火消し」から「燃え尽きる 5 時間前の能動的予兆」へ；SLO 違反事故が四半期あたり 3 件から 0 件へ。

> 💡 珠玉のひとこと
> 「最も危険な障害は叫ばない。それはあなたが気づけない速度で、一ヶ月分の容認許容量を一定速度で灰にしていくだけだ——静的閾値は爆発は見えても、燃焼は見えない。」

> 🔍 上級講評──道はどこにあるか
> これはロブスターを「異常検知者」から「トレンド外挿者」へと格上げする：その関心は「今、間違っているか」ではなく「この速度だと間違えるか、いつ間違えるか」だ。この道の価値はアラートを事後から事前へと移すことにある。先を見据えた信頼の難題は「予言の代償」だ——外挿に基づく能動的ロールバックは、被害がまだ生じていないうちに手を打つことを意味し、外挿が外れればそれは無意味なロールバックの撹乱となる。今後ロブスターは外挿の一本一本に「信頼度と不確実区間」を添え、ロールバック提案を「リマインド/待機/自動」に格付けし、予測的運用を大胆さと自制の間で、説明責任を果たせるバランス点へと落とし込む必要がある。

## シナリオ40　カーディナリティのコスト帰属(Cost Attribution)と可観測性請求のガバナンス
**背景**：可観測性プラットフォームの月次請求は 60 万ドル。metrics/logs/traces を網羅し、200 以上のチームで共用され、総額に責任を負う者は誰もいない。
**問題**：請求が三ヶ月で 40% 上がり、CFO がテーブルを叩いた。だが金がどこに使われたか知る者は誰もいない——可観測性自身が「観測できない」ブラックホールと化した：誰が最も高価な metric を書いたか、誰のログが ingest の 35% を占めるか、どの trace ラベルが最も無駄か、すべてがどんぶり勘定だ。他人のシステムは観測できるのに、自分のコストは観測できない。
**必要なスキル**：遥測コスト帰属のモデリング、チーム別チャージバック(per-team chargeback)、カーディナリティ/ingest コストの分解、ROI 分析。
**オープンソースツール**：Grafana Mimir/Loki(per-tenant usage)、OpenCost、Prometheus(`*_ingested_samples_total`)、Vector。
**活用するエージェントの特性**：ロブスターは毎週、metrics の series 数、logs のバイト数、traces の span 数を tenant/team ラベルごとに帰属させる。サブエージェントは「コスト上位 10 名 + 前年同期比の増加幅 + 各 metric のクエリ命中率(ダッシュボード/アラートに参照されたことがあるか)」を算出し、月に 4 万ドルを燃やしながら一度もどのダッシュボードからも引かれたことのない一群の「ゾンビ指標」を炙り出し、ローカルでチーム別のチャージバックレポートと廃止提案を作成し、Multi-Channel Gateway を通じて各チームの owner と財務グループへ同期プッシュし、「これらを削っても既存のアラートには一切影響しない」という証明を添える。
**エージェントがいない場合の苦境**：プラットフォームチームは手動で請求 CSV をエクスポートし、人力で tenant を分解し、200 チームと一つひとつ email で照合し、一巡のレポートを作るのに二週間かかる。作り終えた頃には請求がまた上がっており、永遠に追いつけない。
**効果**：コスト帰属が二週間の人手から毎週の自動生成へ；初回のゾンビ指標廃止だけで月 11 万ドルを節約、しかもアラートへの影響はゼロ。

> 💡 珠玉のひとこと
> 「自分の出費を観測できない可観測性プラットフォームは、それ自体が最大のグレー障害だ——あなたはシステム全体の脈を見通せるのに、自分が失血していることは見えていない。」

> 🔍 上級講評──道はどこにあるか
> この道はロブスターを、エンジニアがしばしば避けてきた戦場へと連れて行く：「可観測性の経済学」だ。観測はタダではなく、一つひとつの metric、一行ごとのログが利息付きの負債である。ロブスターはここで「遥測の財務監査」を演じ、コストと価値(クエリ命中率)を結びつけて評価する。先を見据えた工学的命題は、「コスト」を遥測の一等属性とし、カーディナリティや保持期間とともに CI 段階で値付けすることだ。最終的な信頼境界はやはり廃止の意思決定である——ゾンビ指標が今日引かれていないからといって、次の大事故で使えないとは限らない。エージェントが大胆に削りつつ、救命の藁を削らないようにするには、「削除ではなく冷凍」という可逆なガバナンスが必要だ。これこそがコストと安全の最適解である。
