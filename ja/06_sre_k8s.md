# 第6章　K8s クラスタ：ノード、スケジューリング、自己修復

## シナリオ 11　ImagePullBackOff のクラスタ全体免疫(Cluster-wide Immunity)
**背景**：3 つの region にまたがり、計 1,200 ノードを擁する EKS クラスタ。毎日 400 回以上デプロイし、イメージは自前構築の Harbor registry と AWS ECR の二重ソースから取得している。
**問題**：午前 02:14、ECR のある NAT Gateway が断続的にパケットをドロップし始めた。8 分のうちに、新たにスケジュールされた Pod がドミノのように倒れていく——`ImagePullBackOff` が 3 個から 1,900 個へと急増し、ちょうどその時 HPA がトラフィックのスパイクでスケールアウトしようとした結果、増えたのはイメージを引けないゾンビ Pod ばかりだった。当直エンジニアのスマートフォンには 2 分で 600 件のアラートが届き、Slack はそのまま固まった。
**必要なスキル**：Kubernetes event ストリーム解析、コンテナ registry トポロジの理解、region をまたぐネットワークデバッグ、バッチ kubectl 操作。
**オープンソースツール**：`kube-state-metrics`、`Trivy`、`k9s`、`stern`。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** を通じてクラスタ全体の `FailedPull` event ストリームを継続的に watch し、「同一イメージ digest が 90 秒以内に ≥3 ノードをまたいで失敗」を検知すると、即座にこれが単一マシンの問題ではなくソース側の障害だと判定した。その **子 Agent** は二手に分かれる——一方は `nslookup` + `curl -w` で ECR endpoint の RTT とパケットロス率を計測し、もう一方は Harbor の同一イメージが健全かどうかを照合する。ECR がダウンしていると確認した後、ロブスターは **ClawHub** から「registry-failover」スキルプラグインをロードし、影響を受けた Deployment の `imagePullSecrets` とイメージプレフィックスを Harbor ミラーへホットスイッチし、`Multi-Channel Gateway` を使って Slack、PagerDuty、企業微信に region トポロジ図つきの根本原因カードを同時投下した：「ECR ap-northeast-1 のパケットロス 47%、1,900 Pod を Harbor ミラーへ切り替え済み、復旧見込み 4 分。」
**Agent がない場合の窮状**：当直エンジニアは 600 件のアラートに溺れ、「壊れたのは自分の app ではなく registry だ」と気づくまでに 15 分かかり、さらに 11 個の namespace の imagePull 設定を手動で書き換えるのに 20 分かかる。その過程で 2 つの namespace を誤って変更し、二次障害を引き起こす。
**効果**：MTTR は 52 分から 3 分 40 秒へ短縮；アラート嵐は 600 件から 1 枚のカードへ収束；本来オンライントラフィックの 30% に波及しかねなかった容量崩壊を avoided(回避)した。

> 💡 珠玉のひとこと
> 「`ImagePullBackOff` は決して Pod の病ではなく、サプライチェーンの咳である——治すべきは上流であって、解熱ではない。」

> 🔍 進んだ論評──道はどこにあるか
> このケースはロブスターを「アラートの転送係」から「サプライチェーン健全度の能動的な審判」へと押し上げる。一歩先を見れば、その道は**クラスタをまたぐイメージソースの信頼グラフ**を築くことにあり、failover をスクリプト的な力任せの切り替えではなく、リアルタイムの SLO に重みづけされたスマートルーティングにする。実装の工学的境界はきわめて現実的だ——誰が Agent に本番の imagePullSecrets を変更する権限を与えるのか？failover 後の「自動切り戻し」は、registry のジッタが引き起こすピンポン振動をどう避けるのか？これには Agent と GitOps(Argo CD) のあいだに「誰が真実のソースか」という明確なレッドラインを引く必要がある。

## シナリオ 12　コントロールプレーンのスプリットブレイン(Control Plane Split-Brain)の仲裁者
**背景**：自前構築の 5 ノード etcd クラスタ。2 つのマシンルーム(AZ-A 3 台、AZ-B 2 台)にまたがり、金融グレードの kube-apiserver 高可用デプロイを支えている。
**問題**：14:03、両マシンルームを結ぶ基幹光ファイバーが工事で切断された。AZ-A 側の 3 台の etcd はまだ quorum を満たして書き込みを続けられたが、AZ-B の 2 台の etcd は多数派を失って読み取り専用になった。だが厄介なことに、AZ-B には自前のローカル load balancer があり、依然として書き込みリクエストをその 2 台へ振り向けていた——controller-manager が幻覚を起こし始め、同じ一群の Pod を繰り返し create/delete し、`resourceVersion` 衝突ログが毎秒 4,000 行流れる。さらに 90 秒後、クラスタ全体の leader election がジッタに陥り、scheduler がスケジューリングを停止した。
**必要なスキル**：etcd raft 合意原理、quorum と fencing メカニズム、kube-apiserver HA トポロジ、災害隔離の意思決定。
**オープンソースツール**：`etcdctl`、`etcd-defrag`、`Patroni`(設計参照)、`kube-apiserver` healthz プローブ。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** を通じて各 AZ に軽量な歩哨を配備し、各 etcd member に対して `etcdctl endpoint status --write-out=json` を継続的に走らせていた。「AZ-B の member が報告する `raftIndex` が AZ-A より 50,000 以上遅れ、かつ `isLeader` がすべて false」と発見した時、即座にネットワーク分断が発生したと判定した。それは軽率に手を出さず、まず **子 Agent** で検証する——これは本物の分断かプローブの誤判定か。AZ をまたぐ ping、BGP ルーティングテーブル、クラウドベンダーのステータスページを相互確認する。確認後、ロブスターは最も肝心な **fencing の決断** を実行する——AZ-B のローカル LB を書き込み経路から取り外し(backend の重みを 0 に更新)、すべての書き込みトラフィックを quorum を持つ AZ-A へ強制的に戻し、スプリットブレインの二重書き込みを阻止する。同時に **Multi-Channel Gateway** で指揮チャンネルに赤色カードを発し、当直責任者に @ する：「control plane split-brain を検知、AZ-B の書き込み経路を fence 済み、クラスタは単一の真実へ復帰、光ファイバー修復の人手確認を待って復旧する。」
**Agent がない場合の窮状**：スプリットブレインは SRE が最も恐れるシナリオの一つだ。人間はまず毎秒 4,000 行の衝突ログから「これは分断であって過負荷ではない」と見抜かねばならず、この一歩だけで 20 分はかかる。fencing が必要だと気づく頃には、二重書き込みによるデータの分岐がすでに数千の Pod の状態を汚染している可能性があり、事後の突き合わせは一晩がかりになる。
**効果**：分断発生から fencing 完了まで 75 秒；二重書き込み汚染(estimated 影響 8,000 以上のオブジェクト)を回避；本来なら etcd をスナップショットから再構築する必要があった P0 を、秩序ある片側縮退へと格下げした。

> 💡 珠玉のひとこと
> 「分散システムの最も深い恐怖は、片方が死ぬことではなく、両方ともまだ生きていて、しかも双方が自分こそ唯一の真実だと思い込んでいることだ。」

> 🔍 進んだ論評──道はどこにあるか
> スプリットブレインの仲裁は Agent 自動化の「深海域」だ——なぜなら fencing は**システムの一部から能動的に能力を奪う**破壊的な決断だからである。これはロブスターの未来において最も論争的でありながら最も価値ある道を指し示す——**分散合意のメタ仲裁層になる**こと。だがここでの信頼の境界はきわめて鋭利だ：Agent 自身の歩哨もまた切断されたネットワークをまたいでいるとき、それは自分が分断による「半分の真実」に基づいて判断していないと、どうやって保証するのか？答えはおそらく、**K8s コントロールプレーンの外に独立した第三者の見証人(witness)** を導入し、Agent の決断そのものも quorum を満たすようにすることだ。さもなくば、自動化された fencing が次のスプリットブレインの源になりかねない。

## シナリオ 13　クラウドマシンのハードウェア予兆時の無感覚移住(Live Migration)
**背景**：GCP 上で動くステートフルサービスのクラスタ。Spot と on-demand ノードを混用し、その中の一群の c2-standard-60 では Redis、ClickHouse など再起動に敏感な StatefulSet が動いている。
**問題**：03:47、GCP が `HostError` のメンテナンス予兆を送ってきた——ある基盤ホストマシンの ECC メモリが訂正可能エラーを 17 回連続で報告し、6 時間以内に強制的な live migration かオフライン化が予測される。このマシンには折悪しく ClickHouse のある shard leader が動いており、ハードな移行は 40〜90 秒の stop-the-world フリーズを引き起こし、上流のリアルタイムレポートクエリをすべて timeout させるに足る。
**必要なスキル**：クラウドベンダーのメンテナンスイベントの読解、StatefulSet の優雅な移行、PodDisruptionBudget の設計、ステートフルサービスの leader 移譲。
**オープンソースツール**：`Node Problem Detector`、`Descheduler`、`Velero`、`cluster-autoscaler`。
**用いた Agent の特性**：ロブスター OpenClaw は GCP の metadata `maintenance-event` endpoint を購読し、**ローカルスクリプト実行** を通じて Node Problem Detector の上に意味理解の一層を加える——ただ「メンテナンスがある」と見るだけでなく、**子 Agent** でこのノードでどんな workload が動いているか、どれが leader か、どれが PDB で保護されているかを逆引きする。ClickHouse shard leader がリスクノードにあると判定した後、ロブスターは**先手を打つ能動策**を選ぶ：メンテナンスウィンドウが来る前の閑散時間(午前 04:10)に、まず ClickHouse の優雅な leader 移譲を健全ノードへ起動し、続いてリスクノードを cordon + drain して、GCP の live migration には空のマシンを移行させる。この全過程は **Multi-Channel Gateway** を通じて Slack にタイムラインを残す：「04:10 予測的に shard leader を移行、04:14 drain 完了、04:30 GCP メンテナンス待ち、ユーザーは無感覚。」さらに **ClawHub** から「stateful-graceful-evict」プラグインをロードし、quorum が全過程を通じて崩れないことを保証した。
**Agent がない場合の窮状**：多くのチームではそもそも metadata endpoint を見張る者がおらず、GCP が本当に live migration を始め、ClickHouse が 60 秒フリーズし、レポートが全部赤くなって初めて受動的に火消しに走る。たとえ予兆を見た者がいても、深夜に手動でステートフルサービスの leader 移譲をするのはリスクが極めて高く、手元が一度狂えばデータ不整合だ。
**効果**：必ず起きるはずだった 40〜90 秒のユーザー体感フリーズを、**無感覚**移行に変えた；予測的処理によって受動的な火消しウィンドウを「6 時間以内いつ爆発するか」から「深夜の閑散時間に能動的にスケジュール」へと変えた；ステートフルサービス移行の人為ミス率をゼロにした。

> 💡 珠玉のひとこと
> 「最も巧みな運用とは、災害が起こる前に、すでに現場を空にしてしまうことだ。」

> 🔍 進んだ論評──道はどこにあるか
> このケースの真髄は**「イベントへの応答」から「予兆への応答」への進化**にある——ロブスターが読んでいるのはハードウェアの「死亡証明」ではなく「心電図」だ。先を見れば、この道は**容量と健全性の確率的スケジューリング**へ通じる：Agent はホストマシンの ECC エラー率、ディスク SMART、Spot 中断確率に基づいて各ノードに動的な「寿命スコア」をつけ、scheduler が高リスクのホストを能動的に避けるようにする。工学的な挑戦はこうだ：予測的移行にはコストがある(マシンを一台余分に占有し、leader 移譲を一回余分に行う)。Agent は「予防のコスト」と「災害の期待損失」のあいだで定量的なトレードオフを学ばねばならず、予兆を見るたびに過剰反応してはならない。

## シナリオ 14　K8s レプリカ数の動的退勤制(Replica Off-hours Scheduling)
**背景**：B2B 企業顧客向けの SaaS。トラフィックの 80% は平日 09:00〜19:00 に集中しているが、開発チームはすべての環境の `replicas` を「ピークに耐える」数字に固定する習慣があり、180 個の Deployment が年中 7×24 でフル稼働している。
**問題**：財務の月末締めで判明したのは、staging と internal-tools の 2 つの namespace だけで、夜間(19:00〜翌 08:00)と週末の遊休計算が毎月 USD 38,000 も焼いていたことだ——毎秒 0 QPS の Pod が一晩中灯りをつけて空回りし、CPU 使用率は長期的に 3% を下回るが、誰も手動で縮小する勇気がない。翌朝戻し忘れて事故になるのが怖いからだ。
**必要なスキル**：トラフィックのプロファイリングと周期的モデリング、HPA/VPA のチューニング、コスト帰属(FinOps)、安全なスケーリングのガードレール設計。
**オープンソースツール**：`KEDA`、`kube-downscaler`、`OpenCost`、`Goldilocks`。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** を通じて 14 日間連続で各 Deployment の QPS とリソース曲線を採取し、**子 Agent** で各サービスの「生活リズムのプロファイル」を自動描画して、どれが「真の 7×24」(決済、認証)、どれが「9 時 5 時」(バックオフィス、レポート)、どれが「純粋な平日」かを識別した。それはいきなり切り捨てず、まず**動的な退勤スケジュール提案**を生成し、**Multi-Channel Gateway** を通じて Slack に送り、owner にワンクリックで承認させる。承認後、ロブスターは **ClawHub** から KEDA の `Cron` ScaledObject プラグインをロードし、各サービスに「退勤制」を装着する：夜間は最小レプリカまで縮小し、早朝のトラフィック回復の 15 分前に自動でウォームアップしてスケールアウトする。肝心なのは**二重の安全ガードレール**を設けたことだ——「退勤」したサービスが予期せぬトラフィック(QPS がベースラインの 3σ を突破)を受け取れば、即座に自動で全量スケールバックして通報する。
**Agent がない場合の窮状**：FinOps レポートが毎月叱り、エンジニアが毎月謝るが、180 個のサービスを一つずつ生活リズム解析し、一つずつスケーリングルールを書き、さらに「縮小ミスがオンライン事故を招く」責任まで負う余裕のある者は誰もいない。こうしてこの金は年々焼かれ続ける。
**効果**：staging/internal namespace の夜間と週末の計算コストが 71% 低下し、月約 USD 27,000 を節約；180 サービスの生活リズム解析が「誰もやらない」から「14 日で自動完了」に；3σ のトラフィックガードレールを設けたため、縮小期間中の事故はゼロ。

> 💡 珠玉のひとこと
> 「クラウド請求で最も高い項目は『誰も手を出す勇気がない』というものだ——そして Agent が売るのは、まさに『手を出す』という行為の安心感である。」

> 🔍 進んだ論評──道はどこにあるか
> これは Agent が **FinOps 自治** へ入る典型的な入口だ——「節約」を勇気の要る人間の決断から、ガードレールがあり、監査可能で、ロールバック可能な自動化アクションへ変える。先の道は**クラスタ全体の弾力的容量の頭脳**だ：時間割だけでなく、業務カレンダー(決算日、大型セール)、地域のタイムゾーン、さらには顧客契約の SLA までを融合して容量を編成する。だがここでの信頼の境界は「縮小の爆発半径」にある：Agent が縮小する勇気を持つほど節約は大きくなるが、過小評価された依存サービスを一つ縮小ミスすれば、連鎖障害だ。未来の真の試練は、Agent が単一サービスの QPS 曲線を見るだけでなく、「サービス間の暗黙的な依存」の因果モデルを構築できるかどうかである。

## シナリオ 15　ノードがランサムウェアに襲われた際の孤立分区・尾切り生存(Ransomware Quarantine)
**背景**：ハイブリッドクラウドのクラスタ。一部の worker ノードは IDC にホストされたベアメタルで、あるとき第三者のサプライチェーン部品にマイニング兼ランサムウェアの悪意あるペイロードが仕込まれた。
**問題**：02:58、セキュリティ側の Falco が突然連続でアラートを発した：3 つのノード上のコンテナが異常な挙動をしている——大量の `chmod`、`/var/lib/kubelet` への怪しい書き込み、国外 IP への TLS 接続開始、CPU 100% で暗号化演算を回す。これはランサムウェアの横方向移動であり、この 3 ノードは正常な本番 workload と同じ VLAN に同居していて、あと数分で service account token を介してクラスタ全体を汚染しうる。
**必要なスキル**：runtime セキュリティ検知、K8s NetworkPolicy とマイクロ隔離、RBAC/ServiceAccount の無効化、フォレンジックスナップショット(forensics)。
**オープンソースツール**：`Falco`、`Cilium`(NetworkPolicy)、`Tetragon`、`kube-bench`。
**用いた Agent の特性**：ロブスター OpenClaw は Falco のアラートストリームを **ローカルスクリプト実行** の意思決定エンジンへつなぎ、60 秒以内に「同種の異常挙動が ≥2 ノードをまたぐ + 国外接続 + 暗号化エントロピーの上昇」という組み合わせの特徴を見ると、ランサムウェアの横方向爆発と判定して**尾切り生存**プロトコルに入る。その **子 Agent** は同時に三つのことを実行する：① Cilium で感染ノードに `quarantine` NetworkPolicy を付け、東西方向・南北方向のすべてのトラフィックを切断する(フォレンジック通路のみ残す)；② これらノード上の Pod の ServiceAccount token を即座に失効させ、漏洩した可能性のあるクラスタ secret をローテーションする；③ 感染コンテナのメモリとディスクのスナップショットを取った後で `kubectl cordon` + 凍結し、証拠を保全する。隔離完了後、**Multi-Channel Gateway** を通じてセキュリティ、SRE、法務の三チャンネルへ同期で incident カードを発し、war room を起動する。それは独断で何かを削除することはしなかった——**フォレンジック優先、尾は切るが死体は焼かない**。
**Agent がない場合の窮状**：午前 3 時、大量の Falco アラートの中から「これはランサムウェアの横移動だ」と識別するにはシニアのセキュリティエンジニアが必要で、その者がオンラインになるまで 20 分かかるかもしれない。この 20 分は悪意あるペイロードがクラスタ全体の secret を汚染するに十分で、事後にはクラスタ全体の証明書ローテーション + 再構築が必要になりかねず、影響範囲は 3 ノードから region 全体へ拡大する。
**効果**：最初のアラートからマイクロ隔離 + token 失効の完了まで 52 秒；横方向の爆発半径を 3 ノードにしっかり押さえ込んだ(さもなくば estimated 200 以上のノードに波及)；フォレンジックスナップショットを完全に保全し、事後の追跡を「当て推量」から「実証あり」へと変えた。

> 💡 珠玉のひとこと
> 「ランサムウェアに直面したとき、1 秒の遅れは余分にマシンを 1 台失うことではなく、信頼ドメインを丸ごと一つ失うことだ——尾切りは速く、しかし証拠まで一緒に燃やすな。」

> 🔍 進んだ論評──道はどこにあるか
> このシナリオはロブスターを **セキュリティ自動応答(SOAR)と運用の境界** へ押し上げる。そしてこれこそ最も繊細な信頼の境界だ：Agent は「ネットワークを切断し、証明書を失効させる」という強い破壊性を持つ防御アクションを実行する権限を与えられている。先の道は **可逆で、段階的な自動封じ込め**だ——隔離はヒューズのように段階的に溶断すべきで、一刀両断ではない。最大の工学的難題は「誤殺コスト」だ：もし Falco の特徴が悪意あると誤判定された正常なバッチタスクに命中すれば、Agent の自動隔離そのものが自傷式の DoS になる。ゆえにこの道の鍵は、Agent の封じ込め決断に「信頼度の段階分け」と「秒級のロールバック可能性」を持たせ、セキュリティと可用性を二者択一にしないことである。

## シナリオ 16　トポロジ認識スケジューリングが救った AZ 間レイテンシ(Topology-Aware Scheduling)
**背景**：3 つの可用区にまたがるマイクロサービスのクラスタ。コアの呼び出し経路は `gateway → order → inventory → payment` で、四つのサービスはそれぞれ数十のレプリカを持ち、scheduler によって各 AZ にランダムに撒かれている。
**問題**：大型セールの負荷試験時、P99 レイテンシが不可解にも 380ms まで急騰したが、各サービスを個別に見るとどれも健全で、CPU も高くない。深掘りして初めて判明した：scheduler が呼び出し経路の上流・下流の Pod を別々の AZ に散らばらせており、一回の完全な注文リクエストが AZ をまたいで 6 回往復し、1 ホップごとに +1.5ms の区間越えレイテンシが連鎖的に増幅される。さらに AZ 間トラフィックが 1GB あたり USD 0.01 の転送料を焼き続け、1 時間の負荷試験で純粋なネットワーク料金だけ USD 900 を焼いた。
**必要なスキル**：呼び出し経路のトポロジ解析、Topology Spread Constraints、Pod Affinity 設計、AZ 間トラフィックコストのモデリング。
**オープンソースツール**：`Jaeger`、`Kiali`、`Descheduler`、`kube-scheduler`(topology plugin)。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** を通じて Jaeger の trace データをサービス間の「AZ 間ホップ数ヒートマップ」へ集約し、**子 Agent** で各経路の区間越え増幅係数を算出して、「order↔inventory という黄金コンビが AZ-A と AZ-C に引き裂かれている」のが元凶だと精確に指摘した。それは `topologySpreadConstraints` + zone-aware affinity に基づくスケジューリング修正案を生成し、まず staging で A/B 検証を回し(同区親和の後、P99 が 380ms から 90ms へ低下)、副作用がないことを確認した後、**Multi-Channel Gateway** を通じて before/after 比較図をアーキテクチャ組へ送って承認を得て、続いて Descheduler で位置のずれた Pod を段階的に同一 AZ へ再スケジュールした。全過程がグレー(段階的)で、いつでも停止できる。
**Agent がない場合の窮状**：「各サービスは健全なのに全体が遅い」は分散システムで最も人を苦しめるグレー障害だ——人間のエンジニアは dashboard を 2〜3 日見ても見つけられないかもしれない。なぜなら単一の指標が赤く点灯することはなく、真相は「トポロジのずれ」という専用の監視項目がない次元に隠れているからだ。
**効果**：コア経路の P99 が 380ms から 90ms へ低下(−76%)；大型セール期間中の AZ 間転送料が 64% 低下；本来なら 3 人日かけて調査するはずだったグレー障害を、一度の自動トポロジ解析へ圧縮した。

> 💡 珠玉のひとこと
> 「すべての部品が正常を示しているのに機械が震えているとき、問題は往々にして部品ではなく、それらが置かれた配置にある。」

> 🔍 進んだ論評──道はどこにあるか
> トポロジのずれは教科書級の Grey Failure だ：単一点のアラートはなく、ただ全体の緩慢さだけがある。これはロブスターの深遠な道を指し示す——**呼び出し経路の空間設計者になる**こと。スケジューリングを「リソース視点(どこに CPU があるか)」から「関係視点(誰が誰の近くにいるべきか)」へ次元上昇させる。実装の緊張はこうだ：親和性が強いほど、災害耐性は弱くなる——上流・下流を全部同じ AZ に詰め込めばレイテンシは最低だが、その AZ が一つ落ちれば全経路がゼロになる。未来の Agent は「レイテンシ最適」と「障害ドメインの隔離」のあいだで動的なトレードオフをし、さらには大型セール/平常時で異なるトポロジ戦略を切り替えねばならない。これは静的な最適解のない多目的最適化問題である。

## シナリオ 17　退去嵐(Eviction Storm)下の優先度防衛戦
**背景**：リソースをオーバーコミット(overcommit)したマルチテナントのクラスタ。利用率を上げるため memory request は概して低めに設定され、limit と QoS の段階分けで下支えしている。
**問題**：あるデータチームが深夜に limit を設定していない Spark タスクを走らせ、メモリが風船のように膨張して、所在ノードを MemoryPressure へ追い込んだ。kubelet の eviction メカニズムが起動するが、多くの重要サービスが当初「スケジュールされやすい」ように request を非常に低く設定し、QoS が `Burstable` どころか `BestEffort` まで落ちていたため、kubelet が QoS 順で退去させた結果、**まず決済ゲートウェイの Pod を追い出してしまった**。一方、メモリを食う当の Spark は request を高く設定し QoS が `Burstable` だったために生き延びた。退去は Pod の他ノードへの再スケジュールを引き起こし、それがまた別のノードを爆発させ、ノードをまたぐ**退去連鎖嵐**を形成して、3 分で 47 個の Pod が連環退去された。
**必要なスキル**：QoS 段階分けと eviction メカニズム、リソース request/limit のガバナンス、PriorityClass 設計、ノード圧力の伝導解析。
**オープンソースツール**：`kube-state-metrics`、`Goldilocks`(VPA 提案)、`Kyverno`(ポリシー門番)、`node-exporter`。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** 層で各ノードの `node_memory_*` と eviction event を継続監視し、「同一ノードで 60 秒以内に ≥3 回の eviction かつ重要サービス(`tier=critical` label つき)が退去された」を検知すると、退去嵐がコアサービスを誤って犠牲にしていると判定した。その **子 Agent** は即座に二つのことをした：① 誤って退去された重要サービスに緊急で高 `PriorityClass` を一時注入し `system-node-critical` をマークして、次のスケジュールラウンドで優先的に着地させ、再退去を免れさせる；② 加害者である Spark Pod を逆方向に特定し、cordon マークを付けて流量制限し、圧力源を断つ。嵐が静まった後、ロブスターは **ClawHub** から Kyverno ポリシープラグインをロードし、「limit なしのバッチタスクが本番ノードプールへ入るのを禁止する」という受け入れルールを自動で補い、**Multi-Channel Gateway** を通じてデータチームへ「あなたのタスクが退去嵐を引き起こしました。隔離済みです。limit を追加してください」という事故レシートを送った。
**Agent がない場合の窮状**：退去嵐の恐ろしさは「自己伝染」することにある——人間がまだ最初のノードがなぜ退去したかを調べているうちに、嵐はすでに 3 つ目、4 つ目のノードへ飛び移っている。「実は QoS 順が決済ゲートウェイを BestEffort 扱いして先に殺していた」と解明する頃には、コア取引はすでに 10 数分震えている可能性がある。
**効果**：嵐の起動から重要サービスの損失止めまで 68 秒；連環退去をノードプール全体ではなく 47 個の Pod に押さえ込んだ；事後に受け入れポリシーを自動で補い、「limit なしバッチタスク」という再発性の病根を根治した。

> 💡 珠玉のひとこと
> 「kubelet は退去するとき、お前が重要かどうかは問わない、ただお前の request が高く書かれているかだけを問う——リソースガバナンスの怠慢は、最悪の瞬間にお前に代わって誰が生き誰が死ぬかを決める。」

> 🔍 進んだ論評──道はどこにあるか
> 退去嵐は残酷な真実を暴いた：K8s のスケジューリングの公平性は、request/limit が正直に書かれているという前提の上に完全に成り立っているが、この前提はほとんど決して成立しない。ロブスターの道はゆえに **リソース契約の能動的なガバナー** へと延びる——事故時に火消しするだけでなく、受け入れ時にポリシーエンジンで「リソースを偽申告する」workload を堰き止める。工学上の深海域はこうだ：Agent が一時的に PriorityClass を引き上げるのは諸刃の剣で、決済ゲートウェイを救った一方、次の瞬間に他者をノードから押し出しかねない。未来の真に成熟した形態は、Agent が**クラスタ全体の優先度とリソース予算の総勘定**を維持し、緊急の権限引き上げのたびに既知のゼロサムゲームの中で証拠ある取捨選択をすることであって、その場の英雄主義ではない。

## シナリオ 18　Cluster Autoscaler の Spot 中断潮における容量延命(Spot Interruption Surge)
**背景**：徹底的な節約のため、あるバッチ計算クラスタはノードの 70% を AWS Spot インスタンスにし、cluster-autoscaler で自動伸縮しながら、大量の中断可能な ETL と訓練タスクを走らせている。だが「自分はずっと存在する」と仮定したロングコネクションのサービスもいくらか混ざっている。
**問題**：ある日 AWS が ap-northeast-1 の全区で `c5.4xlarge` という機種の Spot を回収し、2 分以内に 60 枚の 2 分カウントダウンつき中断通知を発した。cluster-autoscaler は新ノードを増やして穴埋めしようとしたが、皆が同じ機種を奪い合ったため `InsufficientInstanceCapacity` が連環でエラーになり、スケールアウトに失敗した。スケジュール可能な容量が一瞬で 40% 蒸発し、Pending Pod が 900 個まで積み上がり、タスクキューが雪崩れ始めた。
**必要なスキル**：Spot 中断処理、cluster-autoscaler と node group 設計、多機種/多 AZ の容量分散、バッチタスクの中断可能化。
**オープンソースツール**：`Karpenter`、`AWS Node Termination Handler`、`cluster-autoscaler`、`Kueue`。
**用いた Agent の特性**：ロブスター OpenClaw は EC2 の Spot 中断 metadata を購読し、**ローカルスクリプト実行** 層で容量の状況認識をする。「単一機種で 2 分以内に ≥20 枚の中断通知 + autoscaler が連続 `InsufficientCapacity`」を検知すると、Spot 中断潮と判定して**容量延命**プロトコルを起動する。その **子 Agent** はリアルタイムに Karpenter の NodePool 制約を書き換え、奪えない `c5.4xlarge` を第一候補から取り除き、`m5/m6i/c6i` など 6 つの代替機種 + 3 つの AZ へ動的に拡大して、autoscaler が一つの型に固執しないようにする。同時に「自分は中断されないふりをしている」ロングコネクションのサービスを識別し、残り少ない on-demand ノードへ優先的に再スケジュールして生き延びさせ、本当に中断可能な ETL にジッタを引き受けさせる。**Multi-Channel Gateway** を通じて容量ダッシュボードを発する：「Spot c5.4xlarge が全区回収、多機種混合スケールアウトへ切り替え済み、Pending は 900 から収束中、コアサービスは on-demand へ移行済み。」
**Agent がない場合の窮状**：cluster-autoscaler の node group 機種制約は通常 IaC にハードコードされており、中断潮が来ると人間はその場で Terraform を書き換え、apply を回し、反映を待つ。各ステップが分単位だ。だが 900 個の Pending Pod と雪崩れるキューは待ってくれず、書き換え終わる頃には SLA がすでに破られている可能性がある。
**効果**：Pending Pod が 900 から 4 分以内に 50 以下へ低下；多機種分散によって単一 Spot 機種への依存を 70% から 25% へ引き下げた；コアのロングコネクションサービスは中断ゼロ；この中断潮の復旧が「SLA 破り」から「波風立たず」へ変わった。

> 💡 珠玉のひとこと
> 「卵を Spot という安いカゴに入れること自体は問題ない、問題はお前がカゴを一種類しか買わなかったことだ——容量の靱性は、お前がどれだけ多くの代替品を受け入れる気があるかに隠れている。」

> 🔍 進んだ論評──道はどこにあるか
> Spot 中断潮が突きつけるのは FinOps の永遠の矛盾だ：極限まで節約することと、極限まで安定させることは生来対立する。ロブスターの道は **動的な容量ポートフォリオの操縦者** になることだ——投資ポートフォリオを管理するように機種/AZ/Spot-OnDemand の配分を管理し、中断確率と価格に応じてリアルタイムでリバランスする。実装の硬い骨は「状態の正しさ」にある：Agent が NodePool を書き換え、workload を移行する速度は、中断の 2 分カウントダウンより速くなければならず、これは Agent の意思決定レイテンシにハードリアルタイムの要求を突きつける。さらに先を見れば、この道は最終的に Agent とクラウドベンダーの容量市場との**駆け引きと予測**へ向かう——中断潮が本当に爆発する前に、すでにこっそり卵をカゴごと替え終えているのだ。

## シナリオ 19　ゾンビ Pod と孤児リソースのクラスタ全体清掃人(Zombie & Orphan Reaper)
**背景**：4 年間稼働し、十数代のエンジニアの手を経た「歴史ある」クラスタ。誰も覚えていないテスト namespace、`Terminating` で固まった Pod、バインド解除後に回収されなかった PV、そして削除済み Pod を指す孤児 endpoint が大量に積もっている。
**問題**：あるスケールアウト時に判明した。クラスタは「明らかに 30% のリソースが遊休している」のに新しい Pod を増やせない——`kubectl get pods -A` を見ると、2,400 個の Pod のうち 380 個が `Terminating` で 6 時間以上固まっており(finalizer のデッドロックのため)、リソースを離さず占有している。さらに 60 個の PV が `Released` なのに回収されず、バインドされた EBS ボリュームが毎月 USD 1,200 を空焼きしている。もっと陰険なのは、大量の孤児 endpoint がまだ Service の負荷分散リストに残っていて、トラフィックをとうに存在しない Pod IP へ振り向け、断続的な 502 を起こしていることだ。
**必要なスキル**：finalizer と GC メカニズム、PV/PVC のライフサイクル、Service/Endpoint の一貫性、クラスタ衛生のガバナンス。
**オープンソースツール**：`kube-janitor`、`Velero`、`Polaris`、`kubectl-neat`。
**用いた Agent の特性**：ロブスター OpenClaw は定期的に **ローカルスクリプト実行** を通じてクラスタ全体の「健康調査」をし、**子 Agent** で四種のゴミを分類して掃き出す：ゾンビ Terminating Pod、孤児 PV、行方不明 endpoint、持ち主なし namespace。高リスク操作(PV 削除、namespace 一掃)については、それは決して勝手に手を出さない——むしろ「証拠の連鎖」つきの清掃提案を生成し(各項目に「なぜゴミと判定したか」の根拠を添える：どれだけ owner がいないか、最終活動時刻、まだ参照があるか)、**Multi-Channel Gateway** を通じてプラットフォーム組へ送って**段階別承認**を求める：低リスクのゾンビ Pod(finalizer の一掃)は自動処理可、高リスクの PV 削除は人手の頷きが必須。承認後、ロブスターは **ClawHub** から kube-janitor ルールプラグインをロードして安全に実行し、各ステップにロールバック可能な監査ログを残す。
**Agent がない場合の窮状**：クラスタ衛生は典型的な「重要だが緊急でない」案件で、いつもすべての要望の後ろに回され、ゴミが年々積もる。それがついに「容量を増やせない」「謎の 502」という形で爆発したとき、人間は 2,400 個の Pod の中から肉眼で考古学をし、どの Terminating がデッドロックか、どの PV が本当に削除できるかを判別せねばならない——まだ使われている PV を一つ削除ミスすれば、それはデータ災害だ。だから皆ますます手を出す勇気を失う。
**効果**：380 個のゾンビ Pod が占有していたリソースを回収し、30% の「見せかけの遊休」を真の利用可能へ変えた；60 個の孤児 PV を一掃し、月 USD 1,200 を節約；孤児 endpoint を修復し、断続的な 502 をゼロに；「誰も手を出す勇気のない考古作業」を毎週一回の自動調査へ変えた。

> 💡 珠玉のひとこと
> 「クラスタの中で最も危険なのは壊れたものではなく、『死んでいるのに誰もその死を宣言する勇気がない』ものだ——技術的負債の利息は、容量と 502 で返済される。」

> 🔍 進んだ論評──道はどこにあるか
> ゾンビと孤児リソースはエントロピーの具現化だ——どんな長寿システムも自発的に混沌へ向かう。ここでのロブスターの道は **クラスタの常駐免疫システム** だ：たまに大掃除をするのではなく、死んだ組織を継続的に識別・隔離・回収する。最も肝心な工学的命題は「あるものが本当に死んでいることをどう証明するか」だ——一見持ち主のなさそうな namespace が、四半期に一度だけ走るコンプライアンスタスクかもしれない。ゆえにこの道の核心は「清掃能力」ではなく、**説明可能な死亡判定**にある：Agent は回収のたびに監査に耐える証拠の連鎖を提供し、破壊的操作は信頼が長期的観測によって蓄積されるまで、常に「人間の承認」という門の手前で止まらねばならない。

## シナリオ 20　スケジューラのジッタ(Scheduler Thrashing)と反親和デッドロックの打破
**背景**：高可用性への要求が極めて厳しいクラスタ。コアサービスには概して `podAntiAffinity` を設定し、「同一サービスのレプリカは同一ノードに落ちてはならない」を強制して、単一ノード障害が全滅を招かないことを保証している。
**問題**：あるノード縮小の後、クラスタは不可解な状態に入った：ある 6 レプリカの重要サービスが、反親和制約が `requiredDuringScheduling`(ハード制約)であり、残った利用可能ノードが条件を満たすもの 5 個しかないため、6 番目のレプリカが永遠に `Pending` になる。同時に HPA が「レプリカが目標数に達していない」のを見て scheduler を催促し続け、scheduler は試みては失敗し、スケジュールキューが毎秒数百回ジッタし、kube-scheduler の CPU が自身の徒労な試行で 90% まで焼かれ、巻き添えで**クラスタ全体のすべての Pod のスケジュール速度を遅らせた**——一つのサービスのデッドロックが、クラスタ全体のスケジュールスループットを劣化させたのだ。
**必要なスキル**：affinity/anti-affinity 制約の求解、scheduler のパフォーマンスプロファイリング、制約緩和(soft constraint)のトレードオフ、スケジュールキューの健全度監視。
**オープンソースツール**：`kube-scheduler`(profiling)、`Descheduler`、`kube-state-metrics`、`Prometheus`。
**用いた Agent の特性**：ロブスター OpenClaw は **ローカルスクリプト実行** を通じて scheduler の `scheduler_pending_pods` と `scheduling_attempt_duration` 指標を監視し、「ある Pod のスケジュール試行回数が急増 + クラスタ全体のスケジュールレイテンシが同期して上昇」を発見すると、**制約が無解でスケジュールジッタが発生した**と判定した。その **子 Agent** は制約求解のシミュレーションを一度回し、「6 レプリカ × ハード反親和 × 適格ノードわずか 5 個 = 数学的に無解」と精確に算出し、トレードオフつきの三つの選択肢を提示した：① 6 番目のレプリカの反親和を `required` から `preferred` へ格下げ(わずかな災害耐性を犠牲にしてスケジュール可能性を得る)；② 適格ノードを 1 つ増設；③ 目標レプリカ数を 6 から 5 へ削減。それは **Multi-Channel Gateway** を通じて、この「不可能な三角形」を各選択肢の災害耐性への影響とともに明快に owner へ報告し、独断はしなかった。owner がノード増設を選んだ後、ロブスターは自動で Karpenter のスケールアウトを起動し、6 番目のレプリカが無事に着地し、scheduler の CPU が下がり、クラスタ全体のスケジュールレイテンシが回復したことを検証した。
**Agent がない場合の窮状**：これは最も隠れた類の障害だ——表面上は「ある Pod がずっと Pending」だけで、それがクラスタ全体のスケジューラを引きずり倒しているとは誰も思わない。人間のエンジニアは通常「なぜクラスタ全体のすべてのデプロイが遅くなったのか」になって初めて警戒し、その後ずいぶんかけてようやく因果の連鎖を「あの無解な反親和制約」へ遡れる。この二つのことは dashboard 上ではまったく無関係に見えるからだ。
**効果**：スケジュールジッタから制約デッドロックの根本原因特定まで 90 秒；クラスタ全体のスケジュールレイテンシが劣化した 8 秒から 200ms へ回復；「一見 1 個の Pod だけに影響するように見えて、実はスケジューラ全体を引きずり倒す」見えざる殺し屋を、定量的なトレードオフのある決断可能な選択問題へと変えた。

> 🔍 進んだ論評──道はどこにあるか
> このシナリオの深遠さは、それが**数学的には無解なのに性能問題に偽装した**障害である点にある——制約求解の充足不可能性が、スケジューラの CPU 燃焼として投影されたのだ。ロブスターの道はゆえに **制約システムのソルバーかつ通訳官** を指し示す：「無解」を算出するだけでなく、この冷たい数学的結論を人間がトレードオフできる業務言語(災害耐性 vs 容量 vs レプリカ数の不可能な三角形)へ翻訳する。工学上で最も先見的な命題はこうだ：制約衝突が大規模クラスタで普遍的になるとき、Agent は「事後の打破」から「受け入れ時に無解な制約を堰き止める」へ進化できるか——エンジニアが数学的に必ず Pending になる YAML を提出した瞬間に、「あなたのこの制約の組は現クラスタでは無解だ」と前もって告げる。それこそスケジューリングを火消しから、証明可能な事前の正しさへと真に押し進めることである。
