# 第16章　装置通信：SECS/GEM のミリ秒治水

## シナリオ11　基幹装置 SECS/GEM の突発切断（T3 Timeout）に対するミリ秒級自動復旧
**背景**：12インチ工場リソグラフィ区の EUV 露光装置が、HSMS-SS over TCP/IP を介して EAP（Equipment Automation Program）と常時接続を維持し、リアルタイムの Job 配送と RMS レシピのダウンロードを担っている。
**問題**：午前03:17、EAP が装置に S2F41 リモートコマンドを発したものの S2F42 の応答が返らず、T3 Reply Timeout（45秒）が今にも発火しようとしている。接続は NOT SELECTED 状態へ移行し、装置の Control State は ONLINE/REMOTE から LOCAL へ転落、**ロット全体の露光がプラズマがまだ安定していない窓の中で凍結され、一秒滞留するごとに2.3万ドルが瀬戸際で燃えていく**。当直は MES が真っ赤に染まっているのを見るだけで、ネットワークなのか、装置スタックなのか、それとも EAP ドライバ自身がデッドロックしているのかを言い当てられない。
**必要なスキル**：HSMS 接続ステートマシン（CONNECTED/SELECTED/NOT-SELECTED）の判読、SECS-II メッセージ（SxFy）の解析、TCP ハーフオープン接続の検知、装置 Control State の復帰フロー。
**オープンソースツール**：`secsgem`（Python SEMI プロトコルスタック）、`Wireshark` + HSMS dissector、`tcpdump`、`Prometheus` による接続ヘルス計測。
**活用したエージェントの特性**：ロブスター OpenClaw の**ローカルスクリプト実行**が EAP ドライバの T3 タイマを監視し、Timeout 発火の8秒前に `secsgem` で Linktest.req を一発補って生存確認を行う——TCP ハーフオープンであって装置の本当の死ではないと確認したうえで、**子エージェント**がただちに HSMS Separate→Select の再ハンドシェイクを走らせ、SELECTED 状態を再び立ち上げて呑み込まれた S2F41 を再送する。同時に**Multi-Channel Gateway** が「T3 発火寸前→自己修復済み、所要740ms」のタイムラインを当直の Teams と現場の Andon ランプへ同期し、再接続前後のパケット対照を添える。
**エージェントなしの窮地**：エンジニアが叩き起こされ、VPN を繋ぎ、Wireshark を開いてパケットを取り、肉眼で SELECT.req/rsp を突き合わせる。ハーフオープン接続だと判断できた頃にはロットはとうに scrap となり、MTTR は軽く30分超に膨らむ。
**効果**：T3 切断の自己修復 MTTR は30分 → **740ミリ秒**。一バッチのウェハが廃棄を免れ、一回のインシデントで約280万ドルを守った。

> 💡 珠玉のひとこと
> 「Timeout は故障の終点ではなく、エージェント介入のスタートラインだ——人間はタイマがゼロになって初めて目を覚まし、機械はタイマが半分を過ぎた時点ですでに手を打っている。」

> 🔍 上級コメント──道はどこにあるか
> この事例はロブスターを「事後アラート」から「Timeout 前の先回り」へと押し進め、**予測的介入**という一本の道を指し示す。将来のエージェントは故障が確定するのを待たず、ステートマシンの遷移エッジで賭けに出るようになる。だが先回りの代償は誤判断だ——それは740msのうちに人間に代わって接続を握り直すが、それには「どのハンドシェイク動作が無人で通してよく、どれが人間の最終署名を残すべきか」を先に線引きする必要がある。真の工学的難題は再接続スクリプトにあるのではなく、エージェントの自信閾値を装置の物理的リスクレベルにいかに整合させるかにある。

## シナリオ12　EAP と装置の SECS メッセージ滞留（Message Queue Overflow）に対するスマート治水
**背景**：ある CVD 装置が idle 後に突然、連続アラームの嵐へ突入し、毎秒数百件の S5F1（Alarm Report）を EAP へ噴出し、EAP の受信キューが逆流し始めた。
**問題**：09:42、EAP の入站キューが常態の50件から **4.7万件の未消化**へ暴騰、ドライバの ack（S5F2）が返しきれず、装置側は EAP を失聯と誤判断、**collection event を進行中の他6台の装置の SECS ハートビートまで一斉に遅延**し、toolgroup 全体が連鎖 OFFLINE の危機に瀕する。メモリ水位は92%、あと90秒持ちこたえれば EAP プロセスは OOM で kill され、それは全区の host 通信が一斉に断たれることを意味する。
**必要なスキル**：SECS-II メッセージキューのバックプレッシャー分析、アラーム嵐の発生源特定、collection event レポートのトラフィック調整、EAP ドライバのメモリ水位管理。
**オープンソースツール**：`secsgem`、`RabbitMQ`（メッセージバッファ中継）、`Grafana`、`htop`/`pidstat`。
**活用したエージェントの特性**：ロブスターの**子エージェント**が入站トラフィックをリアルタイムでグルーピング統計し、4.7万件のうち93%が同一の温度制御 sensor のチャタリングに起因する重複 S5F1 であることを突き止める。**ClawHub の既製スキルプラグイン**が「SECS Alarm デバウンス」skill をロードし、当該 ALID に秒級のスロットリングを掛け、装置に S5F3（Enable/Disable Alarm Send）を補って一時的にこのノイズ源を黙らせる。同時に滞留した有効メッセージを RabbitMQ のバイパスへ導き、ゆっくり消化させる。**Multi-Channel Gateway** はグループに「queue 4.7万→600へ治水済み、OOM リスク解除」の水位曲線を貼り出す。
**エージェントなしの窮地**：人間はまず EAP に SSH してキューを見て、次にアラームログを繰ってどの sensor かを探し、手動で S5F3 を打つ——この一連を走らせ終える頃には EAP はとうに OOM killer に持っていかれ、6台の装置もろとも脱落する。
**効果**：キュー水位は4.7万 → 600件。EAP は OOM を免れ、toolgroup の連鎖切断はゼロ、治水所要は **22秒**。

> 💡 珠玉のひとこと
> 「メッセージ滞留はそもそも水道管が細すぎるからではなく、漏れている蛇口を誰も閉めに行かないからだ——治水の知恵は、半分が排水にあり、半分が源探しにある。」

> 🔍 上級コメント──道はどこにあるか
> ここでロブスターがやったのは「バッファの拡張」だけではなく、**源流をたどる絞り込み**であり、これは「根本治療型のトラフィック治理」という道を指し示す。だが装置に S5F3 を打って特定のアラームを止めることは、本質的にエージェントがエンジニアに代わって「どのアラートを無視するか」を決めることだ——これは極めて危険な信頼境界である。止められた sensor がもし本物の異常の前兆だったらどうするのか。実装に当たっては、エージェントが「ノイズのチャタリング」と「本物の劣化の高頻度前兆」を区別できなければならず、それには単なるトラフィック統計ではなく装置のヘルスモデルを食わせる必要がある。

## シナリオ13　SECS キューオーバーフロー（Queue Overflow）のオンライン・スマート治水と動的アンロック
**背景**：量産の繁忙期、一つの EAP に同時に38台の装置がぶら下がり、host 側の SECS 送信キューは固定深度8192のリングバッファを採用している。
**問題**：14:05 の配工ピーク、EAP が装置群へ S16F11（Process Job Create）を一括投下し、出站キューが瞬時に8192を満たして**末尾のメッセージを破棄し始める**。3台の装置は Job を受け取れないのにエラーも出さず——静かに idle で止まり、**WIP がバッファ内に積み上がって擬似的な fab down となるが、生産ライン排程システムはすべて正常と表示する**。この「沈黙のスタック」はあからさまな機器停止より致命的で、OEE レポートが落ちてくる頃にはすでに2時間後だ。
**必要なスキル**：リングバッファのオーバーフロー検知、SECS 出站バックプレッシャーのモデリング、Process Job ライフサイクルの追跡、装置の idle 擬似死の識別。
**オープンソースツール**：`secsgem`、`Redis`（動的オーバーフロー用バイパスキュー）、`Prometheus`、`Locust`（負荷リプレイ）。
**活用したエージェントの特性**：ロブスターの**ローカルスクリプト実行**が「発信済み S16F11 数」と「受信した S16F12 ack 数」の差分を継続的に突き合わせ、差分がキュー深度と同期して8192へ迫った瞬間にオーバーフロー必至と判定する。**子エージェント**が出站深度を一時的に12288まで動的拡張し、オーバーフローしたメッセージを Redis のバイパス再送キューへ落とす。同時にその3台の idle 装置へ一台ずつ失われた Process Job を補って投下し、S16F12 を検証する。**Multi-Channel Gateway** が「沈黙のスタック3台→アンロックして再配工済み」を配工台と排程エンジニアへ送る。
**エージェントなしの窮地**：誰も「正常表示」のシステムを見に行きはしない。この3台の装置は産出が合わなくなって排程監査で暴かれるまで idle を続け、まるまる2時間分の生産能力を無駄に焼くことになる。
**効果**：キューオーバーフローの取りこぼしゼロ。擬似死装置は「2時間後にようやく発見」→ **即時再配工**。一回で約5千枚の WIP のストール時間を救った。

> 💡 珠玉のひとこと
> 「最も恐ろしいのはシステムがクラッシュして悲鳴を上げることではなく、平然とした顔で『すべて正常です』と告げてくることだ——治水の第一歩は、まずその平静を疑うことを学ぶことにある。」

> 🔍 上級コメント──道はどこにあるか
> この事例の価値は「沈黙の取りこぼし」を発見したことにあり、ロブスターを「突合型の可観測性」という道へ押し進める——いかなる単一のダッシュボードも信じず、発信／受領の差分から真相を炙り出す。将来このような突合能力は無人工場の免疫系統となるだろう。工学的難題はこうだ——エージェントが「正常表示」のシステムを疑い、自ら Job を再配工し始めると、それは既存の排程権威をバイパスすることになる。これには明確な「補償動作の追跡可能な台帳」が要る。さもなければ二つの自動化システムが同一バッチの WIP 上で喧嘩を始める。

## シナリオ14　HSMS メッセージスナップショットのタイムアウト（Linktest Timeout）のオンライン・スマート治水
**背景**：機房間の長距離配線下、ある計測装置（Metrology）が HSMS で EAP と接続し、周期的な Linktest でハートビートを維持している。
**問題**：02:50、機房間の光ファイバリンクに微細な突発ジッタが生じ、連続3回の Linktest.req が T6（5秒）以内に rsp を受け取れず、HSMS はリンク死亡と判定して Separate する。**だが装置は実際には生きており、CD-SEM 計測を実行中で、接続が切れると計測結果メッセージ（S6F11）がすべて装置側に積もって送り出せない**。EAP 側は無駄に再接続を繰り返し、再接続のたびに collection event を再購読して、せっかくクリアしたキューをまた灌ぎ戻す。
**必要なスキル**：HSMS の T5/T6/T7/T8 タイマ調整、光ファイバリンクのジッタ識別、計測結果メッセージの補送、再接続嵐の抑制。
**オープンソースツール**：`secsgem`、`mtr`/`smokeping`（リンク品質）、`Wireshark`、`fluent-bit`（メッセージ落地）。
**活用したエージェントの特性**：ロブスターの**子エージェント**が `mtr` を引いてリアルタイムに、装置の死ではなくリンクの jitter だと測り当てる。そこで EAP に強引な再接続を急がせず、**T6 を5秒から一時的に8秒へ動的に緩めて**ジッタの窓をやり過ごし、Separate を回避する。**ClawHub の既製スキルプラグイン**が「HSMS 再接続バックオフ」skill をロードし、残余の再接続に指数バックオフを掛けて再購読の嵐を断つ。リンクが安定したら**ローカルスクリプト実行**が装置を駆動して滞留した S6F11 計測メッセージを吐き出させ、data id の連番に漏れがないか照合する。**Multi-Channel Gateway** が「リンクジッタ収束、計測メッセージ漏れ0」をグループへ同期する。
**エージェントなしの窮地**：人間が直面するのは「装置は明らかに動いているのに繋がらない」という堂々巡りで、たいていは EAP ドライバをそのまま再起動してしまう——一度再起動すれば、バッチ全体の計測 context が失われ、CD-SEM データが wafer id へ照合できなくなり、計測が無駄になる。
**効果**：T6 を動的に緩めることで無駄な Separate を回避、計測メッセージの漏れ0。再接続嵐は消滅し、全装置の再購読を一巡（約4分）省いた。

> 💡 珠玉のひとこと
> 「心拍が止まったからといって人が死んだとは限らない、聴診器の接触が悪いだけかもしれない——リンクのジッタを装置の死と誤判断するのは、運用において最も高くつく藪医者の過ちだ。」

> 🔍 上級コメント──道はどこにあるか
> ここでロブスターの最も肝心な一手は**プロトコルタイマの動的調整**（T6 の一時緩和）であり、これは「適応型プロトコルパラメータ」という道を指し示す——将来のエージェントはアプリケーション層で救済するだけでなく、トランスポート層でも環境に応じてリアルタイムに調整できるようになる。これは巨大な能力の飛躍であり、同時に巨大な信頼境界でもある——HSMS タイマは SEMI 標準の一部であり、エージェントが勝手に緩めると一部のエッジケース故障が覆い隠されないか。実装に当たっては、この種の「調整」を監査可能・ロールバック可能・上限ありの安全な檻に閉じ込めねばならない。さもなければ適応は自己欺瞞へと退化する。

## シナリオ15　EAP と装置の通信メッセージ滞留の動的アンロック（Deadlock Breaking）
**背景**：あるイオン注入装置（Implanter）と EAP の間は厳格な SECS ハンドシェイク手順を採り、S6F11 一筆ごとに S6F12 ack を待ってから次の一筆を送る（同期ハンドシェイク）。
**問題**：11:30、装置と EAP それぞれの transaction id カウンタが一度の再接続でずれ、**装置は EAP の第N筆への ack を待ち、EAP は装置の第N-1筆への返答を待つ**——典型的なハンドシェイクのデッドロックだ。双方のキューにはそれぞれ千件超の互いに待ち合うメッセージが積もり、どちらも先に進もうとせず、装置の Control State は ONLINE のまま完全に動作を止め、**注入進行中の一炉の wafer が次の手順指令を得られず、ドーズの窓が流れ去っていく**。
**必要なスキル**：SECS transaction id（system bytes）の整合、同期ハンドシェイクのデッドロック識別、片方向 ack 注入によるアンロック、注入ドーズの時系列保護。
**オープンソースツール**：`secsgem`、`py-spy`（ハングしたスレッドのスナップショット）、`Grafana`、`jq`（メッセージログ解析）。
**活用したエージェントの特性**：ロブスターの**子エージェント**が両端の SECS log の system bytes をクロス突合し、transaction id のずれによる循環待ちだと一目で看破する。**ローカルスクリプト実行**が `secsgem` で整合用の S6F12 を一筆 EAP へ精密に補って注入し、循環を断ち切って古い方の一筆を先に決済させる。**ClawHub の既製スキルプラグイン**が「ハンドシェイク順序校正」skill をロードし、後続の system bytes を同一基準へ再整合して同期フローを回復する。**Multi-Channel Gateway** が「ハンドシェイク・デッドロック→注入してアンロック済み、注入ドーズの窓を死守」をデッドロック前後の transaction 図譜とともに装置エンジニアへ送る。
**エージェントなしの窮地**：ハンドシェイクのデッドロックは log 上では「双方とも正常に待っている」ように見え、人間にはきわめて識別困難で、標準動作は装置通信の reset だ——一度 reset すれば注入中の一炉のドーズ時系列が断裂し、一炉まるごと scrap となる。
**効果**：デッドロックを reset なしで解除。ドーズの窓を死守し、一炉約25枚の高価な wafer が廃棄を免れた。アンロック所要 **9秒**。

> 💡 珠玉のひとこと
> 「デッドロックの本質は双方とも規律を守りすぎていることだ——二つのシステムが互いに譲り合い、かえって誰も交差点を通れないとき、先に行くべき者をそっと押す一本の手が要る。」

> 🔍 上級コメント──道はどこにあるか
> これは本章で最も微妙な一手だ——ロブスターが**自らプロトコルメッセージを一筆注入して対称的な膠着を打ち破る**。それは「プロトコル層の調停者（arbiter）」という道を指し示す——エージェントはもはや単なる通路ではなく、二つのシステム間のハンドシェイク仲裁に介入できる存在となる。だがここは信頼境界が最も薄い場所でもある——ack を一筆間違って注入すれば、両端の状態を永久に不整合にしかねない。将来この「調停権」は、ハンドシェイク意味論の形式的理解の上に築かねばならず、かつ一回ごとの注入が双方のシステムによって事後に突合確認できねばならない——さもなければエージェントが一つのデッドロックを解くたびに、より深い不整合を三つ植え付けることになる。

## シナリオ16　GEM Collection Event レポート嵐（Report Flooding）の購読スリム化
**背景**：新規導入された成膜装置で、エンジニアが debug のために一時的に EAP へほぼ全 CEID（Collection Event）の DVVAL レポートを有効化し、後で閉じ忘れた。
**問題**：装置が量産に入るや、process step ごとに数十の CEID がトリガされ、CEID ごとにさらに百を超える DVVAL を抱え、**S6F11 メッセージが毎秒1.2MB の速度で EAP へ灌ぎ込む**。host 側の trace DB 書き込みのディスク IO が一気に飽和し、MES のクエリが全線で遅くなり、他の装置の正常なレポートまで巻き込まれて遅延する。
**必要なスキル**：GEM Report/CEID/DVVAL の購読関係の整理、S2F33/S2F35（Define Report/Link Event Report）の動的再構成、trace 書き込みのバックプレッシャー、必須 vs debug イベントの格付け。
**オープンソースツール**：`secsgem`、`TimescaleDB`（trace 時系列DB）、`Grafana`、`iotop`。
**活用したエージェントの特性**：ロブスターの**子エージェント**が S6F11 トラフィックの87%が純 debug 用の12個の CEID 由来であることを統計で割り出す。**ClawHub の既製スキルプラグイン**が「GEM 購読治理」skill をロードし、S2F35 を通じてこの12個の CEID と report の連結を動的に解除、量産に必須のイベントだけを残し、**全工程で通信を再起動しない**。**ローカルスクリプト実行**がスリム化前後の購読リストを保管して後の照査に備える。**Multi-Channel Gateway** が「レポートトラフィック1.2MB/s→180KB/s、ディスク IO 回復」を装置と IT 双方のグループへ送る。
**エージェントなしの窮地**：人間は装置の EDS（Equipment Data Spec）を手動で照らし合わせ、どの CEID が debug の残骸かを一条ずつ探し、慎重に S2F35 を打たねばならない——一条間違えれば量産必須の event まで閉じてしまいかねず、多くの人はトラフィックを我慢して手を出さないことを選ぶ。
**効果**：レポートトラフィックは85%減、ディスク IO の圧迫が解け、MES クエリ遅延が回復。購読治理は **全工程ゼロ中断**。

> 💡 珠玉のひとこと
> 「最大のトラフィック災害は、しばしば閉じ忘れた一つの debug スイッチに端を発する——可観測性に節度がなければ、それ自体が最大の不可観測へと化す。」

> 🔍 上級コメント──道はどこにあるか
> ここでロブスターは「購読の庭師」を演じ、GEM report を動的に剪定し、「自己治理する遥測平面」という道を指し示す。将来、装置と host 間のデータ購読の量級はますます増えるばかりで、人手で EDS 購読表を維持するやり方はいずれ破綻する。だがエージェントが「どのイベントを上報しなくてよいか」を代わりに決めるとき、それは工場のデータ境界を定義している——剪定された DVVAL が後日、異常の追跡時にちょうど必要になったらどうするのか。この道の工学的核心は、剪定を可逆・説明可能にし、下流のデータ需要者と契約的に協議することであって、一方的に黙って裁断することではない。

## シナリオ17　複数装置の SECS メッセージタイムスタンプ漂移（Clock Skew）の整合校正
**背景**：FDC（Fault Detection & Classification）システムは、各装置の S6F11 メッセージ内の timestamp に依拠して装置間の関連分析を行っている。
**問題**：一度の NTP サーバのジッタの後、工場内9台の装置のローカル時計が0.3〜2.1秒のばらつきで漂移し、**それらの上報する SECS timestamp が各自勝手なことを言い始めた**。FDC は同一の wafer の前後ステーションのデータの時系列が合わず、実在しない「異常な温度上昇トレンド」を一本誤検出し、それを根拠にあやうく一本の生産ラインまるごとを hold するところだった。
**必要なスキル**：SECS timestamp の時系列整合、複数装置の clock skew の定量化、FDC 関連ウィンドウの校正、NTP 漂移の補償。
**オープンソースツール**：`secsgem`、`chrony`（NTP 校時）、`InfluxDB`、`Pandas`（時系列の再整合）。
**活用したエージェントの特性**：ロブスターの**子エージェント**が既知の同期イベントを一筆基準として、9台の装置それぞれの時計オフセットを逆算する。**ローカルスクリプト実行**が SECS メッセージが FDC へ入る前に校正中継を一層噛ませ、各装置のオフセットに応じてリアルタイムに timestamp を補正、同時に `chrony` を駆動して装置を権威時計へ合わせ直す。**ClawHub の既製スキルプラグイン**が「時系列整合」skill をロードして FDC 関連ウィンドウを再計算し、**あの虚偽の温度上昇トレンドは即座に消え去る**。**Multi-Channel Gateway** が「時計漂移9台校正済み、FDC 誤検出撤回済み」を歩留まりと装置エンジニアへ送る。
**エージェントなしの窮地**：人間は FDC が報じた「温度上昇トレンド」に対し、まずそれを信じてしまう。そして hold 線、装置調査、case 起票——さんざん振り回された末にようやく誰かが装置の時計を照合してみようと思いつく。この間のライン停止損失は偽トレンドそのものを遥かに上回る。
**効果**：時計オフセットをリアルタイム補正、FDC の偽トレンドを撤回、全線の一度の誤 hold（約40分の停機）を回避。9台の装置の校時は10ms以内に収束。
**効果の補足**：ステーション間のデータ時系列が再び信頼可能となり、FDC 関連の正確率がベースラインへ回復。

> 💡 珠玉のひとこと
> 「データが合わないとき、慌てて装置を責めるな——多くの場合、それらの腕時計の時刻が初めから合っていないだけなのだ。」

> 🔍 上級コメント──道はどこにあるか
> この事例はロブスターを「データ信頼性の門番」という役回りへ押し進める——データが分析システムへ入る前に、その時間基準を先に校正する。これは「前置的なデータ治理」という道を指し示す——エージェントが遥測フローの洗浄ゲートとなる。工学的挑戦はこうだ——校正それ自体も一種の改竄である。エージェントは装置が上報した原始 timestamp を書き換えており、これは追跡とコンプライアンスにおいて敏感な動作だ。将来これを通すには「原始値と校正値が併存して痕跡を残す」ことを実現し、校正を透明で監査可能にせねばならない。洗浄後のデータが原始の真相を僭称してはならない。

## シナリオ18　SECS-II メッセージ構造の不正（Malformed SxFy）のオンライン遮断と隔離
**背景**：ある旧型装置がファームウェア更新後、SECS-II body 構造が SEMI E5 規範に合わない畸形の S6F11（list 長さフィールドが実際の item 数と一致しない）を散発的に吐くようになった。
**問題**：07:20、EAP ドライバの SECS-II parser がこの畸形メッセージにぶつかって即座に例外を投げる。**しかも全入站メッセージに対して単一スレッドの逐次解析を行っている**ため——一筆の畸形メッセージが解析チェーン全体を詰まらせ、後ろに並ぶ正当なメッセージがすべて堰き止められ、この装置の全上報が瞬時に「全黒」となり、alarm すら送り出せなくなる。
**必要なスキル**：SECS-II E5 構造の検証、parser 異常の遮断、畸形メッセージの隔離とバイパス、装置ファームウェアの互換性判読。
**オープンソースツール**：`secsgem`、`Hypothesis`（構造ファズテスト）、`Sentry`（異常集約）、`jq`。
**活用したエージェントの特性**：ロブスターの**ローカルスクリプト実行**が parser の前段に軽量な構造プリチェックを一道置き、この list 長さの合わない畸形 S6F11 を真っ先に捕まえ、**それを遮断して主解析チェーンへ入れず**、後続の正当なメッセージは普段どおり流す。**子エージェント**が畸形メッセージを丸ごとバイパスして落地させ、`Hypothesis` で畸形 pattern を逆算し、ファームウェアの某バージョンが特定の DVVAL の組み合わせ下で起こすエンコーディング bug だと突き合わせる。**ClawHub の既製スキルプラグイン**が再現条件を含む設備異常票を自動生成してメーカーへ送る。**Multi-Channel Gateway** が「畸形メッセージ隔離済み、主チェーン無中断、根因はファームウェア vXX の疑い」を同期する。
**エージェントなしの窮地**：人間が目にするのは「装置が完全に無音」という状態で、まず切断と決めつけてネットワークや接続を調べ、大回りした末にようやく一筆の畸形メッセージが parser を窒息させたと気づく——この間、装置は事実上ブラックボックスで、いかなる alarm も送り出せず、リスクエクスポージャは甚大だ。
**効果**：畸形メッセージを遮断隔離、主解析チェーンは0中断。装置「全黒」時間は潜在的に数十分 → **0秒**。付随して再現可能なファームウェア bug 票を一枚交付。
**効果の補足**：parser 逐次デッドロックという単一障害点のリスクがバイパスで解消された。

> 💡 珠玉のひとこと
> 「一筆の畸形メッセージに解析チェーン全体を窒息させる力があってはならない——真の堅牢さとは、誤りを出さないことではなく、一つの誤りがその隣へ伝染できないようにすることだ。」

> 🔍 上級コメント──道はどこにあるか
> ここでロブスターがやったのは「プロトコル層の遮断と隔壁隔離」であり、「耐障害通信ゲートウェイ」という道を指し示す——一筆ごとのメッセージを信頼できない入力として防御する。これは数十年標準で装置ファームウェアの良し悪しがまちまちな SECS/GEM のような場では特に肝心だ。次なる工学的問題はスケールである——エージェントが遮断・バイパス・異常票の自動起票を始めると、それは人とメーカーの間の緩衝層となる。本物のプロトコル劣化までも「過度に寛容に」遮断して問題を覆い隠してしまうことをいかに避けるか、耐障害と甘やかしの間に引くべきその一線こそ、この道で明確化せねばならないものだ。

## シナリオ19　装置 Control State の想定外の転落（Online→Local）の自動復帰
**背景**：生産ラインの規定では、装置が EAP のリモート配工を受けるには GEM の ONLINE/REMOTE 状態を維持せねばならないが、オペレータが装置パネルを誤操作して LOCAL へ切り替えてしまうことが時折ある。
**問題**：夜勤21:40、ある PVD 装置がオペレータに不用意に ONLINE/LOCAL へ切り替えられ、**EAP の S2F41 リモートコマンドがすべて装置に「not in remote」で拒絶される**。だが MES の画面では装置はなお緑ランプ（接続正常）で、いかなる alarm もなく、配工は黙って拒絶され続け、**WIP がこの装置の前で無音のうちに堆積し、1時間後に現場の人間が通りかかってようやくずっと idle だったと気づく**。
**必要なスキル**：GEM Control State Model の理解、S1F17/S1F15（Request ONLINE/OFFLINE）の操作、リモート復帰とオペレータ権限の境界、黙殺拒絶の検知。
**オープンソースツール**：`secsgem`、`Node-RED`（状態フローの可視化）、`Prometheus`、`Alertmanager`。
**活用したエージェントの特性**：ロブスターの**ローカルスクリプト実行**が各装置の S1F3（Selected Equipment Status）内の Control State を周期ポーリングし、この装置が REMOTE から LOCAL へ転落して3分間配工がないことを発見する。**子エージェント**がこの時点で誰も装置前で手動メンテをしていない（maintenance lockout マークなし）と判断し、S1F17 で装置に ONLINE/REMOTE へ戻すよう要求し、拒絶された S2F41 を補って送る。**Multi-Channel Gateway** は知らせるだけでなく、「装置が LOCAL へ切られた→REMOTE へ復帰済み、誰がいつ切ったか」をパネル操作のタイムラインとともに現場の班長へ送り、復帰と責任追跡を兼ねる。
**エージェントなしの窮地**：緑ランプが点いていて alarm もないとなれば、誰も「正常に見える」装置がストライキ中だとは疑わない。たいていは WIP レポートの異常か引き継ぎ巡検まで発見されず、まるまる1時間分の生産能力を失う。
**効果**：Control State 転落は「1時間後に巡検で発見」→ **3分以内に自動復帰**。付随して操作追跡を提供し、再発を断つ。

> 💡 珠玉のひとこと
> 「緑ランプは稼働中を意味しない——装置の最も危険な状態は、健康なランプを点しながら、一方ですべての指令を静かに拒絶していることだ。」

> 🔍 上級コメント──道はどこにあるか
> この事例はロブスターを「通信運用」から「状態治理」へと踏み込ませ、「装置状態の能動的巡査と復帰」という道を指し示す。その価値は、工場のために「接続は正常だが行動は失能している」という人間のダッシュボードでは照らせない盲点を見張ったことにある。だがオペレータに代わって装置を REMOTE へ戻すことは、エージェントが物理現場の権限を越える一歩だ——もしオペレータがメンテのために LOCAL へ切ったのなら、エージェントの強制復帰は安全リスクをもたらしかねない。実装の鍵は、エージェントが現場の「メンテ意図」信号（lockout/tagout 状態）を確実に読み取れるようにし、自動復帰を「人為的意図なし」の前提内に厳格に限定することにある。

## シナリオ20　量産ライン切替時の SECS レシピダウンロード失敗（Recipe Download Mismatch）の自動検証ロールバック
**背景**：product 切替の際、EAP は S7F3（Process Program Send）で新しい RMS レシピを装置へダウンロードし、ダウンロード後に S7F5 で取り戻して一致を比較確認せねばならない。
**問題**：02:05 の夜勤ライン切替、ある EUV レシピが S7F3 ダウンロードの過程でパケット再送が起き、装置に落地したレシピが EAP のソースより**末尾に14バイトの残留物が多くなった**。だが装置が返した S7F4 の ack code は0（受理）だった。**このまま通せば、次の一炉の wafer は汚染されたレシピで露光され、バッチまるごと scrap となり、しかも ack が成功を示しているため、事後にダウンロード汚染だと追うのはきわめて困難だ。**
**必要なスキル**：S7F3/S7F4/S7F5 のレシピダウンロード・ハンドシェイク、PPID/PPBODY 内容の検証（hash 比較）、レシピ汚染のロールバック、ライン切替の通過 gating。
**オープンソースツール**：`secsgem`、`xxd`/`hexdump`（バイト級比較）、`git`（レシピバージョンの痕跡保存）、`Prometheus`。
**活用したエージェントの特性**：ロブスターの**ローカルスクリプト実行**が S7F4 で ack=0 が返っても軽信せず、ただちに S7F5 を発して装置に実際に落地した PPBODY を取り戻し、EAP のソースに対して SHA-256 でバイト単位比較を行い、**あの14バイトの末尾残留物を炙り出す**。**子エージェント**がレシピ汚染と判定し、この装置のライン切替の通過を自動で阻止（gating）し、クリーンな S7F3 を一度再送、hash が一致するまで再検証してから gating を解除する。**ClawHub の既製スキルプラグイン**がこのバージョンのレシピのソース hash と落地 hash を併せて `git` へ書き込み痕跡を残す。**Multi-Channel Gateway** が「レシピダウンロード汚染14B→再ダウンロードして一致を検証済み、ライン切替通過」をライン切替エンジニアと品質保証へ送る。
**エージェントなしの窮地**：ack=0 は装置が「ちゃんと受け取った」と言っていることを意味し、人間はまずレシピ内容をバイト単位で再照合などしない。こうして汚染レシピが堂々とラインに乗る——この種の事故はたいていバッチ全体の wafer 計測が異常になり、log をさかのぼって翻してようやく発覚し、損失はバッチ単位で計上される。
**効果**：レシピ汚染を露光前に食い止め、バッチ全体の EUV wafer（約400万ドル）が scrap を免れた。ライン切替の通過は「ack 頼みの盲信」→ **hash 級の強検証**、全工程でバージョン痕跡を付随。

> 💡 珠玉のひとこと
> 「装置が『ちゃんと受け取った』と言うことと『本当に正しく受け取った』ことは別物だ——百万ドルの賭けの卓では、唯一信じられる ack は、自分の手で照合したあの一連の hash だけだ。」

> 🔍 上級コメント──道はどこにあるか
> これは本章の大トリであり、信頼哲学の縮図でもある——ロブスターは**プロトコル層の ack を信じることを拒み、エンドツーエンドの内容検証をやり抜く**。それは「ゼロトラスト・レシピ管理」という道を指し示す——一回ごとのライン切替を、暗号学的証明を必要とする一つの取引とみなす。これは無人工場で最も妥協できない一環である。なぜならレシピの誤りの代償はバッチ全廃棄だからだ。将来の工学的命題はこうだ——エージェントが「ライン切替の通過を食い止める」gating 権を握るとき、それは量産のリズムと品質安全の天秤の中央に立つ。検証をライン切替を遅らせないほど速く、1バイトも見逃さないほど厳しくし、かつ誤って食い止めた際に人間が最小コストで再確認して通過させられるようにすること——それがこのゼロトラストの道が真に一座の Lights-Out Fab を支えられるか否かを決める。
