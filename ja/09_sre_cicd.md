# 第9章　CI/CD とリリース：爆発半径を檻に閉じ込める

## シナリオ41　カナリアリリース(Canary)の微量異常ハンター
**背景**：日次アクティブユーザー三千万の決済ゲートウェイ。Argo Rollouts による段階的リリースを採用し、カナリアトラフィックを 1% → 5% → 25% → 100% の四段階で推進、各段階ごとに10分間観察する。
**問題**：深夜02:14、新バージョンが5%カナリアに到達。全体のエラー率はわずか 0.012% から 0.019% に上昇しただけ——ダッシュボード上ではほぼ一直線で、誰も二度見しない。しかしこの 0.007% の増分は、すべて「日本リージョン + Android + 分割払い」という交差領域に集中しており、この分岐の失敗率は実はひそかに11%まで跳ね上がっていた。25%段階でアラートが発火した頃には、すでに4.2万件の分割払い取引がロールバックされ、財務の照合作業を三日かけてやり直す羽目になった。
**必要なスキル**：逐次検定(SPRT)と統計的検出力(power)分析、多重検定補正(Benjamini-Hochberg/FDR)、最小サンプルサイズ推定、業務リスク加重の意思決定、Prometheus クエリ、リリース戦略設計
**オープンソースツール**：Argo Rollouts、Prometheus、Flagger、Grafana、statsmodels(`multipletests`)
**活用するエージェントの特性**：ロブスター(🦞)OpenClaw が ClawHub 上の `canary-slicer` スキルをマウント。それは「次元爆発」の真の罠が p 値を算出できないことではなく、**組み合わせ爆発が各スライスのサンプル数を希釈し統計的検出力を崩壊させること**だと熟知している。region(8)×OS(3)×payment(4)=96 個のスライス。5%カナリアは02:14の低ピーク時で毎秒の総リクエストが約 1.2k、これを `jp/android/installment` のようなロングテールスライスに分配すると毎分わずか40件程度——この状態では本当に問題があっても N が小さすぎて検出できず(偽陰性)、しかも96回の同時検定は必然的に大量の偽陽性(family-wise error)を生む。そこで子エージェントのフローはこうなる：(1) **まず統計的検出力を算出する**——各スライスについて、ベースライン失敗率 0.4%、検出したい効果量(≥3% への上昇)、α=0.05、power=0.8 を与え、必要な最小サンプルサイズ(約600件以上)を逆算し、**サンプル不足のスライスは無理に結論を下さず「データ不足、引き続き蓄積」とマークする**；(2) サンプルが十分なスライスに対して SPRT を実行し、一組の生の p 値を得る；(3) **Benjamini-Hochberg で FDR(目標5%)を制御する**ことでこの p 値群に多重検定補正を施す。素朴に 0.05 で一つずつ比較するのではなく——`jp/android/installment` は補正後の q 値が依然として < 0.01 でなければ有効とみなさない；(4) 決定的な最後のステップは**意思決定は p 値とイコールではない**ということ：p が有意というのは「劣化が本物である」ことを示すにすぎず、推進を停止すべきかどうかにはさらに業務上の重みを掛ける必要がある——当該スライスは総取引額の6%を占め、失敗率11%、毎分の流出は約¥X。子エージェントは「もし25%段階まで放流すれば予想損失は4万件/¥Y」と算出し、あらかじめ設定した「単一スライスで許容可能な損失」のしきい値を超えて初めて停止へとエスカレーションする。5%段階の90秒目、それは SRE グループにこう投げ込む：「⚠️ カナリアは全体として健全だが `jp/android/installment` で局所的悪化：N=640(検出力しきい値に到達済み)、失敗率11%(ベースライン0.4%)、BH補正後 q=0.008、25%まで放流した場合の予想損失は約4.2万件——**推進の一時停止を推奨**(ロールバックではなく、残り95スライスは正常)」。これにワンクリックの `kubectl argo rollouts abort`、当該スライスの trace サンプル、そして「その他のスライスに有意差なし」という反証テーブルを添える。
**エージェントがいない場合の苦境**：当番の SRE は滑らかな全体曲線を眺めながら安眠している；たとえ誰かが次元で切ろうとしても、二つの落とし穴にはまる——0.05 で96個のスライスを裸で走らせて偽陽性に溺れ信頼を失うか、ロングテールスライスの N が小さすぎることに気づかず「検出できなかった」を「問題ない」と取り違えるかだ。
**効果**：局所的劣化の検出が「25%段階、4.2万件の損失」から「5%段階、90秒、約600件の損失」へと前倒しされ、損失取引量は98.6%減少；しかも意思決定には検出力と多重検定補正が付随し、偽陽性による誤停止率は制御可能となる。

> 💡 珠玉のひとこと
> 「平均値は麻酔薬だが、p 値もまた別種の麻酔薬だ——96個の問いを同時に投げかければ、必ずどれか一つが『有意に』あなたを欺く。真の規律とは p を算出することではなく、まず『この問いを投げかけるだけのサンプルが自分にあるか』を問い、次に『たとえ本物だとしても、ライン全体を止める価値があるか』を問うことだ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例はカナリア分析を「しきい値アラート」から「検出力制御と FDR 補正を備えた分散仮説検定」へと押し進めた。だがグレーゾーンも正直に認めねばならない：検出力分析はまず「検出可能な最小効果量」を仮定する必要があるが、この数字自体は統計的に導出されたものではなく業務が決定したものだ；FDR が制御するのは「偽陽性の割合」であって「絶対に誤殺しないこと」ではなく、5%の q しきい値とは、たまに誤って停止することを受け入れるという意味だ。次なる道は、エージェントが過去のインシデントの事後分布を用いて**自動的に次元を剪定する**こと(七、八次元では96が数千スライスに膨れ上がり全検定は不可能)、そして「検出可能な最小効果量」と「許容可能な損失」というこの二つの決定パラメータを、ハードコードされた定数から、スライスごとの業務価値に応じて動的に調整される関数へと昇格させることだ。最も深い工学的難題は依然として**信頼の境界**にある：エージェントが「推進を一時停止する」と言ったとき、誰がそれを覆す権限を持つのか、一度の誤停止のコストをどうその目的関数に組み込むのか——統計的に厳密でも業務的に過敏なハンターは、それだけでパイプライン全体を身動きできなくすることができる。

## シナリオ42　CI/CD パイプラインの幽霊デッドロックの自動リトライと環境解凍
**背景**：200人のエンジニアリング組織が一本の GitLab CI パイプラインを共有しており、統合テスト段階ではステートフルなテストデータベースプール(8スロット)を奪い合う必要がある。
**問題**：金曜午後16:40、ある統合テストタスクが「DBスロットを取得した後、解放する前」に OOM Killer に殺され、スロットの分散ロックが解放されないまま残った。続いてすべての MR の統合テストが「スロット待ち」で詰まり始める——8スロットのうち3つが死に、スループットは半減、さらにリトライによって残り5つも埋め尽くされた。17:30には**147個のパイプラインが行列**をなし、リリース枠を逃しそうになり、グループ内では「また落ちたのか」という声が上がり始めた。
**必要なスキル**：分散ロック診断、CIスケジューラ運用、デッドロック検出、冪等性設計
**オープンソースツール**：GitLab CI、Redis(Redlock)、Kubernetes、Argo Workflows
**活用するエージェントの特性**：ロブスターの子エージェントは pipeline のキュー深度を常駐監視しており、「行列数 > 過去 p99 の3倍が5分間継続」したときに調査をトリガーする。それはローカルスクリプトで Redis 内のスロットロックをスキャンし、各ロックの holder PID と K8s 上で実際に生存している Job を突き合わせる——「保持者がすでに死んでいる」孤児ロックを3つ突き止め、**この3つだけを正確に解放する**(乱暴に全部クリアして実行中のタスクを誤殺するのを避ける)。それから詰まっていた pipeline に retry を発行する。完了後グループに同期する：「🔓 解凍完了：孤児DBロック3個を清掃(holder job は16:41に OOM 終了済み)、行列中の147個の pipeline をリトライ、キューは平常に回復。根本原因：テストフレームワークが `try/finally` でロックを解放していなかった、issue #2891 を起票済み。」
**エージェントがいない場合の苦境**：人間はまず「テスト自体が壊れたのではなくインフラが詰まっている」と気づき、次に Redis に SSH で入り、肉眼でロックとプロセスを突き合わせ、手動で `DEL` し、しかも実行中のものを消していないよう祈る必要がある——平均40分の格闘で、金曜午後に誰もこの貧乏くじを引きたがらない。
**効果**：環境解凍の MTTR が40分から50秒に短縮され、リリース枠を逃すのを回避；しかも根本原因の issue が自動的に記録され、「繰り返しの解凍」から「恒久的な修正」へと向かう。

> 💡 珠玉のひとこと
> 「デッドロックはコードの中で起きるのではない、コードが『実行し切れなかった』その一行で起きる；リソースの返却こそが、真の堅牢性なのだ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> 自動解錠は爽快だが、その本質は「他人の非冪等なコードの尻拭い」をしているにすぎない。ロブスターの進んだ道は、「受動的な解凍」から「能動的なリース統治」へと向かうことだ——各ロックに TTL と owner ハートビートを付与し、エージェントをリソースの「破産管財人」にする。実装上の工学的難題は**規模における因果の帰属**にある：147個の詰まったタスクのうち、どれが本当のデッドロックの被害者で、どれが単に自分が遅いだけなのか？エージェントがひとたび「遅い」を「死んだ」と誤判定してリトライすれば、雪崩をさらに大きく押し進めてしまう。

## シナリオ43　IaC 構成ドリフト(Configuration Drift)の自動修正 PR
**背景**：インフラはすべて Terraform で管理され、状態は S3 に保存、理論上は「コードこそが真理」である。だが本番環境には6つのチーム、3000を超えるクラウドリソースが存在する。
**問題**：あるオンラインの火消し作業で、一人のエンジニアが出血を止めるため、AWS Console で手動である RDS の `max_connections` を200から800に変更したが、事後 Terraform への書き戻しを忘れた。三週間後、別のチームが無関係な変更をデプロイしようと `terraform apply` を実行したところ、Terraform は差分を検出して**勝手に接続数を200に戻してしまった**。折しもトラフィックのピーク時で、接続プールは瞬時に枯渇、API の 5xx が23%まで急騰し、8分間続いた。
**必要なスキル**：Terraform 状態管理、ドリフト検出、クラウド API 監査、変更リスク評価
**オープンソースツール**：Terraform、driftctl、Atlantis、OpenTofu
**活用するエージェントの特性**：ロブスターは30分ごとに `driftctl scan` で全アカウントに対してドリフトスキャンを行う。帯域外(out-of-band)の変更を発見したとき、それは軽率に「修正」したりはせず、逆に意図を判断する：CloudTrail を呼び出して「誰が、いつ、なぜ」この値を変えたのかを突き止め、これが誤操作ではなく**意図的な火消しの変更**であることを識別する。そこでそれは PR を生成する——`max_connections = 800` を `.tf` に書き戻し、PR の説明には CloudTrail の証拠、インシデントチケットのリンク、そして「この値は人手による火消しで設定されたもの、保持を推奨」という判断を自動的に添え、当該リソースの owner にレビューを依頼する。「沈黙のドリフト」を「監査証跡のあるコード変更」へと転換するのだ。
**エージェントがいない場合の苦境**：ドリフトは次回の apply で爆発するまで無視されるか、人が定期的に数千リソースの diff を手動レビューするかのどちらかだ——そんな根気のある者はおらず、こうしてドリフトは頭上に懸かるランダムな爆弾となる。
**効果**：ドリフトが「平均23日潜伏した後 apply で爆発」から「30分以内にレビュー可能な PR へ収束」へと変わり、構成ドリフトに起因するインシデントはゼロになる。

> 💡 珠玉のひとこと
> 「IaC の嘘は、コードが間違って書かれていることではない。コードが自分をまだ真理だと思い込んでいる一方で——本番環境はとっくにこっそり現実を書き換えていることなのだ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例の真髄は「ドリフトの検出」にあるのではなく、「ドリフトをロールバックすべきか受け入れるべきかをエージェントが判断する」ことにある。未来の道は、エージェントを**意図の考古学者**にすることだ：あらゆる帯域外変更の背後には人間のトレードオフがあり、盲目的な修正は応急処置を消し去ることに等しい。工学的課題は「修正権限の段階分け」にある——エージェントは余分なタグを一つ自動修正できるが、データベースパラメータを一つ自動で書き戻す勇気はあるか？この信頼のレッドラインは、その判断精度が上がるにつれて一マスずつ前へとずれていく。

## シナリオ44　製品ラインの秘密ローンチを SRE に通知しなかったアーキテクチャ準拠監査
**背景**：会社には「ローンチ前に SRE の容量・可観測性レビューを通すべし」という厳格な規定があるが、業務プレッシャーの下、「迅速な実験」の名目でプロセスを迂回し、新サービスを直接本番 K8s にリリースするチームが必ず現れる。
**問題**：ある成長チームがこっそり「AIレコメンド」マイクロサービスをローンチした。SLOなし、レート制限なし、アラート接続なし、容量評価もなし。それは共有の下流ユーザーデータサービスの QPS をひそかに40%も押し上げた。二日後、マーケティングキャンペーンの波が重なると、その下流サービスが真っ先に過負荷で雪崩を起こし、**それに依存する7つのコアサービスを道連れ**にして、全サイト可用性が96.8%まで低下した。だが SRE はきょとんとしていた——この元凶がそもそも彼らのレーダーに映っていなかったからだ。
**必要なスキル**：サービストポロジー発見、準拠ポリシーのコード化(Policy as Code)、容量計画、依存関係分析
**オープンソースツール**：OPA(Open Policy Agent)、Kubescape、Backstage、Kyverno
**活用するエージェントの特性**：ロブスターの子エージェントは本番クラスタを「継続的な国勢調査が必要な領地」とみなし、毎時間「実際に稼働している Deployment 一覧」と「Backstage サービスカタログ + レビュー記録」を突き合わせる。「稼働中だが、レビュー記録なし、SLOなし、PodDisruptionBudget なし」の幽霊サービスを捕まえるや、ただちに準拠グループに通報し、自動生成した依存関係図を添える：「🚨 未申請ローンチを発見：`reco-ai-svc`(稼働2日)、レート制限なし、アラートなし、かつ `user-profile-svc` に +40% QPS を注入、後者の残容量はわずか18%。**爆発半径：7つのコアサービス**。即座のレート制限追加とレビューを推奨。」
**エージェントがいない場合の苦境**：SRE は事故後のインシデント RCA を行うときになって初めて、「先週サービスが一つ増えていたのか」と愕然とする——準拠はすべて人の自覚頼みであり、その自覚は deadline の前では一文の価値もない。
**効果**：未申請サービスが「平均2日潜伏した後にサービス横断の雪崩を引き起こす」から「ローンチ1時間以内に準拠監査で捕獲」へと変わり、爆発半径を事前に定量化、可用性インシデントを未然に防ぐ。

> 💡 珠玉のひとこと
> 「プロセスは deadline に追われる人を抑え込めない；ただ『プロセスを迂回する』という行為そのものを、プロセスを踏むよりも目立たせることだけが効く。」

> 🔍 一歩進んだ論評──道はどこにあるか
> 準拠が「ローンチ前のゲート」から「ランタイムの継続的国勢調査」へと進化する、これは重要なマインドセットの転換だ——ゲートは迂回できるが、国勢調査からは逃れられない。ロブスターの次なる道は、この能力を「トポロジー認識の容量門番」に変えることだ：幽霊サービスを発見するだけでなく、それがトラフィックを注入する瞬間に下流の残容量を見積もる。工学的難題は**自動化の政治的境界**にある：エージェントが公然とあるチームの違反を名指しするとき、それが演じるのは監査官か、それとも密告者か？自動監査に牙を持たせつつエンジニアの信頼を損なわないようにすることは、技術よりも難しい組織の課題だ。

## シナリオ45　全自動カナリアのトラフィック染色(Traffic Coloring)とグレーリリース監査
**背景**：Istio ベースのサービスメッシュ、マイクロサービス間の呼び出しは何層もネストし、深さは12ホップに達する。新バージョンのグレーリリース時、最も外側の入口でのみ1%のトラフィックを染色する。
**問題**：チームは「入口で1%染色 = 全リンクの1%が新バージョンを通る」と思い込んでいたが、途中のあるサービスのルーティングルールが誤って書かれており、染色されたトラフィックを第4ホップで全量、旧バージョンの下流に再注入していた。その結果、**カナリアは本当に検証したかった新しいパスをそもそもカバーしていなかった**。新バージョンはローンチ時すべて「グリーン」、全量化した後に初めて爆発した。テストされていたのがそもそも新ロジックではなかったからだ。この「偽カナリア」はリリースサイクル全体を騙し切った。
**必要なスキル**：サービスメッシュのトラフィック統治、分散トレーシング、染色タグの伝播(baggage propagation)、グレーリリース監査
**オープンソースツール**：Istio、OpenTelemetry、Jaeger、Kiali
**活用するエージェントの特性**：ロブスターは ClawHub の `trace-color-audit` スキルをマウントし、グレーリリース期間中に染色された(`x-canary: true`)リクエストの完全な Jaeger trace を取得し、**染色タグが12ホップの間ずっと生存しているか、かつ各ホップで新バージョンの subset にヒットしているかをホップごとに検証する**。それは染色トラフィックが `order-svc`(第4ホップ)で断裂——タグが失われ、旧バージョンへ再注入されていることを発見する。ただちに通報する：「⚠️ カナリア染色リンクが第4ホップ `order-svc` で断裂：その VirtualService が `x-canary` baggage を透過伝播しておらず、新バージョンの実カバー率は0%(期待値1%)。**これは偽グレーリリースだ**、タグ修正前の全量化を禁止することを推奨。」そして断裂点の trace と修正後の Istio 設定 diff を添える。
**エージェントがいない場合の苦境**：人間は入口の1%染色が成功したのを見て安心してしまい、12層の trace をホップごとに追って染色タグが最後まで生きているか確認する者などいない——全量化して爆発して初めて振り返り「カナリアは偽物だった」と気づくのだ。
**効果**：偽グレーリリースが「全量化後に初めて露呈、リリースサイクル一つ分の信頼を損失」から「グレーリリース最初の1時間以内に監査で捕獲」へと変わり、カナリアの有効カバー率が「自分で思っていた1%」から「本物の1%」へと較正される。

> 💡 珠玉のひとこと
> 「最も危険なのはカナリアが死ぬことではなく、カナリアがそもそも炭鉱に入っていないことだ——テストしているつもりで、実は丸裸で突っ走っているのだ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例はグレーリリース最も隠れた嘘を暴いた：「染色カバー率」と「実検証カバー率」の間に横たわる溝だ。ロブスターの進んだ道は、「グレーリリースの監査官」になることだ——何をデプロイしたかは問わず、ただ『本当に何をテストできたか』だけを問う。実装上の工学的課題は**タグ伝播の全リンク契約**にある：Kafka の非同期があり、キャッシュのバイパスがあり、サードパーティのブラックボックスがある現実のシステムでは、baggage は必ずいくつかの境界で蒸発する運命にある。エージェントは「合理的な染色の断点」と「致命的な染色の断裂」を区別することを学ばねばならない、さもなくばその監査レポートは誤報の中に埋もれてしまう。

## シナリオ46　依存チェーン高危険脆弱性のリリースゲート(Supply Chain Gate)による即時遮断
**背景**：毎日数百回マージされる CI パイプライン、サービスは数千のサードパーティパッケージに依存し、SBOM(ソフトウェア部品表)はビルド段階で生成される。
**問題**：広く依存されているあるログライブラリ(Log4Shell 風シナリオ)が、土曜の未明に RCE 0-day を露呈、CVSS 9.8。問題はそのライブラリが直接依存ではなく、**透過依存の第6層**にあり、SBOM の深部に潜んでいたことだ。月曜の朝にいつも通りリリースすれば、既知のバックドアを自らの手で本番にデプロイするに等しい。だがリリース前に千個のパッケージの6層依存ツリーを手動でめくる者などいない。
**必要なスキル**：ソフトウェアサプライチェーンセキュリティ、SBOM 解析、脆弱性インテリジェンスの関連付け、リリースゲート設計
**オープンソースツール**：Trivy、Grype、Syft、OSV-Scanner
**活用するエージェントの特性**：ロブスターの子エージェントは OSV と GitHub Advisory の脆弱性インテリジェンスフローを購読しており、新しい CVE が公開されるや `osv-scanner` で**すべてのリリース待ち artifact の SBOM に対して逆方向の突き合わせを行う**——直接依存だけを見るのではなく、依存ツリー全体を貫通する。土曜03:00、それはセキュリティグループでアラートを出す：「🛑 リリースゲート遮断：`payment-api:v2.4.1` は透過依存で `logj-core 2.14.1`(第6層、`audit-sdk → log-bridge` 経由で引き込まれた)を含み、CVE-2026-XXXX CVSS 9.8 RCE にヒット。すでに**当該 artifact の promote 権限を自動凍結**、2.17.x へのアップグレード PR を生成済み。」完全な依存パスと影響を受ける17の下流サービス一覧を添える。
**エージェントがいない場合の苦境**：セキュリティチームは各脆弱性インテリジェンスを手動で追跡し、プロジェクトごとに SBOM をめくって6層の依存を突き合わせる必要がある——この作業は遅すぎて、脆弱性はしばしば「ニュースになって初めて自分が被害に遭ったと知る」もので、そのときバックドアはすでに本番で数日走っているかもしれない。
**効果**：高危険な透過脆弱性の発見が「人手のインテリジェンス追跡頼み、平均数日」から「CVE 公開後 < 10分で自動的にリリース凍結」へと圧縮され、既知の脆弱性を本番環境の中ではなく promote ゲートの外で食い止める。
> 💡 珠玉のひとこと
> 「あなたは自分のコードをリリースしているつもりだが、実は千人の見知らぬ他人が書いたコードをリリースしている——そして自分の書いたその一行しか読んでいない。」

> 🔍 一歩進んだ論評──道はどこにあるか
> サプライチェーンゲートはセキュリティを「promote の最後の門」まで左シフトさせた、これは DevSecOps の重要な飛躍だ。ロブスターの次なる道は、「遮断」から「自律的修復と回帰」へと向かうことだ：凍結するだけでなく、自動でアップグレード PR を起票し、互換性テストを走らせ、アップグレードの破壊性を評価する。工学的難題は**ゲートの裁断権**にある——CVSS 9.8 は堂々と遮断できるが、CVSS 5.3 で、しかもそもそもトリガーされていない脆弱性はリリースを止めるべきか？過度に厳格なゲートはエンジニアにそれを迂回することを覚えさせ、その瞬間サプライチェーンセキュリティは名ばかりのものになる。到達可能性分析(reachability)がこの道の次の技術的深淵となるだろう。

## シナリオ47　データベースマイグレーション(Schema Migration)とコードリリースの順序デッドロック事前チェック
**背景**：ブルーグリーンデプロイを採用、アプリ層のリリースは頻繁。データベースの schema 変更は独立した migration パイプラインを通る。二本のパイプラインは異なるチームが管理し、調整はすべて Slack の掛け声頼みだ。
**問題**：あるリリースで、バックエンドエンジニアが「`users.legacy_token` カラムを削除する」migration を書き、新バージョンのコードでその参照を取り除く計画だった。だがリリース順序が逆になった——migration が新バージョンのコードより**先に**ローンチされ、まだ稼働中の旧バージョンのコードは依然として削除済みのそのカラムを SELECT していた。瞬く間に、ログインサービスが100% `Unknown column` を返し、全サイトのログインが6分間ダウン、migration を緊急ロールバックするまで続いた。これは典型的な「破壊的変更に後方互換を施さなかった」ケースだ。
**必要なスキル**：データベース変更管理、後方互換性分析(expand-contract)、リリースオーケストレーション、静的コードスキャン
**オープンソースツール**：Flyway、Liquibase、gh-ost、Atlas
**活用するエージェントの特性**：ロブスターは migration PR が CI をトリガーしたときに介入し、ローカルスクリプトでこの migration の AST を解析、「DROP COLUMN `legacy_token`」が**破壊的(destructive)操作**であることを識別する；続いてそれは**現在本番で稼働中のコードバージョン**の全コードベースを逆スキャンし、依然として `legacy_token` を参照している箇所を14か所 grep し出す。衝突を判定するや、ただちにこの PR を block して通報する：「🛑 危険なマイグレーションを遮断：`DROP COLUMN users.legacy_token` は現在の本番コードと衝突——14か所がまだ参照している(一覧参照)。expand-contract 原則に違反。正しい順序は：①まずコードをリリースして参照を取り除く → ②二週間の観察期間 → ③その後 DROP すべき。分割後の安全な migration を添付済み。」
**エージェントがいない場合の苦境**：リリース順序の正しさは、すべて「二つのチームが Slack ですり合わせたかどうか」という口頭契約に懸かっている——人が忙しいとき、交代したとき、誤解したとき、破壊的 migration が先に走ってしまい、データベースの DROP は覆水盆に返らずだ。
**効果**：破壊的 schema 変更によるオンライン障害が、「人の調整頼み、稀だが起きれば毎回致命的」から「CI 段階で100%遮断」へと変わり、自動的に変更を expand-contract に準拠した安全なシーケンスへと分割する。

> 💡 珠玉のひとこと
> 「コードのバグはロールバックできるが、DROP COLUMN はできない——データベースの時間には、一方向の矢印しかない。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例は「人間の口頭調整によるリリース順序」を「機械が検証可能な互換性契約」へと固定化した。ロブスターの進んだ道は、パイプライン横断の**リリースオーケストレーション官**になることだ：block するだけでなく、「まず A をリリース、観察、その後 B をリリース」という多段階の脚本を能動的にオーケストレーションし、各段階の間に検証関門を配置できるべきだ。工学的課題は**チーム横断の状態の真正性**にある——エージェントが「コードがまだあるカラムを参照している」と判断するのは、把握している『現在の本番バージョン』が正確であることに依存するが、マルチリージョンで、グレーリリース中で、バージョンがまちまちな現実の艦隊では、「現在の本番が一体どのバージョンを走らせているのか」そのものが難題なのだ。

## シナリオ48　ロールバックストーム(Rollback Storm)の根本原因特定と止血の意思決定
**背景**：40個のマイクロサービスから成る EC プラットフォーム、各サービスは独立してリリースされる。リリースツールはワンクリックロールバックに対応し、チームも「アラートが鳴ったらまずロールバックしてから考える」という筋肉の記憶を身につけている。
**問題**：木曜の夜のピーク時、決済成功率が突然99.5%から91%に落ちた。アラートが鳴るや、五つのチームが**同時に、それぞれ独立して**自分たちの直近のリリースをロールバックした——結果、成功率は上がるどころか84%まで下がった。そのうち三つのサービスのバージョンが互いに非互換な古い組み合わせにロールバックされ、かえって新たなプロトコルの不整合を生んだからだ。これは「パニック駆動のロールバックストーム」だ：誰もが火を消そうとしていたが、彼らのホースは互いにぶつかり合い、本当の火元がどこにあるのか誰も知らなかった。
**必要なスキル**：変更関連分析、分散根本原因特定、リリース依存モデリング、止血の意思決定
**オープンソースツール**：ArgoCD、Sentry、Tempo、Grafana
**活用するエージェントの特性**：ロブスターの子エージェントは「サービスのバージョン互換性 + 直近の変更タイムライン」という一枚の図を維持している。成功率が低下したとき、それはパニックに追従せず、「直近30分の全サービスのデプロイイベント」と「エラー率の急変点」を時系列で関連付け、90秒以内に特定する：エラーは実際には `coupon-svc:v3.2` のデプロイから始まっており、しかもこれが急変点の時刻と一致する**唯一の**変更だった。それはただちに指揮グループで制止をかける：「🧯 止血指令：根本原因 = `coupon-svc:v3.2`(20:31デプロイ、成功率の変曲点と完全に一致)。**他のサービスを盲目的にロールバックしないこと**——`payment/order/cart` のロールバックはバージョンの不整合を引き起こし、かえって障害を悪化させる。推奨：`coupon-svc` のみロールバックし、その他は現状維持。」そしてバージョン互換性マトリクスを添える。
**エージェントがいない場合の苦境**：障害時、各チームは自分のサービスしか見えず、情報のサイロの中でそれぞれ盲目的にロールバックし、単一障害点をグローバルなバージョン混乱へとエスカレーションさせる——ロールバックは本来止血なのに、二次被害となってしまう。
**効果**：ロールバックストームの MTTR が「複数チームが互いに足を引っ張り合い、25分かけて救えば救うほど悪化」から「90秒で唯一の根本原因を特定、単一サービスを正確にロールバック」へと変わり、不要なロールバックによるバージョン不整合を回避する。

> 💡 珠玉のひとこと
> 「パニックのとき、人間の第一反応は『動くこと』だ；だが分散システムにおいて、最も貴重な能力は『誰が動かずにいるべきか』を知ることだ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> ロールバックストームの本質は、「局所最適な個々の意思決定」が積み重なって「グローバルな災害」になることだ——これは分散システムの縮図であり、組織の縮図でもある。ロブスターの次なる道は、「根本原因の助言者」から「リリース艦隊のグローバル協調者」へと進化することだ。障害時に全サービスのロールバック操作に対して「アドミッション制御」を行使し、協調なき群衆行動を防ぐ。だがこれこそ最も深い信頼の境界だ：「ロールバックすべきか否か」の決定権をエージェントに委ねるとは、人間が最もパニックに陥り、最も自分の手で何かしたいと思う瞬間に、機械が彼に『動くな』と言うのを信じることを選ぶという意味だ。この直感に反する信頼は、エージェントが一度また一度と正確な止血を重ねることで、徐々に勝ち取っていく必要がある。

## シナリオ49　フィーチャーフラグ(Feature Flag)墓場の清掃とリリース技術的負債の監査
**背景**：チームはフィーチャーフラグ(LaunchDarkly 風)を多用して段階的リリースと A/B テストを行っており、コードの中には数百もの `if (flag.isEnabled(...))` 分岐が散在している。
**問題**：本来一時的に存在し、グレーリリースが終わったら削除すべきだったフラグ `new_checkout_flow` が、100%放量してから丸14か月経ってもまだ生きていた。ある日、定例の「フラグ設定の一括整理」がそれを誤って `false` に戻し、瞬時に全ユーザーをあの14か月誰もメンテしておらず、依存していた下流がとっくにオフラインになった**ゾンビ旧決済フロー**へと切り替えてしまった。決済は直ちに 500 を返し、GMV は11分間で数百万が蒸発した。「とっくに削除すべきだった死んだ分岐」が、一つの時限爆弾と化したのだ。
**必要なスキル**：技術的負債の統治、デッドコード分析(dead code detection)、フラグのライフサイクル管理、爆発半径評価
**オープンソースツール**：Unleash、OpenFeature、PIRANHA(デッドコード清掃)、SonarQube
**活用するエージェントの特性**：ロブスターの子エージェントは毎週フィーチャーフラグの「墓場監査」を行う：「フラグの評価データ(過去90日間あるフラグがずっと 100%/0% だったか)」と「コード中の参照」を突き合わせる。それは `new_checkout_flow` を捕まえる：「📋 ゾンビフラグ監査：`new_checkout_flow` は安定して100%放量が426日続いているが、コードには依然 `false` 分岐が残されており、しかもその分岐が依存する `legacy-payment-gw` は8か月前にオフライン化済み——**これは『誤トリガーされうる』状態の死んだ分岐であり、爆発半径=全サイトの決済だ**。PIRANHA で『有効をハードコード + 死んだ分岐を削除』の清掃 PR を自動生成することを推奨。」そして実際に PR を起票して人のレビューを待つ。
**エージェントがいない場合の苦境**：フィーチャーフラグは増えるばかりで減らず、どれがまだ生きていて、どれの off パスがとっくに腐っているか誰も覚えていない——技術的負債はコードの中で静かに蓄積し、ある日の手すべりによる誤トリガーが、本来存在すべきでない状態を本番の現実に変えるまで続く。
**効果**：ゾンビフラグが「無期限に潜伏、平均生存1年超、いつ誤トリガーで爆発するかわからない」から「毎週監査、自動で爆発半径を定量化し清掃 PR を生成」へと変わり、リリース技術的負債を「不可視の負債」から「返済可能な ToDo」へと転換する。

> 💡 珠玉のひとこと
> 「削除し忘れたフィーチャーフラグの一つ一つは、自らの手で埋めながら、その場所に印をつけ忘れた地雷だ；システムの腐敗は、『一時的』というこの一言から始まる。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例は深刻に過小評価されている真実を突いた：段階的リリースが生み出す技術的負債は、それがもたらす安心感と同じくらい巨大だ。ロブスターの進んだ道は、「リリース残骸の清掃人」になることだ——フラグを清掃するだけでなく、期限切れのカナリアルール、廃棄されたグレーリリースルーティング、孤児の IaC リソースも清掃する。工学的難題は**デッドコード判定の到達可能性証明**にある：90日間トリガーされていない分岐は、本当に死んだのか、それとも年に一度しか走らない決算タスクを待っているのか?エージェントは「過激な清掃が引き換えにもたらす整然さ」と「生きたコードの誤削除が引き起こす事故」の間で、到達可能性分析に支えられたあの安全線を見つけ出さねばならない。

## シナリオ50　マルチリージョンリリースのクロックスキューとグレーリリースのリズム失調検出
**背景**：サービスは世界5リージョン(us/eu/ap/sa/me)にまたがり、「リージョンごと(region-by-region)」のローリングリリースを採用、各リージョン間は30分間隔、中央のリリースコントローラが調停する。
**問題**：リリースコントローラが置かれたノードで NTP のクロックスキューが発生し、システム時刻が19分遅れた。その結果それは「自分ではまだ」us リージョンの観察期だと思い込んでいたが、実際には us はとっくに安定しており、しかも**eu と ap のリリース判定時点をすべて誤算した**——eu リージョンでは実際にはわずか11分しか観察せず(30分ではなく)早々に ap を放流した、つまり安全な観察窓を迂回したことになる。さらに悪いことに、二つのリージョンのグレーリリース時間窓が奇妙に重なり、監視データが交差汚染され、ダッシュボード上の成功率は解読不能なノイズの塊と化し、一体どのリージョンに問題があるのか誰にも言えなくなった。
**必要なスキル**：分散クロック同期診断、リリースリズム監査、マルチリージョン可観測性、時系列一貫性分析
**オープンソースツール**：Spinnaker、Chrony(NTP)、Thanos、VictoriaMetrics
**活用するエージェントの特性**：ロブスターは ClawHub の `release-cadence-guard` スキルをマウントし、リリースコントローラの「自己申告の時刻」を信用せず、**複数の独立した時刻ソース**(各リージョンの monitoring ノードのタイムスタンプ + 外部 NTP)で各リージョンの「実際の観察時間」を相互検証する。それが eu リージョンの真の観察窓がわずか11分であり、かつ ap の放流決定が19分ずれたクロックに基づいていると算出すると、ただちにリリースグループで制止する：「⏱️ リリースリズム失調：コントローラのクロックスキュー +19min(NTP 同期失敗)により、eu の実観察がわずか11min(< 30min 安全窓)で ap を放流、かつ eu/ap のグレーリリース窓が重複、監視データが交差汚染。**すでにローリングリリースを一時停止**、まずコントローラの chrony を修復し、その後リズムをリセットすることを推奨。」
**エージェントがいない場合の苦境**：「リリースコントローラが自己申告する時刻」が間違っていると疑う者などいない——これはインフラへの暗黙の信頼だ。こうして皆が汚染されたダッシュボードを前に呆然と見つめ合い、「データが読めない」のを監視が壊れたせいにする一方、真犯人は誰も検証しなかった一つのクロックなのだ。
**効果**：クロックスキューによるリズム失調が、「誰も気づかず、安全な観察窓がこっそり迂回され、リージョン横断のデータ汚染で意思決定不能」から「エージェントが多源の時刻で相互検証し、即時に制止して NTP の根本原因を特定」へと変わり、リージョンごとリリースの最も核心的な『十分な観察』という約束を守り抜く。

> 💡 珠玉のひとこと
> 「分散システムにおいて最も高くつく嘘は、しばしば最も目立たないあの仮定からやってくる——『時間は正しい』という仮定だ。」

> 🔍 一歩進んだ論評──道はどこにあるか
> この事例は哲学級の工学的真実に触れた：ほぼすべてのリリース安全機構(観察期、グレーリリース間隔、SLO ウィンドウ)は、ひそかに「時間は信頼できる」という未検証の地盤の上に建てられている。ロブスターの次なる道は、「いかなる単一の信号源も信用しない監査者」になることだ——クロックを検証するだけでなく、監視データそのものの信頼性と時系列の整合も検証する。工学的難題は**検証者自身の信頼性**にある：エージェント自身もクロックスキューが起こりうるあるノードの上で走っているとき、それは何を根拠に自分の判断を信じるのか?この問いは分散システム最古の難題へと押し進められる——絶対的な真理のないシステムの中で、どうやって『十分に信頼できる』合意を確立し、自動化の裁断を流砂の上に建てずに済ませるか、という難題だ。
